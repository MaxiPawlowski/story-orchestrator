# Gotchas

- **A wait that lists the states it accepts goes stale when a new intermediate state is added** (2026-09-22, J11.25). Plan 07 introduced `validated` — a chain the critic passed, waiting for the boundary that makes it part of what the chat is playing, promoted to `inserted` by boundary work order 42 — but J11.25 waited only for `['inserted','needs_review','failed','stale']`. A pre-generation that had **succeeded**, beats and all, sat in `validated` and burned its entire 480 s before being reported as "the prepared expansion never finished". Same class as the schema-version literal above: the fix is to wait on the property ("left queued/generating", "is a settled chain") rather than to enumerate the states that happen to exist today, and when you do enumerate, enumerate what SUCCESS looks like too. Its sibling in the same check: `before.status === 'inserted'` had to become `['validated','inserted'].includes(before.status)`, or a prepared chain that was correctly used on arrival would take the failure branch.

- **A fixture that asserts a schema-version literal goes stale on every bump, and it fails the checks that are ABOUT the format** (2026-09-22, J10). Three checks demanded `blob.version !== 3` while the blob had moved to **4**, so they failed on the number alone — the structural assertions that follow had not even run. Assert the **property** (the snapshot flags the stored version, the server holds this build's stamped blob, `engineHistory`/`visitedPath`/`pinnedStory` are present) or a structural fact, never the current literal; in jest, import `BLOB_VERSION` (v2.5 plan 11 bumped the blob to **5**, v2.6 plan 08 to **6**). A check whose first line is a version equality is a check that will need editing rather than one that will catch a regression.

- **A journey that clears the global config makes the profile picker choose the FIRST profile, so every LLM profile has to be live, not just the one you named** (2026-09-22, J1). `ui: {action: "select-profile"}` keeps the stored `extraction.profileId` **only if the panel still offers it**; `J1`'s `setup.clearGlobalConfig` empties our settings, so `current` is `''` and the action falls through to `labels[0]` — the first option in the Connection Manager order. J1 then timed out on `checkpointNot: "cp1"` with `auditCount: 0`, `blackboard: {}` and `lastAudit: null`: extraction had never run, because the first profile still pointed at a dead endpoint while the two the current work had repointed were fine. **Symptom to recognise: `auditCount: 0` with `lastAudit: null` on a chat that has taken several turns is "no profile could answer", not "the scheduler did not fire".** `ST_DEBUG_PROFILE=<name>` names one explicitly; without it, check every profile the panel offers.

- **`wait: {checkpoint: "cpN"}` races a story that advances past cpN** (2026-09-22, J6). It waits for the ACTIVE checkpoint to be exactly that id, so when real extraction carries the story through cp2 into cp3 during the check's own sends, the wait can never succeed — it burns its whole 300 s budget and reports the checkpoint the story has already left. Three J6 checks failed with that one symptom, at boundaries 4, 6 and 8. The intent ("the story has reached cp2") is monotonic, so express it as **`wait: {checkpointIn: [...]}`** listing cp2 and everything downstream of it — `checkpointIn` succeeds when the active checkpoint is any of the ids. Same trap for `expect: {activeCheckpoint}`; `expect: {activeCheckpointIn: [...]}` is the tolerant form. Reach for the exact match only when the check is *about* being parked there.

- **A privacy check that scans the whole request body is a false positive, because the transcript is shared** (2026-09-22, J5.8). The check recorded every `/api/backends/` request tagged with the drafted member and asserted no other member's private epistemic content appeared in it. It failed — `Ponticius: the request ST sent carries another member's private knowledge` — but the flagged string was inside a **user turn in the chat transcript**, which every member legitimately receives, and the journey had planted the "secret" by writing it into the chat in the first place. Measured: Arin's private block was present and correctly scoped (`- You know: the north road washed out` / `- You are concealing from Ponticius: …`) and **Ponticius's prompt carried no private block at all**. So the assertion must name the BLOCK it tests (`renderPrivateEpistemicBlock`'s header line plus its `- ` bullets) and test inside that region — the loose form also hid a real question, since the "carries its own knowledge" half passed only because that text sits in the transcript too.
- **A member's private knowledge can be created by the very draft you are measuring** (2026-09-22). Making J5.8 test inside the block exposed the second half: `Ponticius` held two private entries *at check time* and its draft's prompt carried no block — because the extraction pass that ran off that draft is what created them. Measuring a draft against knowledge it produced is circular, so the check now asserts only knowledge present **before** the trigger (`state.before`) and RECORDS each member it excluded with the reason, rather than skipping silently. The shape generalises to every "did X reach the payload" assertion over a pass that both consumes and produces X. And `--only <check>` on a journey whose earlier checks seed the state makes the guard fire correctly: with nothing seeded there is nothing to measure, and a vacuous pass is the failure mode, not the goal.

- **A page loaded while the backend was dead keeps `#send_but` hidden, and a reload does not clear it** (2026-09-22). ST caches `ctx.onlineStatus` and hides the send button while it reads `no_connection` — so every `send`/`send_generate` step dies at `locator.waitFor('#send_but') ... resolved to hidden` after 15 s, and every check downstream of the send reports its own unrelated symptom (no transition, `memoryInjection.facts present=false`, the journal missing `transition`/`payload`). This is the same "the button swap hides `#send_but`" rule as generating/disconnected, and it is NOT fixed by `st-session.mts reload` — the load-time probe fails again. **Fix: re-select the profile** (`MSYS_NO_PATHCONV=1 node scripts/debug/st-actions.mts slash "/profile <name>"`), which re-probes and restores both `onlineStatus` (it then reads the model name) and the button. Do this after repointing a Connection Manager profile at a new endpoint, before running any journey. Diagnostic one-liner: `document.querySelector('#send_but').className` contains `displayNone`.

- **A fault-matrix cell is a claim, and only a citation makes it one** (v2.3 plan 11). `test/findings/faultMatrix.json` declares nine stateful packages × nine fault shapes and `src/runtime/faultMatrix.guard.test.ts` checks the file BOTH ways: every pair must have a row, a `covered`/`partial` row must cite a test that is really in the file it names (matched as a quoted string, so `%s`/template-literal titles cannot be cited), and a `todo`/`na` row may not cite anything and must say why. The counts print, so the number only moves deliberately. Writing the census is what found the two defects: **`ExpansionCoordinator.generate` took no ownership token at all** (the last async coordinator without one — a chain generated for chat A was filed into chat B's cache and merged into chat B's story; `expansionOwnership.review.test.ts` keeps the unowned run as a negative control, because a guard test that passes with the guard removed proves nothing), and **`LoreSelector` both discarded `force()`'s `WriteResult`** (a refused force was reported as applied, so the prompt silently carried ST's own keyword scan) **and cached by chat+message+scope but not story**, so a chat that swapped to a story with the same lore scope re-forced the departed story's picks. Two lessons that generalise: a `WriteResult` nobody reads is indistinguishable from success, and **a `RunToken` cannot detect a stale CACHE entry** — it is minted at the start of a call, so a value built under a previous world is only caught by what the key names.
- **`snapshot.scanGate` right after a reopen is ST's pre-cache scan, not the chat's gate** (T7 2026-10-03, I1/I2/I6). ST's own `CHAT_CHANGED` listener runs `getSortedEntries()` (world-info.js:1013-1017) before our hydrate, so the last scan the view holds is `owner: no-story` with no story books appended; every later scan re-chooses (`ScanGateProvider.choose` is keyed by owned chat + story + path, ST caches no sorted result, world-info.js:4590-4640). A reopen diff that compares `wi.scanGate` must first make one scan after the hydrate settles (a loud generation, or in-page `(await import('/scripts/world-info.js')).getSortedEntries()` on both sides), or leave the field out. Test: `runtime/t7ReopenScanGate.review.test.ts`.
- **A `delegate` row in the ownership census must name its target in an `awaits <Class.method>` clause**, or the guard reports "awaits (no `awaits` clause), which is not a censused site". Moving a token check one hop into the function that owns the write turns the caller into a `delegate` and the callee into `checked` — the census follows the chain rather than stopping at one hop.
- **A store write that does not refresh its own injection is a silent empty block** (v2.3 plan 05, found by running J5 twice — the first run passed and the second failed). `applyEpistemic`/`applyLedger` wrote through `patch()` alone, while every other write path goes through `commit()`, which is `patch` → `updateInjection()` → save. So the per-member private staging was refreshed **only if the caller remembered**, and the caller's own guard sits *after* the write — a pass that lapsed in between stored the knowledge and injected nothing. Player-visible shape: a member drafted just after an epistemic pass is handed an EMPTY private block and loses knowledge it demonstrably holds (nothing in the store is wrong, which is why no store-level test could see it). Both applies now call `this.updateInjection()` themselves; the deterministic half lives in `coordinators/memoryInjectionRefresh.review.test.ts`, whose control case ("does not inject a secret for a member the signal did not name") is what proves the assertion is about per-member staging rather than about any injection at all. **The general rule: if a write changes state that is injected, the write refreshes the injection — a caller-side refresh is a race, not a design.**
- **A write-ahead record nobody verifies is not write-ahead** (v2.3 plan 11). `EffectsApplier.withLedger` persisted the `pending` row before the host call and then ran the effect regardless — but `persist()` cannot answer whether the row reached disk, because it wraps `saveMetadata`, which swallows its own errors. The applier now reads the plan-06 save-evidence seam (`unsaved: () => hasUnsavedChanges(extras.saveHealth)`) after the write-ahead persist and REFUSES the effect (`PENDING_NOT_SAVED`, row marked `failed`, journaled) when the save has not landed. The general rule: when a call's return value is not evidence, read the state that is.
- **The RunPod pod's llama-server binds `127.0.0.1:8080` inside the container, and the RunPod HTTPS proxy still reaches it** (2026-09-22). The pod's `start.sh` starts `llama-server` on loopback, so an SSH local-forward was assumed obligatory; it is not. Publish `8080/http` on the pod (`update-pod … ports: ["22/tcp","8080/http"]`) and point the Connection Manager profiles at `https://<podId>-8080.proxy.runpod.net` — an `update-pod` restarts the container, so the model reloads (~3 min for the 19 GB Artemis GGUF), and ST's own server-side proxy means no CORS problem. Do NOT publish 18080: nothing listens there. The `--host 0.0.0.0` experiment via `LLM_EXTRA_ARGS` is unnecessary. **Repointing those profiles is an install-wide change — record the old `api-url` and put it back** (`Artemis RunPod RP` and `Story Orchestrator Memory RunPod` both pointed at `http://127.0.0.1:18080`).
- **An EXITED pod can hold its host's GPU and its network volume**: `pod-action start` answers `400 "There are not enough free GPUs on the host machine"` and no amount of retrying helps. A NEW pod with the same volume in the same data center does start — the earlier "the volume is unclaimable while the exited pod holds it" reading was wrong, and a fresh equivalent pod ($0.72/hr, RTX PRO 4500, EU-RO-1) came up first try.

- **`Math.max(0, NaN)` is `NaN`, and a `NaN` message id rewinds the whole story** (2026-09-23, V4). `engine.shouldRollbackFromMessage` normalizes with `Math.max(0, Math.floor(id))`, so a non-finite id makes every `lastMessageId < id` comparison false, the predicate answers true whenever ANY transition has fired, and `boundaryBeforeMessage` falls back to boundary 0. A host mutation event with no usable id therefore rewound a story that had moved all the way to its start, and `Number(null) === 0` did the same through the other door. Parse host ids with `hostMessageId` (turnBridge.ts), never `Number(value)`. A mutation with no id rewinds nothing, and `runRollback` refuses a non-finite id. A probe for this needs a FIRED transition first, or rollback from 0 is a noop and the check cannot fail.
- **The ownership census used to see only methods and function declarations** (fixed V3, 2026-09-23). Arrow functions (object-literal deps like `selectionDeps.clearStory`, class-property arrows, `.then`/`map`/`withLedger` callbacks), property assignments after an await, and every file outside `src/runtime` + `src/wizard` were invisible, and a comment naming `run.stillOwns()` counted as a check. Three of the defects V3 fixed sat in that shadow (`clearStory`, the scheduler's error writes, `applyWorldInfo`); two more (the judge fallback, the mirror) were `checked` rows whose check did not precede every write, which a body-level census cannot see; the rest were plain `todo` rows. The census now names an arrow by where it lives (`Class.deps.key`, `callback[cp]`, `Owner>withLedger`), so when you move code into or out of an object literal, expect its row key to change.
- **Run `npm run typecheck:test` with every item that touches a test file.** Jest does not type-check (`jest.config.cjs` runs ts-jest with `diagnostics: false`), so a test with a type error passes and still breaks `typecheck:test`. V5 and V15 went to master that way (found during V3).
- **An occluded browser starves `requestAnimationFrame`, and Playwright's click then times out on a button that never moved** (2026-09-23, J3.1 twice in three runs). The failure reads `locator.click: Timeout 30000ms exceeded … element is not stable`, which looks like layout jitter. Two timer-based probes found `#send_but` perfectly still during real reads. A per-frame probe found **16 frames in 15 s**: Chrome throttles rAF to about 1 fps for a page it treats as backgrounded or covered, and Playwright's stability check needs consecutive frames with the same box. `sendUserMessage` now clicks with `force: true` after its explicit visibility wait, which skips only that check. The diagnostic that tells the two apart: count rAF callbacks over a few seconds (`document.getAnimations()` was empty too, so nothing was animating). Any other harness click can hit the same starvation; if a `locator.click` times out on stability, count frames before hunting for a moving element. On a locked or occluded desktop a headed lane browser rendered 0 frames (2026-10-01, lane 4), so `shot` and every rAF-polled wait timed out; `st-session start` now launches Chrome with `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding --disable-background-timer-throttling` (a browser started before that needs `st-session stop` + `start`).
- **A deleted group chat can come back after the delete was verified** (2026-09-23, V18). ST saves a group through a 1 s debounce that captures the group OBJECT (`group-chats.js:140`, `saveGroupDebounced(group, reload)`). `getGroups()` replaces the array (`groups = data.slice()`), so a pending save scheduled before a reload still holds the OLD object. It lands after the cleanup's check, re-lists the deleted chat and points `chat_id` at it, and the next open of the group re-creates the file with a greeting. Anything that calls `getCharacters()` mid-run triggers it; creating a character does (provisioning reloads). Seven sandbox chats leaked this way while the cleanup reported them deleted. `deleteSandboxChats` now waits out the debounce, re-reads the server, repairs a resurrection on the live object, reports `resurrected`, and fails the run on `notDeleted`. Verify a group deletion no sooner than about 2.5 s after the last group write.
- **`editGroup(id, false)` is a 1 s debounce, and `_save` never reads the answer** (2026-09-23, V15c). A group write through it returns before anything reaches the server, so every cast write answered `ok` early; a restore interrupted by a reload in that second was lost with its ledger row already `reverted`. `stHost/groups.ts` saves with `editGroup(id, true, false)` and reads `/api/groups/all` back. A live check cannot see the debounce by reading state afterwards (an awaited event means the rollback, its persist and the debounce are all done before the next step), so it asserts request ORDER instead: `/api/groups/edit` before the rollback's `/api/chats/group/save`.
- **`ctx.saveSettings` does not exist, and ST's `saveSettings` swallows its own failure** (2026-09-23, V20e). `st-context.js` exposes only `saveSettingsDebounced`, so every `if (typeof ctx.saveSettings === 'function') await ctx.saveSettings(); else ctx.saveSettingsDebounced()` in the harness took the debounced branch. Config restores slept a blind 1.5 s, and the extraction restore, story removals and asset cleanup returned before anything reached disk. The exported `saveSettings` in `script.js` (8051) catches its own fetch failure, so awaiting it proves nothing either. The harness persists through `scripts/debug/lib/settingsSave.mts` `saveSettingsNow(page)`, which observes the `POST /api/settings/save` answer. Use it for any new settings write in a debug script.
- **Swapping the played graph must keep the engine's queue AND its history** (2026-09-23, L4). `replaceStory` used to `loadStory` + `hydrate(state)`: `loadStory` builds a fresh `ApplyQueue` and `hydrate` without a history clears the boundary log. So every expansion merge or stale-rebuild threw away the accepted deltas waiting for the next boundary, and the rollback history with them — and `commitBoundary` revalidates (and can rebuild) BEFORE it drains. Symptom: a write that answers ok, a boundary that advances, `queue {applied:[],discarded:[]}`. Use `engine.replaceGraph(story)`; never re-create the engine state by hand around a graph change.
- **A staled chain is part of what a rollback undoes** (2026-10-03, T6-1-2). `revalidateInserted` never stales the ACTIVE generated chain, but once play leaves it (a stub exit into the anchor) the next revalidation stales it and the merged graph loses its checkpoints, while the boundary snapshots still name them. Swiping the reply that left it restored `activeCheckpointId: gen_…` into a graph without it: `activeCheckpoint` undefined, `requirementsHost.refresh` threw 23 times, no boundary ever committed again. A stale now records `staledAt {boundary, from}`; `runRollback` calls `restoreStaledAfter(restoredBoundary)` (rebuilds the graph) before anything reads the checkpoint, then `engine.ensureActiveCheckpoint()` falls back to the trail and journals if the checkpoint is still gone (also at every `commitBoundary`). `engine.activeCheckpoint` is typed `Checkpoint | undefined`, and the pipeline reads `error` while a played state has no checkpoint. Test: `runtime/t61Rollback.review.test.ts`.
- **`npm run test:release` rewrites `dist/manifest.json`** (2026-09-23, L2). The bundle is untouched, but `builtAt` and the source hash move, so a run header diffed around a live batch reports build drift that is only the manifest. Do not run the release suite during a live batch; if it ran, check `bundle.served.sha256` — that is the field that says whether the code under test changed.
- **The main bundle's babel targets are ST's own browser floor, not package.json `browserslist`** (2026-10-02, bundle headroom). webpack's babel-loader used to read the `production` browserslist (`>0.2%, not dead`), so preset-env down-levelled object spread and friends and inlined its helpers into every module (288 copies of `ownKeys`/`_objectSpread2`): about 191 KB of `dist/index.js`. Prod main went 1,249,137 B -> 1,057,800 B with no source change. Move the floor only when ST moves its own; Storybook keeps its own babel config in `.storybook/main.ts`.

- **A `try`/`catch` around an awaited save is a guard against a failure the host cannot report** (2026-09-22, plan 05). `saveMetadata` wraps `saveChatConditional`, which wraps the whole write in `try { … } catch (error) { console.error(…) }` (`script.js:9412–9439`) — it *never rejects*.
