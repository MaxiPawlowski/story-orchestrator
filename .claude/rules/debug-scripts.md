# Debug Scripts

For any live/E2E work, load the **`debug` skill** (`.claude/skills/debug/SKILL.md`) — full tool reference, recipes, error table. Also: `scripts/debug/README.md`.

Essentials:

- **The repo lives at `C:\dev\story-orchestrator`, outside ST** (v2.6 step 0, 2026-09-30). ST's slot `public/scripts/extensions/third-party/story-orchestrator` holds only the staged allowlist: `npm run build:dev && npm run stage -- --flavor dev` (or `npm run build && npm run stage` for prod), then `st-session.mts reload`. `serve:dev` alone no longer reaches ST. The ST root is `ST_ROOT` or the gitignored `.st-root` file (`scripts/lib/stRoot.mjs`), never derived. The pre-move checkout (with the 70 old agent worktrees and the old `.debug`) is parked at `C:\devackups\story-orchestrator-in-st-2026-09-30`; `.debug` was copied to `C:\dev\so-lanes\0\debug`.
- Scripts are `.mts`, run directly: `node scripts/debug/<tool>.mts`. Artifacts → the debug dir: `SO_DEBUG_DIR`, default `<so-lanes>/0/debug` (`C:/dev/so-lanes/0/debug`, beside lane 0's browser profile) since v2.5 plan 12 P3, because ST serves everything under `public/` and run logs, journals and payload captures hold chat text. - **The live harness runs on the DEV build, and ST serves whatever `dist/` holds** (v2.5 plan 12). ST loads `/scripts/extensions/<name>/<manifest.js>` (`public/scripts/extensions.js:819`, `:434`) and our `manifest.json` names `dist/index.js`. Every lane is its own server over the SAME code tree (`st-lanes.mts` spawns `server.js` with `cwd: ST_ROOT` and only a different `--dataRoot`), so every lane serves the one `dist/` of the checkout inside ST's `public/` (not a worktree's). `npm run build` writes the PROD bundle there: no `storyOrchestrator*` handles, no debug responses, so every script that drives `storyOrchestratorRuntime` fails on it. `npm run build:dev` writes the dev bundle to `dist-dev/`, which ST never loads. **Switch to dev:** `npm run build:dev && npm run serve:dev` (`scripts/release/serveFlavour.mjs`: checks the dev manifest's flavour, file list and hashes, then replaces `dist/` with it), then `node scripts/debug/st-session.mts reload` (a lane: `node scripts/debug/st-lanes.mts run <n> -- scripts/debug/st-session.mts reload`). **Back to prod:** `npm run build` — required before `npm run test:release`, which refuses a dev `dist/`. Guards: `so-journey` and `so-scenario` refuse to start when the page has no `storyOrchestratorRuntime` and say whether it serves prod or a stale page (`lib/bundleFlavour.mts`); `st-lanes.mts batch` refuses before any lane runs when the served `dist/manifest.json` is not `flavor: "dev"`; the run header records `build.manifest.flavor`. `npm run dev` (watch) writes `dist-dev/` too, so follow each rebuild with `npm run serve:dev`.
- Responsive testing: prefix EVERY command with `ST_DEBUG_VIEWPORT=<W>x<H>` (e.g. `390x844`) to hold an emulated viewport; unprefixed runs snap viewports narrower than 1280px back to 1920×1080.

Repo `.mcp.json` points the playwright MCP at that endpoint — **an MCP server without `--cdp-endpoint` launches its own isolated Chromium** whose state scripts can't see. Verify sharing with a `globalThis.__x` marker round-trip (MCP `browser_evaluate` set → `st-eval.mts` read) before any shared-state MCP work.
- Chat/entity control: `st-navigation.mts list-entities | open-group <id|name> | open-character <name> | list-chats | open-chat <chatId> | new-chat`. Group draft: `st-actions.mts trigger <member>`. Ad-hoc in-page JS: `st-eval.mts "<js>"` (ctx + rt in scope) — no more throwaway .mts files.
- Test cleanup: `so-library.mts remove "<title>"` (the v2Stories library) + `so-library.mts wipe-chat-meta` + `/delchat`.
- **The memory mirror leaves a lorebook per chat** (`Story Orchestrator - <title> - <chatId>`, recorded in `getSnapshot().memory.wiBook`), and deleting the chat does not delete it. `so-scenario --sandbox` and `so-journey` cleanup delete them. The guard records every story title and `wiBook` after each step. Once the chats are gone, cleanup deletes each listed book whose name is `<recorded title> × <owned chat id>`, via `deleteWorldInfo` after `updateWorldInfoList`. A name without an owned chat-id suffix is never touched. The report is `cleanup.mirrorBooks {deleted, failed, leaked}`. A scenario that reads its mirror book takes the name from `memory.wiBook`, never a fixed title: `loadWorldInfo` answers a missing name with an empty dummy. The old fixed-name `Story Orchestrator - <title>` books from before per-chat mirroring are out of scope for run cleanup; v2.5 plan 11 step 9 moves them to a backup outside the ST tree.
- **`storyOrchestratorDebug*` globals outlive a run** until the page reloads. The next run's first real pass got plan07-memory's leftover mock fact, and so would a real player in the shared browser. `so-scenario --sandbox` now clears them at start and at cleanup, as `so-journey` setup already did at start. A mocked plumbing scenario must also keep real extraction out: extraction is on install-wide since v2.1 plan 02, and real reads of the group greeting raced plan07-memory's exact memory counts. It pins `storyOrchestratorDebugExtractionResponse = 'SCENE_NONE'` before `import_story`, which parses clean and has no rejected line, so extraction does not pause.
- **A step's `eval` is one line of JavaScript, so a `//` comment in it comments out the rest of the step.** `page.evaluate` wraps the string in a `new Function`, and a `//` swallows everything after it — including the closing braces — so the step fails with `SyntaxError: Unexpected end of input` and nothing else (2026-09-21, J2.12). Put the explanation in the check's `goal`, or use `/* … */`, which is also safe only if the step is a single line.
- **Fixtures are only syntax-checked when they run.** `validateFixture` closes the *vocabulary* (verbs, keys), not the JS inside `eval`. A malformed eval is a runtime failure mid-run, so syntax-check a new eval before a long run: `new Function('return (async () => { ' + step.eval + ' })()')`.
- **Git Bash mangles leading-slash slash-command args**: `node scripts/debug/st-actions.mts slash "/delchat"` gets MSYS-path-converted to a Windows path (`C:/Program Files/Git/delchat`) and silently no-ops — the JSON result's `"command"` field shows the mangled path. Prefix with `MSYS_NO_PATHCONV=1` for any slash command starting with `/`.
- **`cast_changes`/`setGroupMembersDisabled` mutate the group's `disabled_members`, not the chat** — this persists across `/newchat` sandbox sessions and outlives `--sandbox` cleanup. A live scenario that disables a roster member leaves that member disabled in the real group afterward; restore it (e.g. another `cast_changes: {enable:[...]}` pass) before ending the session. **Restore after deleting the sandbox chat, not before** — `/member-enable` inside the sandbox chat reports success and is then undone when ST reloads the group behind `/delchat`; `so-journey` now enables members post-`/delchat` and reports the resulting `disabledMembers` in its cleanup record (v2.1 plan 04).

- **The wizard's technical stage chips sit behind a `details` disclosure** (v2.3 plan 09): the tab's control is four author-facing steps (Premise / Turning points / Characters / Setup, `[data-so="wizard-step"]`) over the unchanged five `COPILOT_STAGES`. The chips carry `data-so="wizard-stage"` and their `aria-pressed` is the only thing that reports the running stage — `so-ui.mts` reads the stage from that attribute, and `runWizardStage` opens the disclosure before clicking because Playwright will not click a hidden button. J9's `expect_ui.contains` on `#so-wizard` still passes: a closed `details` keeps its text in `textContent`.
- **The wizard creates real ST assets** (v2.1 plan 06). Drive it as an author with `so-ui.mts open-wizard | new-story-wizard | wizard-run [stage] [message] | wizard-answer [a1|a2|a3] | wizard-apply [index] | wizard`. Clean up with `so-assets.mts remove --marker <prefix>`, and never delete an unmarked asset. The whole scope is the marker, plus the `applied` ledger of **test** wizard sessions only: keys starting with the slugged marker (`so-j9-wizard`), plus, in a journey, entries recorded since the run's `snapshotAssets` baseline. A real author's sessions, their resume state and the assets they created are never touched. With a baseline, any asset that existed before the run is spared (`protected`), and only this run's own sessions are dropped (marker-keyed, or one whose ledger entry was actually deleted). An **empty baseline is untrusted, not empty**: cleanup then falls back to marker-only scope and says so (`baselineUntrusted`), because an empty one used to promote every foreign session's ledger into scope. The baseline is written to `.debug/so-journey-asset-baseline.json`, and `restoreGlobalConfig` refuses to write an empty snapshot over a populated config (that clear is self-perpetuating and takes `extraction.profileId` with it).
- **The World Info curator writes to a real lorebook** (v2.1 plan 07), so drive it the way an author does and clean up after it: `so-scenario` step `{stagecraft: {action: "curate"|"accept"|"reject"|"accept-op"|"reject-op"|"apply"|"state"}}`, review through the drawer with `so-ui.mts stagecraft | curator-accept [index|text-first] [text] | curator-reject [index]` (`ui: {action:"stagecraft", minOps}` waits for the cards; `pick:"text-first"` lets the model choose the op kind: never hard-code that a real curator proposes a text change), and assert with `expect: {background}` / `expect: {stagecraft: {...}}`. It is on by default since v2.5 plan 19 (`#so-curator-enabled`), a journey that switches it on must snapshot the global config, and `so-assets.mts remove --marker` deletes the lorebook it wrote into.
- **A fixed timeout around a real generation is a hardware assumption** (2026-09-20). `sendUserMessage` waited a hard-coded 15s for idle *before* typing, which the caller's `timeoutMs` never reached. Invisible on the 5090; fatal on the RTX PRO 4500 at ~33 tok/s, where ordinary turns run 15-35s — checks carrying a 300000ms budget died at 15s (J11.16). It is now `preSendIdleTimeoutMs`, default 60s. When the backend moves, suspect every fixed timeout in the harness before suspecting the product.
- **Another session can move the page out from under a run, and the guard is the only thing between that and corrupt results** (2026-09-20). A peer's `st-navigation.mts open-group` timed out; it then ran `new-chat`, which acted on whatever group was open — mine — creating a chat there and moving the page mid-J8. The journey's sandbox-escape check caught it and aborted before writing anything. Two rules follow: pin the group id explicitly on every navigation, and treat an `open-group` timeout as a hard stop, never a warning to push past. Also note `evictWorldInfoCache` reloads books page-wide: run it while someone else's curator pass is mid-flight and you hand them a false failure, not a real one.
- **Pin the sandbox group on a shared install**: `so-scenario run <file> --sandbox --group <id|name>`. Without `--group` the sandbox takes ST's *most recent* group, which may be another session's (2026-09-19: a run created and deleted its own chat inside another session's group). Journeys take `setup.group`, or the group already open.
- **A disconnected ST hides both `#send_but` and `#mes_stop`**, and `getGenerationState` used to read a hidden send button alone as "generating", so every `wait: {idle}` timed out while the backend was down. Generating is now `stop visible || (send hidden && stop not hidden)`. With the backend down the mocked scenario corpus runs; only steps that make a real model call fail (`plan08-hygiene`).
- **In a group the resting epistemic block is empty by design** (2026-09-19) and the private block is swapped in per drafted member, so a scenario asserting it must call `onMemberDrafted(chid)` first — **ST's numeric character index** (`ctx.characters.findIndex(...)`), never a roster id. `plan10-epistemic-ledger` asserts both halves.
- **A capability probe may be async, and must not read a global an earlier check set**: a check that reloads the page wipes it, and the probe is cached on first use, so everything after the reload blocks (2026-09-19: five J11 checks). `judge-plugin` now fetches the plugin's own status.
- **Every check imports the story it needs**: `--only` runs one check against a fresh chat, so a check that inherits a story from an earlier one seeds nothing (J11.9/J11.10 seeded 0 of 10). Run the no-backend subset with `--only` to catch the coupling the v2.1 J9 finding warned about.
- **Driving our settings checkboxes**: they live inside `<label>`s, so `input.click()` toggles twice and nets zero (the label re-dispatches to its control) — click `box.closest('label')` instead. And the label only forwards while the panel is **visible**: with the Extensions drawer closed the click is swallowed and the setting silently stays put. Open the drawer first (`ui: {action: "open-settings"}`), then click. And **drive the toggle by the store, never by `box.checked`**: a click while the panel was hidden toggles the DOM without a React re-render, so the box can read `true` while the setting is `false` — a helper that trusts it skips the click and the check fails on the second run (2026-09-19).
- **Journeys are the composition gate** (v2.1): `so-journey.mts --list` / `run <id>`; catalog and check tables in `docs/plans/v2.1/test-plan.md`. Fresh-start by default; outcomes are `pass|fail|blocked|not-runnable|skipped`; `--strict` turns `blocked` into failure at acceptance. **Run a journey twice before believing it**: the plan-08 acceptance run found a stale-cache bug (J5) and a parser-tolerance gap (J8) that only a second consecutive run exposed. Archive the run that greened a gate under `test/journeys/records/<gate>/` — `.debug` rotates. Global-settings clearing is snapshotted to `.debug/so-journey-config-snapshot.json` first — `so-journey.mts restore-config` recovers a crashed run.
- **Nondeterministic journey steps** (2026-09-19, J8 on Artemis): assert whatever the real model chose, never a hard-coded op kind, and read the prompt ST actually sent from `GENERATE_AFTER_DATA` (main `Generate()` only). A fetch wrapper on `/api/backends/` also catches memory-model and curator calls. A check that measures "nothing else changed" starts after `wait: {schedulerIdle: true, quietMs}`, because a slow model is still reading the previous turn when the chat goes idle. `"log": true` next to a step verb prints its output, so an archived log shows which branch ran.
- **Session journal**: `so-journal.mts export|show` writes `.debug/journal-<chat>.md|json` — the artifact a human-eval session hands back. The drawer's ⚑ control files a flag (`#so-flag-moment`).
- **Run header** (v2.3 plan 01 §A0): `so-run-header.mts capture --label <name>` pins every variable of a live run — build, host + macro engine, main/extraction profiles, judge uses, stagecraft flags, extraction cadence/lag/profile, chat, story, group cast, and the `v2Stories` / `wizardSessions` / lorebook-selection inventories. `diff <baseline.json> [--allow a,b]` re-captures and exits 1 on any difference the recipe did not declare; `--allow` takes paths (`chatId`, `stagecraft`) or single list items (`inventory.v2Stories:+SO-J12`). **A declared addition does not excuse an undeclared removal in the same list** — that is the S12 library-loss case. A field the header cannot read lands in `warnings` rather than as a silent `null`, because a value that never changes can never fail a diff.
- **The run header records every profile's api-url (`profiles.urls`) and the active sampler (`sampler.preset/temp/top_p`)** (V22b, 2026-09-23). Before that, a profile repointed at a pod and never put back, and a fixture that left the whole install on its probe preset (V24), both diffed clean. Diff around anything that touches a profile or a preset.
- **Live tails** (v2.3 plan 01 §A0): `so-journal.mts follow --out <f.jsonl>` is what the machine saw while a human plays — journal events plus the full extraction audit (window, trigger, scope, prompt, raw response, each rejected line). `st-payload.mts arm --persist --out <f.jsonl>` keeps every generation request of the session, with the drafted member. Both survive reloads (re-read / re-arm) and both keep writing when stdout is closed — `follow | head` used to kill the tail on EPIPE mid-poll and lose that poll's audits silently (2026-09-20).
- **The payload capture index is monotonic, not the ring position** (fixed 2026-09-20). It was `entries.length` while the ring keeps the last 100, so every capture past the hundredth got index 100: `watch` stopped printing there and any persisted record lost the rest of the session without an error. Entries now carry a monotonic `index` plus an `epoch` (a reload restarts the index, and the epoch is how a drain tells that from new captures); `drainPayloads` reports `dropped` when the poller fell further behind than the ring holds.
- **The scenario vocabulary is closed** (v2.3 plan 01 §C): `scripts/debug/lib/scenarioSchema.mts` lists every verb, modifier, `expect`/`expect_ui`/`wait` key and `ui`/`stagecraft`/`copilot` action the step engine honours, and both runners validate a fixture **before** running it. A typo is now a load error naming the key (`unknown key "activeCheckpont" (did you mean "activeCheckpoint"?)`), an empty assertion object is refused, and a step carrying two verbs is refused because the dispatcher would run only the first. Adding a verb or assertion key means adding it here too, or every fixture using it fails to load. Note `auditCount>=`, `reconciliationEvents>=` and `sceneBreaks>=` are real vocabulary read by bracket access, not typos.
- **A step must not *return* a value carrying `ok:false`, however correct its refusal was.** T2 reads the step's result, so an assertion of the form "this call is refused" — which naturally returns the refusal object — fails the step it just proved. Return a wrapper instead: `return { refused: true, message: outcome.message }`. This cost J9.2 from plan 01 until plan 02 re-ran the journey (2026-09-21); the fixture was right and the harness read its evidence as a failure.
- **A step whose result reports `ok:false` now fails** (v2.3 plan 01 §C, T2). It used to be logged as a passing step, so an import that never landed read as green and every later assertion measured the wrong world. A step that is meant to fail carries `expectFail: true`, and then succeeding is the error. This is enforced once in `runSteps`, so it covers every verb including new ones.
- **A journey reports three gates, not one** (v2.3 plan 01 §D): automated / human / cleanup, each counted and printed separately. A cleanup failure or a leaked asset fails the run **with or without** `--strict`. `--strict` additionally fails on blocked, not-runnable and skipped. `--only` marks the record `partial`, so a subset run can never stand for a gate. New flags: `--group <id>` pins the group from the command line, `--require-human-record <file>` fails when a rubric row is unscored.
- **A journey check can declare the outcome the runner must produce** (`"expect": "blocked"`). That is how J0 gates the runner itself: J0.3 must report blocked (its steps never run) and J0.5 must report fail. J0 is green only when the classifier agrees.
- **Extraction settings are install-wide and are now captured before every journey and restored after it** (S11). Only J1 used to snapshot config, so J8/J9 left cadence 1 behind for the next run and for real play. The restore reads back and reports as `cleanup.extraction`.
- **`ctx.onlineStatus` is a cached label, not a probe.** It happily names the model while every Connection Manager profile is unreachable, so an install can look connected and answer nothing. To actually check, call a profile: `ConnectionManagerRequestService.sendRequest(<id>, [{role:'user',content:'Reply with exactly: PONG'}], 16, {extractData:true,includePreset:true,includeInstruct:true,stream:false}, {})`. A dead backend fails in under 10 ms with `API request failed` (measured 2026-09-20 on all three profiles). Do this before blaming the product for a live gate that will not move.
- **With the backend down, a send still appends an EMPTY assistant message, and that commits a boundary.** So boundaries advance, `wait: {idle}` is satisfied, and `send_generate` used to report `ok` in 4–8 s while nothing had been said — the check then failed 300 s later on a symptom five steps away. `send_generate` now returns `replied` / `lastSpeaker` / `lastLength` and warns when nothing answered; a step that requires an answer sets `expectReply: true` (then a silent turn fails the step). It is not fatal by default because **silence is legitimate** under talk control (`allow_silence`, a director returning NONE) and looks identical at this layer.
- **A scripted `.click()` is not a click** (v2.3 plan 01 §H). `element.click()` fires whether or not the element is on top, so a control can be unreachable to a real pointer while every journey that drives it passes — which is why the review saw the wizard button intercepted and J1 did not. `ui: {action: "hit-test", selector}` asks which element is topmost at the target's own centre. It names the cause: `disabled` (the control is `pointer-events: none` — correct, not a defect), `overlay` (something unrelated covers it), `ancestor` (a layout problem), `offscreen`, `no-box`, `missing`. `#so-self-test` reads `disabled` on a normal install; do not read that as a defect.
- **Extraction settings are install-wide, and BOTH runners now capture and restore them** (S11, `scripts/debug/lib/extractionSettings.mts` — one shared reader so the two ends cannot drift). `so-journey` leaked them because only J1 snapshotted the config; `so-scenario` leaked them because it had no restore at all. Running the 14-scenario mocked corpus left **extraction disabled install-wide** and `stabilityLag: 1` behind — `plan06-convergence` writes the lag, and a failed read pauses extraction for the whole install — so the next real player would have got no extraction, silently. Measured and then proven fixed with `so-run-header capture` / `diff` around the whole corpus (7 blocking differences before, 0 after).
- **Diff a run header around any batch of runs, not just one.** The leak above was invisible per-scenario and obvious across the corpus. `chat.authorView` differing is *not* residue — it is a per-chat override, so another chat legitimately reads another value.
- **The live suite scores every tier a fixture states, not just plot deltas** (v2.3 plan 01 §F). It scored `deltas` only, while 22 of 22 extractor fixtures carried an unscored `facts` expectation and 21 carried an unscored `rejected` one — and the number was quoted as overall extraction accuracy. Per-tier floors now bind independently (`--min-tier facts=0.85,rejected=0.9`), `--expect-count <n>` refuses a shrunken denominator (three of twenty-two passing used to report 100%), an errored fixture is named `incomplete` and fails the run, and the headline is `plotDeltaAccuracy`. A needle that cannot fail — `mustContain` with an empty string, in 16 of 22 fixtures — is reported as `vacuous` and never counted as coverage. The floors are **un-calibrated** until the first real run sets them.
- **A journey check reports whether it passed on the FIRST attempt** (S5). `attempts`/`retryBack` make a single-sample model assertion reportable, but "passed eventually" is a weaker claim than "passed first time", and only the second says a repair worked. F1 is scored on the first-attempt rate, printed as `first try: N of M passing check(s) needed no retry`.
- **Harness unit tests**: `npm run test:debug` (`node --test scripts/debug/**/*.test.mts`) — jest's roots are `src/*` only, so the debug tooling gets node:test, the runner `test:plugin` already established. Tests drive the shipped closures against a fake `page` (`{ evaluate: (fn, arg) => fn(arg) }`) with `SillyTavern` / `storyOrchestratorRuntime` stubbed on `globalThis`, so they exercise the real capture path rather than a replica of it.
- **ST hides `#send_but` while generating** (it swaps in `#mes_stop`), and a stopped stream leaves `streamingProcessor.isFinished === false` behind forever — `getGenerationState` treats the button swap as truth and requires a continuous idle window, so group turns are not cut short between members.
- **ST nests our settings panel two drawers deep** (`#extensions-settings-button` → `#rm_extensions_block` → our `.inline-drawer`). Anything driving the panel must open by *visibility*, and must close the nav drawer afterwards — an open Extensions drawer hides `#options_button` and `#send_but`.

- **A journey must establish the requirements its story declares** (v2.3 plan 04, 2026-09-21). `requirements.lorebooks` is satisfied only by the **globally selected** set — install-wide, shared with every other session and with every sandbox cleanup — so a journey that never asked for its book can have its gated latches silently become no-ops, which surfaces as a 300 s `wait: {checkpoint}` timeout five steps from the cause. Declare `setup.activateLorebooks: [...]` (the runner activates what is missing and deactivates only what it activated), and keep a guard step that fails on `!snapshot.requirements.ready` naming `missingLorebooks`.
- **A scenario `send` does not commit a boundary by itself** (2026-09-21). The engine's `lastMessageId` therefore lags the chat, and a manual read (`runNow`, the `extract` verb, `/cp extract`) taken straight after a `send` used to have an EMPTY window — plan 02's evidence rule then rejected every mocked delta, and the fixture failed five steps later as "the checkpoint never arrived". `runNow` now reads up to the newest message in the chat. Two fixtures remain red for their own reasons (`plan04-pacing`'s calibrated EMA, `plan06-convergence`'s missing boundaries) and are recorded in the plan-04 gate record.
- **`$?` after a command substitution is the substitution's status**: `run "$f" > log; printf "%s" "$(basename $f)" "$?"` prints the `basename` result, always 0, so a whole corpus run can report success while scenarios fail. Capture `code=$?` on the line right after the command, before any substitution.
- **A batch of runs needs a run-header capture around it** — and the open chat is legitimately part of the diff. `so-run-header diff` complaining about `story.*` after a corpus run is the previous chat's story being gone from view, but the same fields are how a *wiped* chat shows up: that is how a chat of the user's was found emptied on 2026-09-21 (restored from `data/default-user/backups/`, per-save copies ST keeps).

- **Parallel lanes** (2026-09-24): `node scripts/debug/st-lanes.mts seed|start|stop|status|env|run|batch`. A lane is its own ST server (port 8100+n, `--dataRoot` seeded from `data/default-user` minus backups/vectors/thumbnails, about 160 MB) and its own browser (CDP 9300+n, `SO_DEBUG_DIR` per lane). Install-wide state therefore never crosses lanes, so journeys and scenarios that snapshot and restore the global config can run side by side. `batch --lanes 1,2 --repeat 2 --strict J3 J5 test/scenarios/x.json` runs each item `--repeat` times back to back on ONE lane, so "twice" stays "consecutive on one install". The model backend is shared (llama-server `LLM_PARALLEL`, 2 today), so more than two LLM-heavy lanes queue at the model. **Lanes live OUTSIDE the ST tree** (`C:\dev\so-lanes`, or `SO_LANES_ROOT`): a lane's data root holds a copy of `secrets.json`, and everything under `public/`, including this extension's `.debug/`, is served over HTTP. A lane is a copy, so a run that escapes its sandbox there damages nothing real, but a lane result is evidence about the lane's copy of the install. Re-seed (`seed n --fresh`) when the real install's characters, groups or lorebooks change.
- **Adolion runs start from `adolion-fresh`** (v2.6 plan 02 step 0, overview rule 14): `node scripts/debug/adolion-fresh.mts seed <lane>` re-seeds lane n (1+, never 0), strips the campaign's own books, cards, `Adolion - ` groups, library records and bindings from the copy, switches `image.enabled` and `sprites.enabled` off in the lane's settings BEFORE the server starts, installs the campaign at the commit in `scripts/debug/adolion-fresh.pin.json` (`git archive` export + its `install_st.py` with `ADOLION_ST_URL`), creates the groups, selects exactly the lorebooks the stories require, imports the nine stories, writes the so-assets baseline to `<lane>/debug/adolion-fresh-asset-baseline.json` and checks the inventory against the pinned build (`<lanes>/<n>/adolion-fresh/inventory-*.json`, diffed against the lane's last one). `check <lane> [--drop-book <name>]` re-checks a running lane. **A lane that imports a story can reach the shared ComfyUI**: since v2.5 plan 19 `image.enabled` defaults on, and 2026-09-30 two seeds with it inherited from the real install posted `/prompt` to 127.0.0.1:8188 during story imports alone (no turn played), while another session was rendering sprites there; the lane log shows the connections reset. `adolion-fresh` fails a seed whose lane log shows any ComfyUI call. Any other script that starts a lane and imports or plays must switch both off first, and never calls `/sd` or `/interrupt`.
- **Session tooling** (v2.6 plan 14): `so-session.mts start <charterId> [--lane n] [--allow-comfy] | stop | digest | cards --write | validate | index` runs one human session per card of `test/sessions/charters.json` (validated against `test/sessions/adolion-stories.json`; `docs/plans/v2.6/14-cards.md` is generated and drift-tested) on an adolion-fresh lane, headed, with tails and run header in `test/sessions/<tier>/<id>-<n>/`. Images/sprites are written off unless the card asks, and such a card is refused without `--allow-comfy`. `digest` ignores rows before `session.playFrom`. Reference: the debug skill's "Human sessions" section. **Autonomous driver** (plan 15 Part B): `turn | swipe-new | regen | edit | delete | switch-chat-mid-gen | reload-mid-gen | flag | shot | age | adopt | score | plan | budget | runbook`; every live verb appends to `<dir>/turns.jsonl`, `start` refuses when the routing pin fails or when it would re-seed a lane holding a chat a later card continues, and `stop` captures the evidence before killing the tails. Sequence per card: `docs/plans/v2.6/14-autonomous-runbook.md` (generated, drift-tested).
- **`ensureSTReady` waits for the page's CSRF token before comparing it** (2026-09-24): a cold page has an empty token for about a second after the context exists, so every fresh lane browser read as "stale".
- **Deleting a chat whose mirror book carries the `so-owner` marker raises a popup** (v2.4 plan 02 T14, `runtime/mirrorReaperHost.ts`): "The chat "<id>" was deleted, but its story-memory lorebook … Delete the lorebook too?". Sandbox cleanup deletes chats, so `so-scenario`, `so-journey`, `so-turn-types-check` and `so-mutation-check` call `settleReapPrompts` after their chat and mirror-book cleanup: it declines every such question naming a chat the run owned (the reaper then finds the book gone and leaves no Repair row) and reports `cleanup.reapPrompts {dismissed, leaked}`; a question left open is a leak and fails the run, because a modal left behind blocks the next one. Any new script that deletes a chat has to do the same, or the popup holds every later reap behind it. `so-mutation-check` has no mirror-book cleanup, so a book it declines stays behind as a Repair row.
- **The scenario `send` verb is `/send compact`: it posts the player's line and generates NOTHING** (2026-09-25, v2.4 plan 05). Three plan-05 fixtures used `send` + `wait: {idle}` as a real turn; the idle wait passed in 1.5 s and every check after it measured a turn that never happened. A real turn is `send_generate` (`expectReply: true` when silence would make the check vacuous). `send` is right only for a deliberate compact line before a `/trigger`.
- **In a group, one player send is N loud generations, not one** (2026-09-25): the director may draft two members, and each is its own generation (own evidence slot, own scan). A check that counts generations drafts exactly one member per generation with `/trigger await=true "<name>"` inside an eval (foreign-filter read "hidden after ONE send" correctly, because the send was two generations). A member-specific lore effect needs the same: sun-ruins `CP1 - Mission` is filtered to DM Narrator (`characterFilter`, world-info.js:4816) and never fires on anyone else's turn.
- **Switching chats while a save is pending can post one chat's metadata under another chat's name, and ST's integrity popup then wedges the page** (2026-09-25, T13 spike run 1): a save carrying the sandbox group chat's integrity slug hit the Ponticius solo chat during `/go`; the server refused it ("Chat integrity check failed"), the popup held `isChatSaving` true, and after OK the reload hung at "Initializing…" until the lane's Chrome was killed (`taskkill /t` on the `--remote-debugging-port=<cdp>` process, then `st-session start`). Wait for `schedulerIdle` before every `solo_chat` and out `isChatSaving` (+ ~2 s) before any in-page chat switch. `openGroupChat` from a solo chat also needs `openGroupById` first.
