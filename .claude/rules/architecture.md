## Invariants

- `STAPI.ts` + `stHost/*` are the only files importing ST host modules, via dynamic `import(/* webpackIgnore: true */ …)`.
- `src/engine/**` and `extraction/scope*` never import STAPI. `EngineHost` is the clock seam (`{ now }`), not an effects seam: host effects live in `runtime/effectsApplier.ts` and `runtime/coordinators/*`, which tests fake by injecting deps.
- Three lifetimes, three homes (spec addendum v2.1 §Configuration homes): install-wide settings in `extensionSettings["story-orchestrator"].settings`; per-chat engine state, rings and the overrides `{ui.authorView, pacing.shapeOverride, talk.enabled}` in `chat_metadata`; authored content in the story record. `extras` still exposes a full settings view in memory (`applyGlobalSettings`), but `stripGlobalSettings` removes the install-wide half before persisting.
- Story identity is the authored `id` (+ `version`), never the content hash: the library is keyed by id, the per-chat blob is keyed by id, and each chat **pins a full copy** of the story it plays (`pinnedStory`), so library edits and deletion never reach a running chat. `contentHash` stays for integrity and drift detection (`contentHashAtLoad`). Re-selecting hydrates; `restartStory()` is the only reset.
- **The stored blob is a detached copy, never the live run** (T7 2026-10-03, live-v5/v5b). `savePersistedRuntime` stores a JSON copy of the record and `loadPersistedRuntime` hands back a JSON copy; `hasPersistedRuntime` answers existence without copying. The record used to hold the engine state and the extras' nested slices by reference, so any in-memory write after a persist (the leave/exit effect restore marking ledger rows, a journal line, a boundary) changed `chat_metadata` too, including a blob that had since read as foreign, and the next ST save wrote it. Test: `runtime/t7ForeignBlobAlias.review.test.ts`.
- **The wizard is create-only, and validation is the guard** (v2.1 plan 06): `src/wizard/provisioning.ts` decides whether a provisioning op may run, folding the environment forward so a step can depend on the previous one; the UI card and `copilotCoordinator.applyProvisioning` both call it, so nothing reaches the install because a prompt asked nicely. Provisioning ops travel in the `ProposalOp` union but `applyOp` deliberately ignores them and `diffProposal` keeps them out of `items` — bulk accept can never reach them. What a created asset leaves in the story is a `setRequirements`/`addRosterMember` op through the ordinary mutation path (`provisioningFollowUpOps`), which is why the requirements panel goes green from evidence. Personas are never provisioned, and never required unless the install has them: `personaRequirementProblem` refuses a `requirements.personas` name missing from `environment.personaNames` in the staged effects stage and the agent's `setRequirements`, the Studio warns `requirement-persona-missing`, and Repair offers removing the requirement (T5-1-4). A group holds only the draft's own cast (`environment.castNames` = roster card names + `requirements.members`, via `castNames.ts`, folded forward by a card created in the same plan); a card from another story is refused with a did-you-mean (T5-1-3).
- **The agentic wizard writes only through its tools, and only the author confirms an asset** (v2.6 plan 11). A tool call is checked by `checkToolCall` (unknown tool/argument refused with did-you-mean, then the ordinary `readOp` grammar); an edit waits for the author in `review` and goes straight to the draft in `auto-draft`; a provisioning call is validated by `validateProvisioningOp` and ALWAYS waits, and `decideStep` can never accept one — it is confirmed only through the install's write path (`applyProvisioning` → `resolveProvisioning`). There is no persona tool and no `grantLorebook` tool. The loop refuses locally (T5-1/T6-3, `agent/rejected.ts`): an op the author rejected (the rejections, with reasons, stay in the prompt), an asset this session already created (listed as ALREADY CREATED), a guide topic already read, a read whose answer has not changed, a `createGroup` that leaves out any of the draft's cast, an invalid checkpoint field (refused with the allowed values, never half applied) and a requirements card that changes nothing; the same refused call `REPEAT_LIMIT` (3) times stops the run with `stopReason`, and Continue is offered after Finished (`continueAgent`). The done check names a created group that lacks a cast member. `tools.test.ts` fails when a `mutations.ts` export has neither a tool nor a stated reason; `safety.review.test.ts` is W5's deterministic half. The transcript rides `wizardSessions[].agent`. **The harness tool bridge changes the transport, not the rule** (v2.6 plan 04, option 2, opencode only): `server-plugin/story-orchestrator-harness/agentBridge.mjs` runs `opencode run --pure` in an owned home with exactly one MCP server, the plugin's own stdio shim (`mcpShim.mjs`), which exposes exactly the page's validated tool schemas and parks each call in a per-user, per-role session (bounded queue, session and call deadlines, tree kill, admin-only, `offer` gate, plugin header + same-origin); the page long-polls `/agent/next`, and every parked call becomes an ordinary reply that `executeReply` runs through `checkToolCall` and `mutations.ts` / `validateProvisioningOp` unchanged — a provisioning call still only waits, and the session closes whenever the author has to decide. `driveAgent` checks the draft's `RunOwnership` (`studio/agentHost.ts`, the draft store's `runEpoch`) after every turn, before the op reaches the draft and before the shim is answered.
- Wizard sessions live install-wide (`extensionSettings["story-orchestrator"].wizardSessions`, cap 8, `runtime/wizardSessions.ts`), keyed by draft id/title, and carry the created-asset ledger that `so-assets.mts` cleans up against.
- One automatic library→chat path, and it is the author's own save (v2.1 plan 05): `applyStoryUpdate(record?)` diffs the **merged** old and new stories against live engine state (`engine/storyDiff.ts`), hot-swaps silently when compatible, and raises a keep/restart/cancel choice when invalidating; keeping prunes exactly the orphaned values (`pruneEngineState`) and re-pins this chat. Other chats are never touched — they take a newer version only through their own "Update to v*N*" or Restart.
- **No chat, no story** (2026-10-02, found live: nine welcome-screen imports each switched ST's global background). With no chat open (`getContext().chatId` empty) nothing activates: `importStoryJson` saves to the library and stops (`Saved “X” vN to the library. Open a chat to play it.`, shown as `#so-no-chat` from `snapshot.noChat`, the import button reads "Save to library"), `selectStory` refuses (`NO_CHAT_STATUS`), `restartStory` and `applyStoryUpdate` do nothing, and `EffectsApplier` refuses `applyCheckpoint` and every ledgered write (`NO_OPEN_CHAT`). Restore on leaving a chat still runs. Tests: `runtime/noChatOpen.review.test.ts`, `effectsApplier.test.ts`, `storyUpdate.test.ts`.
- **A spike is decided by its predeclared floor, and a floor that is unreachable is still not retuned** (v2.3 plan 10). `runtime/repair.ts`-style floors are declared before the run (`LORE_RANKING_FLOORS`), and the lore-ranking rebuild is NOT built because the two arms were measured live and the proposed Score arm ordered worse (nDCG@4 0.886 rounded, 0.920 raw, vs 0.927). Its tie rate of 1.00 came from rounding (raw 0.04), so the refusal rests on nDCG alone (corrected in v2.4 plan 01; raw recomputed from the golden, `loreScore.ts:45` rounds). The measurement is kept as a golden that replays in jest (`loreRelevance.test.ts`), so a later question-shape change is scored against the same answers instead of against a fresh run. Since v2.6 W25 (English only) the golden holds the 17 English rows: Noul nDCG@4 0.921 vs Score 0.875, same verdict.
- **The judge never blocks and never writes** (v2.2 rule 1). It is a read model behind `server-plugin/story-orchestrator-judge`, the only place a provider key is read (v2.6 plan 12: per provider; with ST user accounts on, only that user's own ST secrets, W12; otherwise ST secrets, env, `~/.typesafe/api-key/.env`). Since v2.6 plan 12 A a `DecisionProvider` seam sits under `askJudge` (`src/judge/providers.ts`): `judge.provider[use]` defaults to `typesafe`; a use routed to a provider with no calibration row for provider × model × use is refused (fallback `uncalibrated`, nothing sent); a non-default provider's row must also be passed and on the current fixture revision (`JUDGE_FIXTURE_REVISION`), and an answer from a served model other than the calibrated one is discarded (`model-mismatch`) and refuses the next call before sending (AS-4); the privacy notice does not gate egress (CR-J3, user decision 2026-10-01): a configured key is consent, and the notice says so and how to switch the judge off; the local `llama-logprob` provider reads its llama-server URL from `SO_JUDGE_LLAMA_URL` on the server, never from the page. **TypeSafe's documented limits (user, 2026-10-02) bound every call, and TypeSafe may change them without notice**: a request whose estimate (3.488 chars/token, the lowest measured ratio) passes 32,000 tokens for state + the longest question or 64,000 for the whole request, each minus 10%, is never sent and never truncated: `askJudge` answers fallback `too-large` (ringed, not metered), and the plugin refuses the same request 413 (`pluginFallback` reads it as `too-large`). The plugin's rate ceiling is the account (1,200/min, 250,000 input tokens/s, `SO_JUDGE_ACCOUNT_RATE_PER_MIN` / `SO_JUDGE_ACCOUNT_TOKENS_PER_SEC`), each ST user (a lane) 2 x account / 5 by default (480/min, 100,000 tokens/s; `SO_JUDGE_RATE_PER_MIN` overrides), and both adapt: a real TypeSafe 429 halves the effective rate (floor 10%), a `Retry-After` holds every call for that long (capped 5 min, never retried inside the plugin when longer than the 600 ms retry), and the rate recovers linearly over 120 s after a 30 s hold (`/status` `adaptive`). Every usage is its own install-wide switch (`judge.uses.*`), **on by default since v2.6 (user decision 2026-09-30, `docs/plans/v2.6/00-overview.md` rule 5; was off by default since v2.2)**; with no key every use takes its fallback; each consumer keeps today's path and takes it on disabled/unavailable/timeout/error/ineligible. Calls land in the per-chat `extras.judge.calls` ring (cap 300), never `extras.journal`; the session journal derives `judge` events from it. `src/judge/` is pure and the engine never imports it (`architecture.test.ts`). The judge director runs only when every candidate has an authored `roster[].role` (names-only measured 21/26, below the LLM director).
- **Stagecraft proposes, it never writes** (v2.1 plan 07, spec addendum §Stagecraft): a curator returns typed ops, the runtime applies accepted ones **at a boundary** through the effects path, and its whole write scope is the story's authored `stagecraft.lorebooks` — nothing is inferred from `requirements` or from `world_info` effects. That scope excludes every checkpoint-gated entry: the curator is never shown one, and `isCuratorWritable(story, lorebook, comment)` refuses one at the write edge. Otherwise a curator write would fight the path replay (2026-09-19). The allowlist is re-checked at the write edge (`isCuratorWritable`), so an edited or replayed proposal cannot widen it.
