## What it is
Fork of ReMemory (`rmr_` prefixes throughout; see `rememory-more-memory-management.md`, not repeated here). Chat is cut into **chapters** (manual stop-button, LLM "arc analyzer", or auto at N+X messages); each chapter gets one plaintext summary, stored as `{summary,startMsgId,endMsgId}` in `chat_metadata.timeline` and exposed as `{{timeline}}` JSON. The novel part: **summary → source drill-down** — a question about chapter k goes to a second LLM together with chapter k's *full raw text*, so recall is "summary for routing, raw transcript for truth". Three front ends for that: (1) main-model function tools, (2) a static "timeline fill" pre-pass that emits a JSON list of questions, (3) an "agentic" tool loop that runs **inside the live chat** under a swapped profile. Plus an autonomous lorebook editor (tools with create/update/delete).

## How it works
- **Boot/events**: `APP_READY` → version gate, settings, macros, slash, injection, send-form buttons (`source/index.js:212-227`). `USER/CHARACTER_MESSAGE_RENDERED` → message buttons + `checkAutoSummarize` (`:229-234`). `CHAT_CHANGED` → session abort/recovery, reload timeline, re-render (`:235-296`; comment at `:258`: "CHAT_CHANGED also fires during save/reload of the same chat"). `MESSAGE_SENT` clears last fill results (`:298`). No `MESSAGE_DELETED/EDITED/SWIPED` handling anywhere.
- **Chapter creation**: range = after last message with `extra.rmr_chapter` → target (`source/src/memories.js:1989-1999`), regex-processed window, token-chunked map→reduce (`:1903-1987`, same algorithm as ReMemory), prompt carries prior-chapter `{{timeline}}` "for reference only" (`src/settings.js` default `memory_prompt_template`, `:43-64`). Result appended to `timelineData` + `chat[mes_id].extra.rmr_chapter = true` + `saveChat` (`memories.js:2002-2031`). **`hide_chapter` defaults true** (`settings.js:121`): summarized messages get `is_system=true` directly (`memories.js:1970-1981`).
- **Resummarize** feeds only chapters *before* the target as `{{timeline}}` so the model can't leak later events (`memories.js:1022-1040`).
- **Auto-summarize**: after each character render, if `msgs since last chapter ≥ N+X` (defaults 50/10) the model gets messages `[lastEnd+1, current−X]` as JSON and must answer `{"chapterEnd": int}`; code rejects an out-of-range id (`memories.js:2787-2873`, parse `:2944-2958`). Buffer X keeps the freshest messages out of any summary.
- **Drill-down query**: `queryChapter(n, q)` = timeline JSON + full chapter text (incl. hidden `is_system` messages, deliberately, `:908-944`) + chapter summary + question → query profile (`:1591-1731`). Default system prompt tells the answerer the reader "has already read the chapter_summary" → answer only new info (`settings.js:79-91`). Range variant `queryChapters` with a max-chapters cap (default 3, `settings.js:113`).
- **Static timeline fill** (`memories.js:1346-1587`): one call with `{{chapterHistory}}` (visible chat as JSON) + `{{timeline}}` → JSON array `[{query, chapters|startChapter/endChapter}]` (tolerant extraction `:1186`, validation `:1237-1344`); each item executed via `queryChapter(s)`; results persisted in `chat_metadata.timelineFillResults` and injected. Triggered by UI buttons "Retrieve and Send" = `/send {{input}} | /setinput | /timeline-fill await=true | /trigger` (`index.js:132`) — i.e. **the reply waits** on N LLM calls.
- **Injection**: one `setExtensionPrompt(key, prompt, IN_CHAT, depth, false, role, filter)` with a **filter predicate** that returns false during its own internal/agentic/lore sessions (`memories.js:616-706`). Template macros are pre-expanded by string replace, then `substituteParams`.
- **Macros** via `MacrosParser.registerMacro` returning arrays/objects (engine stringifies): `timeline`, `chapter`, `chapterSummary`, `chapterHistory`, `timelineResponses`, `currentChat`, `lastMessageId`, `firstIncludedMessageId` (`memories.js:494-608`).
- **Tools**: `ToolManager.registerFunctionTool({name, parameters(JSON schema), action, shouldRegister, stealth, formatMessage})` for `query_timeline_chapter(s)` (`src/commands.js:180-265`); agentic adds `list_lorebook_entries`, `roll_dice`, and a **stealth** `end_information_retrieval` that ends the loop (`src/agentic-timeline-fill.js:338-533`).
- **Agentic session** (`agentic-timeline-fill.js:558-686`, cleanup `:910-1017`): write-ahead session record in `chat_metadata.agentic_timeline_fill_session` (`:111-138`) → `/hide` every visible message (`:644`) → swap the **global** profile via `/profile` and wait on `CHATCOMPLETION_MODEL_CHANGED|ONLINE_STATUS_CHANGED` (`:24-100`, `:655`) → `/send` a kickoff user message → `/trigger` in the real chat; `GENERATION_ENDED` without the end tool → swipe/retry up to 5 (`:702-850`). Cleanup: `chat.splice(startIndex)` (`:939`), `/unhide a-b` by range (`:948`), `saveChatConditional` + `reloadCurrentChat`, profile restored. Recovery on next `CHAT_CHANGED` replays the same splice/unhide from the saved record (`:143-228`). Lore management is the same shape with `edit_entry` create/update/delete through `createWorldInfoEntry`/`deleteWorldInfoEntry`/`saveWorldInfo` on the character's book (`src/lore-management.js:326-431`, splice `:994`).
- **LLM calls**: all side calls `ConnectionManagerRequestService.sendRequest(profile, [system,user], maxTokens, {includePreset, includeInstruct, stream:false}, override)` (`memories.js:1104`). `maxTokens` read from the profile's preset (`openai_max_tokens` / `genamt`, `:304-434`); override adds `reasoning_effort` from the preset (`:29-137`), `include_reasoning` for z.ai (`:138-190`), o1/o3/o4/gpt-5 `max_completion_tokens`+`temperature:1` (`:442-474`). Reasoning stripped with the **profile's** `reasoning-template` (`:1142-1172`) in most paths, but with the global template via `parseReasoningFromString` in the summary path (`:1115-1117`). Global min-interval rate limit (`:233-236`, `:1013-1018`).
- **Cleanup commands**: `/remove-reasoning a-b` deletes `extra.reasoning*` + reload (`src/commands.js:49-118`); `/remove-tool-calls` splices tool-invocation messages and the assistant message before each (`:120-172`). The author recommends both as QRs **after every user message** (post.md follow-up 20:47).
- **Backup**: `createChatBackup` = `context.saveChat()`, relying on ST's server-side backup (`src/backup.js:18-41`); that backup is throttled per chat (`src/endpoints/chats.js:29`, `:96`, 10 s leading+trailing).
- **Persistence**: `chat_metadata.{timeline, timelineFillResults, *_session}`; chapter markers in `message.extra.rmr_chapter`; settings/presets install-wide.
- **Mutations**: none. Chapter ranges are raw message indices, so any delete before a chapter end shifts every later range silently; swipes/edits never mark a summary stale; `removeChapterFromTimeline` unhides by range (`memories.js:846-887`).

## Overlap with Story Orchestrator
- **We do better**: automatic typed extraction with provenance + rollback (`src/extraction/sharedRead.ts:87`, `src/memory/derived.ts:56`, `src/runtime/rollback.ts:35`); side calls never touch the user's active profile (`src/services/stHost/connectionProfiles.ts:43`); reply path never waits (invariant 5) — their Retrieve-and-Send blocks the send on N calls; stagecraft proposes/never writes vs their autonomous create/delete lore tool; every async writer owns a RunToken (`src/runtime/runToken.ts:138`) — their `isInternalGeneration`/`commandArgs` module globals and chat-index session records are exactly the unowned-writer class.
- **They do, we don't**: go back to the **raw source** of an old summary to answer a specific question. Our `scene_history` rows already record their `range` (`src/runtime/coordinators/memoryCoordinator.ts:128`) and we can re-read a source window — but only for a conflict (`src/runtime/memoryQueue.ts:177` `rereadConflictWindow`). No retrieval/recall pass exists (grep `recall|drill|lookback`: only `recallCount` scoring, `src/memory/score.ts:8`).
- **They do, we do differently**: profile-aware request shaping (we send fixed `maxTokens ?? 512`, `temperature 0.1`, `top_p 0.9`, `src/extraction/client.ts:14-18`); LLM-chosen chapter endpoint vs our heuristic scene break (`src/memory/sceneDetect.ts:34`) + fixed ~12-message short-term compaction.
- **Coexistence**: they mutate the chat out-of-band (splice + reload, `is_system` writes, side-sessions of real turns). Our TurnBridge only learns about deletions from `MESSAGE_DELETED` (`src/runtime/turnBridge.ts:56`), and every `CHAT_CHANGED` is a full `loadStory` (`src/runtime/turnBridge.ts:149-152` → `src/runtime/runtimeManager.ts:524-549`).

**1. Same-chat reload is not a chat change.** Theirs: `reloadCurrentChat` after every `/remove-reasoning` (`src/commands.js:102`), `/remove-tool-calls` (`:170`), agentic/lore cleanup (`src/agentic-timeline-fill.js:939-956`, `src/lore-management.js:994`); ST's `reloadCurrentChatUnsafe` → `getChat`/`getGroupChat` → `CHAT_CHANGED` for the *same* id (`public/script.js:1710-1726`, `:7700`; `group-chats.js:318`); they note it themselves (`index.js:258`). None of those splices emits `MESSAGE_DELETED`. Ours: `onChatChanged` → `loadSelectedFromChat` → `loadStory` → `invalidateRuns()` (bumps ownership, every in-flight read lapses) and `engine.hydrate` builds a **new `ApplyQueue`** (`src/engine/engine.ts:145`) — so a user running their recommended after-every-message QR loses the pending accepted deltas and in-flight reads every turn (reconciliation eventually recovers, at extra LLM cost and a one-boundary lag). Worse direction: after a splice that removed messages we had consumed, hydrate restores `lastMessageId` beyond `chat.length`; `engine.hydrate`'s only repair is the active checkpoint (`src/engine/engine.ts:140-143`) and `loadStory` never compares against the chat (`runtimeManager.ts:524-549`, grep `truncat|chatLength` in runtime/engine: none) → provenance message ids now point at different messages. Proposal: on `CHAT_CHANGED` with the same `chatId` and a loaded story, (a) if `engine.lastMessageId ≥ chat.length` or a stored fingerprint of the last consumed message no longer matches → `runRollback(firstDivergent)` (E1-style notice, same path as a delete); (b) else keep queue + runs and just refresh injections/snapshot. Fingerprint = short hash of `mes` recorded in the boundary snapshot (boundary snapshots already carry `{lastMessageId, chatLength}`). Parse ids with `hostMessageId` (gotcha V4). Invariant 11 is the reason, 10 unaffected (same world → token still valid). Pure predicate testable in jest.

**2. Scene-source recall.** Theirs: `queryChapter` = question + chapter summary + *entire raw chapter* (`memories.js:1591-1731`), fed by a planner that turns "current scene + timeline" into `[{query, chapters}]` (`:1346-1587`, prompt `settings.js:93-109`: "query only what the summaries don't already answer; max 3 chapters per query"). Ours: scene summaries keep `range` (`memoryCoordinator.ts:128`); raw re-read exists only for conflicts (`memoryQueue.ts:177`). Shape that respects our invariants: an **off-path** P4 pass after a scene break or when the scene read names a returning entity/location — planner picks ≤K `scene_history` rows by summary, re-reads their `range` via `getChatWindow`, asks the targeted questions, stores the answer as a derived artifact with `inputs`=row ids and `range`s (rollback drops it, `src/memory/derived.ts:56`), injected as a one-turn block like `continuityNote` (`src/constants/injectionRegistry.ts:12`); never on the reply path (invariant 5: if not ready, next turn goes without). Quarantined rows never selected (15). Privacy: raw windows are shared transcript, same exposure as extraction; still must not feed private epistemic rows into a shared block. Needs whole-scene ranges first (ReMemory report idea 1) and the chunker (seed D). Worth a Phase-A measurement (does recall improve continuity-check scores?) before building — it's the judge-floor rule by analogy.

**3. Foreign side-session journey.** Nothing in `scripts/debug` simulates another extension writing real turns and removing them. Their agentic session is the realistic case: `/send` + `/trigger` turns in the live chat (`agentic-timeline-fill.js:655-686`) — our TurnBridge commits boundaries on those replies and extraction reads the agent's retrieval chatter as story — then `chat.splice` + save + `reloadCurrentChat` with no delete event. Scenario: seed a story at cp1, append 3 user/assistant turns by writing `chat` + `saveChatConditional`, let a boundary commit, splice them out, call `reloadCurrentChat`, assert blackboard/memory/boundary log equal to the pre-append snapshot. Also exercise `is_system` hiding (their `hide_chapter` default true, `settings.js:121`) against `runMemorizeBacklog`, which skips hidden messages (`src/extraction/chatWindow.ts:8`) — a chat curated by Timeline-Memory backfills nothing for its summarized chapters. Gate for idea 1; runs without a backend (mock only the read).

**4. Profile-aware request shaping.** Theirs: max tokens from the profile's preset (`memories.js:304-434`), `reasoning_effort` from the preset (`:29-137`), profile's own `reasoning-template` for stripping (`:1142-1172`). Ours: `callExtractionModel` sends `maxTokens ?? 512`, `temperature 0.1`, `top_p 0.9` (`src/extraction/client.ts:14-18`). On a Chat Completion profile ST builds the payload with `createGenerationParameters` and then spreads our override **last** (`public/scripts/custom-request.js:601-604`), so our sampler wins over ST's per-model rules (gpt-5 / o-series handling, `public/scripts/openai.js:3052-3098`) — likely a rejected request on such models (unverified live; we run textgen). And a reasoning model at 512 tokens burns the budget thinking → our stripper yields `""` for an unterminated block (gotcha "Inline reasoning is stripped…"). Proposal in `stHost/connectionProfiles.ts`: read the profile's preset max-tokens as a floor for reasoning-capable profiles, omit sampler overrides on CC sources that constrain them, and add the profile's selected reasoning template (`connection-manager/index.js:48` field, `reasoning.js:32` `reasoning_templates`) as one more pattern to `stripReasoningBlocks` (keep the template-independent forms — their global-template path `memories.js:1117` is the bug our gotcha warns about). No invariant touched.

**5. Model-chosen breakpoint, code-bounded.** Theirs: `{chapterEnd:int}` constrained to `[lastEnd+1, current−X]`, validated in code (`memories.js:2831-2873`, `:2944-2958`). Ours: short-term compaction is a fixed ~12-message rolling replace (`extractionCoordinator.ts:314`), scene breaks from a location/cast heuristic (`src/memory/sceneDetect.ts:34`) + opt-in judge `sceneTrigger`. The pattern (model proposes an index, code owns the bounds, buffer X keeps the still-mutable tail out) fits invariants 4/5 as a *read* feeding the scene-break pass, never a state write. Already overlaps the seed "scene-break confirmation" spike — fold it there; do not build separately.

**6. `setExtensionPrompt` filter.** Theirs passes a 7th-arg predicate (`memories.js:694-702`); ST stores it and **awaits** it at every prompt assembly, skipping the block when false (`public/script.js:8926-8934`, `:3241-3242`, `:3268-3270`, `:3303-3304`). Ours: `SetExtensionPromptFn` omits it (`src/services/stHost/extensionPrompts.ts:6`); withholding is done by clearing/restoring blocks around generation events (gotchas: group resting block, impersonate/quiet). A filter removes the set/clear race for foreign `quiet` generations (e.g. their side calls through `/gen`), but it takes no arguments, so it still needs a flag we set on `GENERATION_STARTED`; and `readInjectedPromptBlocks`/next-turn preview (`src/runtime/nextTurn.ts:76`) would have to evaluate it to stay truthful. Small, optional; record the host fact, build only if a withholding race is observed.

**7–8. Anti-patterns** — see below. Both conflict with invariants 5/6/9 and baseline §4 ("no function-calling").

## Patterns to copy / anti-patterns to avoid
Copy:
- **Summary routes, source answers** (`memories.js:1591-1731`): summaries are an index, not the memory; the raw span is re-read when precision matters.
- "Reader already has the summary — answer only what's new" in the answerer prompt (`settings.js:79-91`): cuts duplicate tokens in any drill-down/re-read prompt we write (conflict re-read included).
- **No future leakage on regeneration**: a regenerated derived artifact sees only inputs before its range (`memories.js:1022-1040`). Our `rollback ≡ replay` property covers rollback, not "regenerate scene summary / canon later"; state it as a rule if we add regenerate actions.
- Code-validated model choice of an index/range (`memories.js:2849-2853`, `:1237-1344`), with tolerant JSON extraction but strict shape validation.
- Write-ahead session record + recovery on next load (`agentic-timeline-fill.js:111-228`) — same idea as our effect ledger (`src/runtime/effectLedger.ts:72`); nothing new to take.

Avoid (seen in their code):
- **Running an agent loop as real turns in the user's chat** (`agentic-timeline-fill.js:644-686`): hides the whole chat, swaps the global profile, posts messages, then `chat.splice`s them away with no event (`:939`) — every other extension (us included) processes turns that never "happened".
- **Restore by range, not by recorded set**: `/unhide a-b` (`:948`, `memories.js:863-876`) unhides messages the user had hidden; our compare-and-set restore (`effectLedger.ts:112`) is the right shape.
- **Reply waits on retrieval** (`index.js:132`, and a fixed `setTimeout(5000)` before swiping, `:182`) — violates our invariant 5 and the "fixed timeout is a hardware assumption" gotcha.
- **Index-keyed ranges with no mutation handling** (`{startMsgId,endMsgId}`, `memories.js:753-763`): one early delete misaligns every chapter.
- **Main-model tools that make a second LLM call** (`commands.js:207-211`): the reply stalls on the side model; tool results persist as `is_system` chat messages (ST `tool-calling.js:899-920`), visible to the player (`stealth:false`) — spoiler surface for us, and why they need `/remove-tool-calls`.
- **Autonomous create/update/delete on a lorebook** (`lore-management.js:326-431`) with only a `saveChat` "backup" that ST throttles (`src/endpoints/chats.js:96`) and that does not cover WI files at all — a WI edit has no undo. Our curator: propose, boundary-apply, allowlist, revert.
- Two reasoning parsers in one extension, one using the global template (`memories.js:1117` vs `:1142`).
- Module-global flags as concurrency control (`isInternalGeneration`, `isAutoSummarizing`, `memories.js:199`, `:202`): auto-summarize started in chat A writes into whatever chat is open when it returns (`summarizeChapter` reads `getContext().chat` after the await, `:2002-2031`).

## ST host facts learned
- `setExtensionPrompt(key, value, position, depth, scan=false, role=SYSTEM, filter=null)`; `filter` is awaited per prompt build and skips the block when falsy (`public/script.js:8926-8934`, `:3241`, `:3268`, `:3303`). Their use `memories.js:694-702`. Not in our vendored type (`extensionPrompts.ts:6`).
- `reloadCurrentChat` (mutexed, `script.js:1703`) → `getChat` emits `CHAT_CHANGED` with the **same** chat id (`script.js:7700`; groups `group-chats.js:318`). Their note `index.js:258`. **Relevant to our gotchas**: every same-chat reload is a full hydrate for us (idea 1).
- Out-of-band `chat.splice` + `saveChatConditional` + `reloadCurrentChat` removes messages with **no `MESSAGE_DELETED`** (their `commands.js:166-170`, `agentic-timeline-fill.js:939-956`). Our rollback-on-delete rule has a blind spot here.
- `ToolManager.registerFunctionTool({name, displayName, description, parameters, action, formatMessage, shouldRegister, stealth})` / `unregisterFunctionTool(name)` via `getContext().ToolManager` (`commands.js:180-265`; ST `tool-calling.js:175`). `stealth`: result not shown, no follow-up generation (`tool-calling.js:43`). Tool invocations are saved as a separate `is_system:true`, `extra.isSmallSys`, `extra.tool_invocations` message and emit `TOOL_CALLS_PERFORMED`/`TOOL_CALLS_RENDERED`, not `CHARACTER_MESSAGE_RENDERED` (`tool-calling.js:899-920`) — our `chatWindow.ts:8` already skips them. Whether the assistant turn that *issued* the call commits a boundary for us: unverified.
- Connection Manager profiles carry a `'reasoning-template'` field (`connection-manager/index.js:48`, `:67`); templates in `reasoning_templates` (`reasoning.js:32`). `parseReasoningFromString` defaults to the **global** `power_user.reasoning` (`reasoning.js:1461-1462`) — consistent with our gotcha, no contradiction.
- CC side requests: when a preset is included ST builds the payload via `createGenerationParameters(settings, model, 'quiet', messages)` and spreads `overridePayload` over it (`custom-request.js:601-604`), so an extension's sampler override defeats ST's per-model parameter rules (`openai.js:3052-3098`). Their explicit o-series override (`memories.js:442-474`) is therefore redundant on current ST, and ours (`client.ts:15-18`) may be harmful there.
- Profile switch completion can be awaited on `CHATCOMPLETION_MODEL_CHANGED` or `ONLINE_STATUS_CHANGED` (`agentic-timeline-fill.js:24-60`); our gotchas already note `/profile` now awaits the switch.
- Chat backups are per-chat throttled, 10 s default, leading+trailing (`src/endpoints/chats.js:29`, `:88-96`): a "backup by saving" right after another save may coalesce.
- `MacrosParser.registerMacro` accepts functions returning arrays/objects (engine stringifies) and async functions (`memories.js:495`, `:515`, `:546`); async macros under the new macro engine: unverified.
- No contradiction with our gotchas found; the same-chat `CHAT_CHANGED` and splice-without-event facts extend them.

## Verdict
Relevance **medium**. As a memory system it is weaker than ours (untyped, index-fragile, no rollback), and its "agentic" half runs agent turns inside the user's chat — the thing our architecture exists to avoid. Two things are worth it: the **coexistence finding** (idea 1: same-chat `CHAT_CHANGED` currently costs us the pending queue and in-flight reads every turn for anyone using this extension's recommended QR, and a splice-without-event leaves our state ahead of the chat) — cheap, S/M, fix first; and the **summary-routes/source-answers recall** idea (2) as a measured v2.4 spike on top of whole-scene ranges.
