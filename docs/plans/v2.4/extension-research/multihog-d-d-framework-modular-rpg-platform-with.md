## What it is
Heavy "RPG platform" extension: a second-pass **State Tracker** LLM keeps a text memo (HP/inventory/party/time/combat) and re-injects it every turn; **Hybrid RNG** (pre-seeded dice queue in the prompt + `RollTheDice` function tool that makes the narrator declare a DC before seeing the roll); a **Lorebook Agent** that creates/activates/updates/consolidates WI entries in its own per-chat-prefixed books; **World Progression** (in-world-time-triggered off-screen macro reports) and **Map Evolution** (persistent JSON maps stored in WI entry metadata, evolved off-screen). Plus portraits, CYOA buttons, character creator, "Adventure Companion" side chat, themes, "game cartridges" (config bundles). Single-player D&D-flavoured; not a story graph.

## How it works
- **Injection**: one manifest `generate_interceptor: "rpgTrackerInterceptor"` (manifest.json; body `narrative-hooks.js:1210`). It mutates the prompt copy: finds the last user message and prepends `[PLAYER_CHARACTER]`, `[NPC_RELATIONS]`, pacing/CYOA tags, `[RNG_QUEUE v7.0]` block, `### STATE MEMO`, quests (`narrative-hooks.js:1400-1500`), strips stale injections from older turns (`prepareUserMessagesForContextInject`). `setExtensionPrompt('rpg_tracker_lore', '')` is explicitly cleared — interceptor is the sole path (`index.js:2406-2410`). Also rewrites prompt arrays in place on `CHAT_COMPLETION_PROMPT_READY` (`eventData.chat`) and `GENERATE_BEFORE_COMBINE_PROMPTS` (`eventData.finalMesSend`) to strip superseded CYOA choices (`index.js:7818-7828`).
- **Events** (`index.js:7830-7880`, `10102-10126`): `GENERATION_STARTED/ENDED/STOPPED`, `MESSAGE_SENT/RECEIVED/EDITED/SWIPED/UPDATED`, `CHAT_CHANGED/LOADED/RENAMED`, `MORE_MESSAGES_LOADED`, `STREAM_TOKEN_RECEIVED`, `SETTINGS_LOADED`/`APP_READY` once. Post-reply pipeline on `GENERATION_ENDED` (skipped for quiet/impersonate or non-`{{char}}` speaker): keyword scan → tracker pass (run-every N) → combat profile sync → map updater → WP time check → map evolution → LA tick (`docs/multihogDnDdoc.md:169-186`).
- **LLM calls**: `llm-client.js` routes per subsystem to Main API (`generateRaw`/`generateRawData`), a Connection Manager profile (`ConnectionManagerRequestService.sendRequest` with `signal`, `includePreset`, override payload, `llm-client.js:155-185`), or raw Ollama/OpenAI endpoints via `/proxy/`. Profile's preset is temporarily swapped in-memory and restored in `finally` (`llm-client.js:165-184`).
- **Function tools**: `ctx.registerFunctionTool` for `RollTheDice`/`RollTheDiceD100` (schema requires `who, for, formula, dc` — DC committed before result) and `CreateAreaMap`; tools unregistered during combat so the queue is the only mechanic (`narrative-hooks.js:554-722`). `formatMessage: () => ''` suppresses ST's tool-call message.
- **RNG**: `crypto.getRandomValues` rejection-sampled dice, 12-line queue per turn, `scope=this_response` (`narrative-hooks.js:279-330`). Not seeded, not replayable.
- **Persistence**: per-chat state lives in **`extension_settings.chatStates[chatId]`** (install-wide settings.json), projected into one live settings object on chat switch (`src/state/chat-persistence.js:1-40`, `docs/chat-ownership.md:3-6`). Zero `chat_metadata`/`saveMetadata` use. Rename needs migration (`src/features/chat/chat-rename-migrate.js`); a localStorage WAL guards small global prefs against reload-cancelled `/api/settings/save` (`src/state/critical-settings-backup.js:1-8`).
- **Swipe/edit handling**: per-swipe snapshots on the message itself — `msg.extra.rpgMemoRollback[swipeId]` (pre-pass memo) + `rpgMemoResult[swipeId]` (post-pass memo) (`index.js:3209-3218`); on swipe, `applyMemoSwipeRollback` restores the target swipe's memo **without re-running the LLM** (`narrative-hooks.js:1850-1893`). Relationship deltas undo/re-apply per swipe, aborting a rollback if the user hand-edited the value since (`expectedValue`, `narrative-hooks.js:1901-1980`). LA/map passes stamp `extra.rpg*RanForSwipe` + `runId`; a pass based on an abandoned swipe is rolled back only if still newest in history, and the run-every tick is re-primed so the segment is not skipped (`narrative-hooks.js:1995-2050`).
- **Chat ownership**: `createChatCommitGuard` = chat id + global switch generation (A→B→A safe) + AbortSignal + parent guard; `chatCommitResult(guard, await x)` checks synchronously in the caller's continuation; catch paths re-check before fallback writes (`src/state/pass-affinity.js:14-66`, rationale `docs/chat-ownership.md`).
- **Lorebook Agent** (`router.js:1475 runRouterPass`): Basic (tag markers `[[NPC: …]]`) or Advanced ReAct loop (`grep_lore`, `inspect_book`, `read_entry`, `commit`, max turns `router.js:1678`). "Keyring": inactive entries shown as Book::UID + label + keys only, declared exhaustive (`router.js:1308`). Scope = books named `<prefix>_<Book>` only. Automatic passes may only touch low-risk CORE fields; identity fields need a manual Direct Prompt — enforced in code (`router.js:3529-3533`), and `[CORE]`/`[MAP]` blocks are restored verbatim over any rewrite (`protectCoreBlock`, `router.js:4819-4848`). Writes go straight to `/api/worldinfo/edit` + `worldInfoCache.set/delete` (`router.js:445-525`).
- **World Progression / Map Evolution**: JS parses `[TIME]` from the memo and decides *whether* (every X in-world hours); the LLM only writes *what* (`docs/multihogDnDdoc.md:615-620`; prompt `world-progression-prompt.js`). Reports are directional prose; Map Evolution later consumes each report and marks it `materialized | already_realized_by_play | considered` (`map-evolution-lib.js:61-76`, `map-evolution.js:322-330`). Location rotation: oldest-unadvanced first.
- **Tests**: vitest + CI (`.github/workflows/test.yml`). `tests/chat-operation-races.test.js` AST-extracts production functions into a `vm` context and suspends host I/O at named phases (`load/llm/save/names/registry/known`), switches chats, releases, asserts no write.

## Overlap with Story Orchestrator
- State tracker memo vs our typed blackboard + ledger + memory tiers: ours is typed, scoped, evidence-checked and boundary-applied (`src/extraction/sharedRead.ts:87`, `src/engine/applyQueue.ts:30`); theirs is a free-text memo rewritten by an LLM. We are stronger on determinism; they are stronger on "just works with no authoring".
- Lorebook Agent vs our WI curator: they create/delete/consolidate entries autonomously; our curator is propose-only, edit-only within `stagecraft.lorebooks` (`src/stagecraft/scope.ts:24`). Their prefix-container scope = our allowlist idea; their manual-vs-auto field gating is finer than our global `acceptMode` (`src/stagecraft/types.ts:9`).
- Chat ownership: their guard ≈ our `RunToken` (`src/runtime/runToken.ts:18`), which additionally carries story/version/window revision; A→B→A handled by our `sessionEpoch`. Their doc's rules (check in catch, check per queued job, UI guard captured at click) match our census rules (`test/findings/ownership-sites.json`). We are ahead (census-enforced); they are ahead on **cancelling** in-flight LLM calls (signal passed to `sendRequest`; ours only on the judge path, `src/runtime/judge.ts:130`).
- Swipes: we roll back on `MESSAGE_SWIPED` (`src/runtime/turnBridge.ts:54`) and re-read; they restore a cached per-swipe result without a model call.
- Persistence: we are clearly better — `chat_metadata`, read-back save evidence, pinned story copy (`src/runtime/persistence.ts:60`, `src/runtime/saveEvidence.ts:44`). Theirs lives in settings.json and needs WALs/heuristics to survive.
- Profile switching: their combat override ≈ our effect ledger (`src/runtime/effectLedger.ts:112`) but keeps the baseline in module memory (lost on reload); we have no profile effect at all.
- Scene/time: they own an in-world clock (`[TIME]` in memo) that drives WP/decay; our scene read has categorical `times` only (`src/runtime/coordinators/sceneCoordinator.ts:62`).

**1. Branch-aware story continuation.** ST's `createBranch` writes `newMetadata = { main_chat, integrity }` only (`SillyTavern-MainBranch/public/scripts/bookmarks.js:201`) — `chat_metadata.story_orchestrator` does not follow, so every branch of a story chat starts storyless. They built "Branch Campaign" for exactly this (`src/features/chat/branch-campaign.js:47-60`: ST branch + state partition copy + lore stack clone). Ours: no `main_chat` handling (`grep -rn main_chat src` → none); only the mirror comment anticipates adoption (`src/runtime/memoryMirror.ts:65`). Proposal: on a chat with no blob and `chat_metadata.main_chat`, offer "Continue the story from the branch point": read the parent chat's blob (new `stHost/` seam over `/api/chats/get`), take the pinned story + engine history, roll back to the boundary covering the branch message (within `ROLLBACK_HORIZON` 200, `src/engine/engine.ts:70`; beyond it → the existing horizon notice/restart), stamp for the new chat. Fits invariants 11/12/13 (pinned copy travels, rollback ≡ replay reused); must be explicit (V5: a foreign blob is never auto-adopted) and needs a new host seam (inv. 2).

**2. Abort memory-LLM calls.** `ConnectionManagerRequestService.sendRequest` takes `signal` (`public/scripts/extensions/shared.js:424`); they pass it (`llm-client.js:170-178`). Our `sendConnectionProfileRequest` passes none (`src/services/stHost/connectionProfiles.ts:43-50`), and `callExtractionModel` has no signal (`src/extraction/client.ts:11`), while `RunOwnership.signal` already exists and is wired only into the judge (`src/runtime/runOwner.ts:76`, `src/runtime/judge.ts:130`). Today a chat switch discards the answer via token but the request keeps the single GPU busy (33 tok/s RunPod — see gotchas). Pure win; token check stays the correctness guard, abort is the resource guard. Inv. 10 unaffected.

**3. Per-swipe extraction memo.** They stamp pre/post state per `swipe_id` on `msg.extra` and restore on swipe-back without a model call (`index.js:3209-3218`, `narrative-hooks.js:1850-1893`). Ours: swipe → rollback → P0 re-read every time (`src/runtime/turnBridge.ts:54`; zero `swipe_id` refs in `src/`). Keep a small ring in extras keyed `messageId + hash(message text)` → the accepted audit; when the chat returns to identical text, re-enqueue the cached deltas at the boundary instead of re-reading. Keyed by text (not swipe index) it is replay-equivalent (inv. 11) and still boundary-applied (inv. 3). Saves a read + removes swipe-back nondeterminism. Their abort-if-user-edited-since (`expectedValue`, `narrative-hooks.js:1923-1926`) is the compare-and-set we already use in `effectLedger`.

**4. Library save evidence.** `saveSettingsDebounced` = 1000 ms debounce (`public/script.js:470`, `constants.js` `relaxed: 1000`) and `saveSettings` only logs on failure; they lost settings to reload-cancelled saves and added a localStorage WAL (`src/state/critical-settings-backup.js:1-8`). Ours: Studio save → `saveStoryRecord` → `saveSettingsDebounced()` (`src/runtime/storyLibrary.ts:110`), and the UI says `Saved "X" vN to the library.`; save evidence observes only chat saves (`src/services/stHost/persistence.ts:8`). Extend the observer to `/api/settings/save` for author saves / wizard sessions, and only then claim "Saved" (or say "saving…"). Inv. 17 applied to the second persistence home.

**5. Seeded chance gates.** Their core anti-sycophancy idea: difficulty is committed before the outcome is visible (tool schema requires `dc`, `narrative-hooks.js:640-648`; CYOA commits DCs a turn early, doc `:267-273`). SO has no failure-by-odds: every outcome is an extractor read (grep `random|seed` in `src/engine` → none). Idea: a `source: code` quality with `roll: {sides, target}` authored in the story (the commitment), drawn at the boundary where a gate needs it from `seed = hash(chatId, storyId, boundary, quality)`, outcome injected so the narrator narrates it. Deterministic seed keeps engine purity (inv. 1) and rollback ≡ replay (inv. 11); must NOT copy their `crypto.getRandomValues` (unreplayable). Value hinges on authors wanting chance branches — a spec question.

**6. Curator write tiers + protected spans.** They gate by pass provenance in code: automatic passes may touch only low-risk fields; identity fields need an explicit manual prompt (`router.js:3529-3533`), and `[CORE]`/`[MAP]` blocks are restored over any rewrite (`protectCoreBlock`, `router.js:4819-4848`). Ours: one install-wide `acceptMode` (`src/stagecraft/types.ts:9`) and entry-level allowlist (`isCuratorWritable`, `src/stagecraft/scope.ts:24`); no per-entry auto tier, no protected spans (grep `protect|locked` in `src/stagecraft` → none). Add authored `stagecraft.auto: [entries]` (auto mode applies only these; everything else stays review) and `<!-- so:lock -->…<!-- /so:lock -->` spans rejected at the write edge. Strengthens inv. 6.

**7. Full-restatement extraction mode (spike).** Their "Full Review Mode" replaces the delta contract with "re-output every module" for Gemma/Qwen/Mistral-class trackers because small models drop state under delta contracts (`docs/multihogDnDdoc.md:423-437`). Ours is a pure delta contract ("If nothing changed, output NO_DELTA", `src/extraction/contract.ts:37-42`) and our live-suite facts tier sits at 0.7273 on Artemis. Spike: model restates the current value of every scoped quality; code diffs against the blackboard; only changed values need in-window evidence (inv. 4 kept). Ship only past a predeclared live-suite floor, like judge uses (inv. 7 spirit).

**8. Keyring curator prompt.** LA shows inactive entries as label + keys only and declares that index exhaustive (`router.js:1308`). Our curator prompt renders every allowlisted entry with 400 chars of content (`src/stagecraft/prompt.ts:11-13`). Keyring form bounds prompt size (open seed D: no request-size bound) with a follow-up read for the entries the model names. Low effort, modest value until allowlists get big.

**9. Pressure → realization ledger.** WP: code decides *when* (in-world interval), LLM writes directional prose; consumers mark each pressure `materialized | already_realized_by_play | considered` so it is neither duplicated nor re-injected forever (`map-evolution-lib.js:61-76`, `world-progression-prompt.js`). For SO this is the shape a future off-screen "world pulse" stagecraft curator should take (proposal into an allowlisted WI entry, boundary-applied), and a realization flag would also stop steering/nudges repeating a pressure play already delivered. Blocked by the curator having no create op (seed B, F5) and by no in-world clock quality; keep as a design note.

**10. Profile effect.** Their combat override switches the main connection profile + preset while a condition holds and restores the baseline (`llm-client.js:345-455`), but the baseline lives in module variables (lost on reload, no compare-and-set). SO has no profile effect (grep `/profile` in `src/` → none) and preset effects are textgen-only (`src/services/stHost/presets.ts:41`). A `/profile` effect through `withLedger` (write-ahead row, compare-and-set restore) would give chat-completion users a per-checkpoint model/preset swap — one answer to seed A. Inv. 16/21: must answer a typed `WriteResult`; `/profile` awaits (gotchas).

## Patterns to copy / anti-patterns to avoid
Copy:
- `chatCommitResult(guard, await x)` — check synchronously in the caller's continuation; an async wrapper that checks leaves a microtask gap (`src/state/pass-affinity.js:46-55`). Worth a line in our census rules.
- "UI controls capture a guard at click; rendered rows/popups keep their originating view's guard" (`docs/chat-ownership.md` §UI lifetimes) — explicit rule we have only implicitly.
- Undo only if the pass is still the newest in history, else leave it and journal (`narrative-hooks.js:2020-2033`); re-prime cadence after undoing an abandoned-swipe pass so that segment is re-read.
- "JS decides whether, the LLM decides what" for every autonomous pass (WP trigger) — same as our boundary/cadence ownership; good phrasing for the stagecraft design doc.
- Phase-named deferred-I/O race tests (`tests/chat-operation-races.test.js:39-60`): one harness, suspend at each named host phase, switch A→B and A→B→A, release, assert no write. Our review tests do this per coordinator; a phase sweep would make coverage enumerable.
Avoid:
- Per-chat state in `extension_settings.chatStates` (settings.json bloat, rename migration, reload loss, "substance score" boot heuristics `src/state/chat-persistence.js:24-40`). Ours in `chat_metadata` is right.
- Static imports of ST internals (`import { createBranch } from '../../../../../../bookmarks.js'`, `branch-campaign.js:1`) — violates our inv. 2.
- Canonical state hidden inside chat text (`<div hidden>` maps captured out of messages, `narrative-hooks.js:1238-1245`) and prompt-copy mutation as the only injection path — breaks our next-turn preview/`readInjectedPromptBlocks` model.
- Unseeded RNG for anything gate-relevant (not replayable).
- Module-memory baselines for host overrides (combat profile).
- Trusting `/api/worldinfo/get` for existence (see host facts).

## ST host facts learned
- `ConnectionManagerRequestService.sendRequest(profileId, messages, maxTokens, {stream, signal, extractData, includePreset, includeInstruct}, override)` — `signal` is honored (`public/scripts/extensions/shared.js:424`; used `llm-client.js:170-178`).

Shared.js sets `custom_url: profile['api-url']` then spreads `overridePayload` (`shared.js:451-462`). Unverified by us; relevant only if we add chat-completion-specific paths.
- `worldInfoCache` is an exported `StructuredCloneMap` with `.set/.delete` (`public/scripts/world-info.js:882`); they evict/set it after direct `/api/worldinfo/edit|delete` writes (`router.js:467-497`). Candidate fix for our open "so-assets leaves `worldInfoCache` stale".
- `/api/worldinfo/get` answers a **missing** book with `200 {entries:{}}` (`src/endpoints/worldinfo.js:76` `readWorldInfoFile(…, true)`, dummy at `:18,27-29`). Their `loadWorldInfoFresh` comment "a completed backend response is authoritative, including not found" (`router.js:452`) is **wrong** — **confirms** our gotcha that existence must come from `world_names`, never a WI read.
- `createBranch` seeds the branch with `{ main_chat, integrity }` only (`bookmarks.js:201`); extension `chat_metadata` never follows a branch.
- `saveSettingsDebounced` debounces 1000 ms (`script.js:470`, `constants.js` `relaxed: 1000`); a reload inside the window loses the write, and `saveSettings` only `console.error`s on a failed POST — their WAL rationale (`src/state/critical-settings-backup.js:1-8`).
- `CHAT_COMPLETION_PROMPT_READY` `eventData.chat` and `GENERATE_BEFORE_COMBINE_PROMPTS` `eventData.finalMesSend` are mutated in place and ST sends the mutated arrays (`index.js:7818-7828`).
- `generate_interceptor` receives `type` (`'swipe'|'regenerate'|…`) and they run swipe rollback there, before the new generation (`narrative-hooks.js:1210,1224-1226`) — complements our `MESSAGE_SWIPED` path.
- `ctx.registerFunctionTool/unregisterFunctionTool` exist; `formatMessage: () => ''` suppresses the tool-call chat message (`narrative-hooks.js:604-606`); tools can be swapped per turn by unregister/register (`:707-722`).
- Their doc: `/sendas` does not emit `GENERATION_ENDED` (`docs/multihogDnDdoc.md:184-186`) — consistent with our TurnBridge using render events with `command` type.
- `message.extra` is persisted with the chat and survives swipes, so per-swipe maps keyed by `swipe_id` work (`index.js:3209-3218`).

## Verdict
Relevance **medium**. Different product (free-text RPG simulator, not a checkpoint graph) and its persistence model is what we deliberately avoid, but it has solved several host problems we have not: branches, swipe-back cost, cancelling in-flight passes, and settings-save loss. The one thing worth taking: **story continuation across ST branches** (idea 1) — a real, user-visible gap (`bookmarks.js:201` drops our blob) that our rollback history already makes cheap to close; the S-effort runner-up is passing the epoch `AbortSignal` into `sendRequest` (idea 2).
