# MCP Client (+ MCP Server plugin) — v2.4 review

author: bmen25124 (post by "weather") · repo: https://github.com/bmen25124/SillyTavern-MCP-Client (+ server half https://github.com/bmen25124/SillyTavern-MCP-Server) · commit `04fdfe4` 2026-06-09 (client, per research README) · 16 upvotes / 465 msgs · source available: **y** (client `source/`, server `source-server/`)

## What it is
Bridge from ST's function-calling (`ToolManager`) to external MCP servers. A server plugin (`/api/plugins/mcp/*`) spawns stdio MCP servers (or talks SSE / streamable-HTTP), speaks JSON-RPC, caches their tool lists on disk. The client extension registers every enabled MCP tool as an ST function tool, so a chat-completion model with "Enable function calling" on can call them mid-reply. UI = one settings toggle + a "Manage Tools" popup (per-server and per-tool enable, add server by command line or `mcpServers` JSON, reload, reveal config file in the OS file manager). No story/memory/chat-state logic at all.

## How it works
- **Client boot** (`source/src/index.ts:583-585`): defaults into `extensionSettings.mcp = {enabled}` (`:23-48`), appends settings template to `#extensions_settings` via `renderExtensionTemplateAsync('third-party/SillyTavern-MCP-Client', …)` (`:51-55`, folder name hard-coded), then `MCPClient.handleTools(enabled)` (`:500`).
- **Tool registration**: for each enabled server → `POST /servers/:name/start` → `GET /list-tools` → `context.registerFunctionTool({name: "mcp_<server>_<tool>", displayName, description, parameters: inputSchema, action → callTool, formatMessage})` (`source/src/mcp-client.ts:125-141`). Unregister on disconnect/tool disable (`:231-242`, `:436-445`). Registration state lives only in page memory (`#connectedServers`, `#serverTools`, `:34-38`) — rebuilt each page load.
- **Tool call**: ST invokes `action(params)` → `POST /servers/:name/call-tool` (`mcp-client.ts:457-480`); server re-checks the disabled list (403) and that the tool exists in its cache (`source-server/src/mcp.ts:511-524`), validates args against the tool's JSON schema (`source-server/src/McpClient.ts:434-437`, `jsonschema`), sends `tools/call`, unwraps nested `content` wrappers and maps `isError` to a rejection (`McpClient.ts:652-672`). Result returns `{toolName, status:'executed', data}` (`mcp.ts:538-544`) and ST writes it into chat.
- **Provider schema sanitising** at `CHAT_COMPLETION_SETTINGS_READY` (`index.ts:506-580`): mutates `payload.tools[*].function.parameters` in place — strips `title` everywhere; for `chat_completion_source === 'makersuite'` also strips `additionalProperties`/`default` and fills empty `properties` with a `_dummy` string.
- **Server plugin** (`source-server/src/index.ts:9-53`, `mcp.ts:222-564`): Express router, per-user config `data/<user>/mcp_settings.json` (`request.user.directories.root`, `mcp.ts:38-74`) with lazy field migration on read + `write-file-atomic`. stdio servers spawned with `{...process.env, ...config.env}` (`mcp.ts:98`, `McpClient.ts:180-183`), Windows commands wrapped in `cmd /C` (`mcp.ts:103-109`), 100 ms sleep then `initialize` + protocol-version check (`McpClient.ts:232-262`). Tool lists cached to disk so the UI can list tools without spawning (`mcp.ts:183-184`, `:414-421`); a reload spawns temporarily and stops again (`:164-205`). `/open-settings` shells out to `explorer /select,` / `open -R` / `xdg-open` (`index.ts:12-36`).
- **Persistence**: install-wide toggle in `extensionSettings`; everything else in the server file. Nothing per-chat, nothing in `chat_metadata`.
- **Mutation handling**: none of its own. Swipe/edit/delete of tool messages is ST's (see host facts). No LLM calls of its own; the only LLM is the main generation deciding to call a tool.

## Overlap with Story Orchestrator
- **Server plugin + client split**: same shape as our judge (`server-plugin/story-orchestrator-judge/index.mjs`, client `src/services/stHost/judge.ts`). Ours is better on the failure edge: upstream timeout (`index.mjs:11` `UPSTREAM_TIMEOUT_MS = 10_000`, abort at `:105-118`) and client timeout → fallback (`src/judge/client.ts:40` `askJudge`); theirs has **no request timeout at all** (see anti-patterns). Theirs is better at telling the user *why* the plugin failed (404 → "install plugin, restart ST", `mcp-client.ts:43-67`); ours collapses every failure to `null` (`src/services/stHost/judge.ts:28-31`) and the probe says "not installed, or the route refused" (`src/services/stHost/capabilities.ts:62-66`).
- **Server re-checks the client's enable list at the call edge** (`mcp.ts:511-517`) — same principle as our `isCuratorWritable` re-check at the write edge (`src/stagecraft/scope.ts:24`). Confirms our pattern; nothing to take.
- **Function tools**: we register none (baseline §4; grep `registerFunctionTool|ToolManager|tool_invocations|TOOL_CALLS` over `src/` = 0 hits). Our readers already skip `is_system` rows, which is what tool-result messages are (`src/extraction/chatWindow.ts:8`, `src/runtime/scoreContext.ts:12-13`, `src/runtime/coordinators/stagecraftCoordinator.ts:61`).
- **Payload mutation hooks**: we never listen to `TEXT_/CHAT_COMPLETION_SETTINGS_READY` (grep `SETTINGS_READY` over `src/` = 0). Our only generation-param lever is the persistent preset swap (`src/services/stHost/presets.ts:36-58`, textgen-only, refused elsewhere with `PRESET_UNSUPPORTED_REASON`), guarded by the owned-effect ledger (`src/runtime/effectLedger.ts`).

## Ideas for v2.4

| # | idea | kind | our area | our state | value | effort |
|---|---|---|---|---|---|---|
| 1 | Per-request sampler overlay at `*_COMPLETION_SETTINGS_READY` instead of a global preset swap | host-integration | stagecraft (effects) | absent | 4 | M |
| 2 | Tool-call turns in TurnBridge: decide + live-test the intermediary-reply / recursion / placeholder-delete sequence | testing | host (turnBridge) | absent | 3 | S |
| 3 | Plugin/route failure diagnosis by status code (404 vs 403 stale-CSRF vs 5xx vs network) | ux | judge / capabilities | partial | 2 | S |
| 4 | Do NOT expose story memory/state as function tools (pull-recall or in-reply state report) | anti-pattern | memory / extraction | absent (correctly) | 2 | S |

**1. Per-request sampler overlay.** What: apply a checkpoint's sampler fields (temperature, top_p, rep_pen…) by mutating the outgoing request object in a listener on `TEXT_COMPLETION_SETTINGS_READY` / `CHAT_COMPLETION_SETTINGS_READY`, for the main generation only, instead of switching ST's active preset. Their evidence: in-place mutation of the payload at `CHAT_COMPLETION_SETTINGS_READY` lands in the request (`source/src/index.ts:507-579`); ST awaits the emit right before `fetch` (`public/scripts/openai.js:3146`) and the textgen twin emits `params` in `getTextGenGenerationData` (`public/scripts/textgen-settings.js:1844-1848`, called by main Generate at `public/script.js:5275`). Our evidence: preset effect is a global write (`src/services/stHost/presets.ts:54-58`) that needs write-ahead ledger + compare-and-set restore (`src/runtime/effectLedger.ts:72`, `:112`) and is refused on chat completion (`presets.ts:41`) — baseline seed A "OpenAI/chat-completion preset adapter" is exactly this contract question. Fit: nothing global to restore, cannot leak into another chat, covers both backends, and ConnectionManager memory-LLM calls do not emit these events (`public/scripts/custom-request.js:601` builds params directly) so extraction is untouched. Caveats to verify: textgen `generateRaw` quiet also emits (`script.js:4063`) → gate on our own `GENERATION_STARTED` type; param names differ per API; the overlay must show in the next-turn preview (`src/runtime/nextTurn.ts`) or the author sees one preset and hears another. Invariants: new `stHost/` event seam (2); 21 is relaxed deliberately, not broken; 16 still holds (no host write, so no `WriteResult` needed, but record an applied row for audit).

**2. Tool-call turns in TurnBridge.** What: any installed tool extension (this one, Image Director, etc.) changes the event shape of a reply on chat-completion backends, and SO never saw it. Sequence verified in ST source: intermediary text is finalized and emits `MESSAGE_RECEIVED` + `CHARACTER_MESSAGE_RENDERED` (`script.js:5415-5416` → `:3798-3801`) — i.e. a **boundary commits mid-turn**; an empty placeholder is instead removed with `deleteLastMessage` → `MESSAGE_DELETED(chat.length)` (`script.js:5414`, `:1607-1611`) — i.e. a **rollback call** mid-turn; the tool result is a hidden-from-extraction `is_system` message with only `TOOL_CALLS_PERFORMED/RENDERED` (`tool-calling.js:899-921`); then `Generate('normal')` recurses and the real reply renders again (`script.js:5434-5435`). Any stealth tool call ends generation with no reply (`script.js:5421`). Their evidence: `mcp-client.ts:129` is what puts a user on this path. Our evidence: `src/runtime/turnBridge.ts:9` denylist has no notion of it, `:79-87` keys boundaries per message id. Fit: invariant 3 (one boundary per rendered reply) — decide whether the pre-tool text is a turn (probably yes, it is character speech) and assert the continuation commits its own boundary; add the row to `scripts/debug/so-turn-types-check.mts` with a dummy `registerFunctionTool` on a chat-completion profile. Also check deleting a reply: ST deletes preceding tool-invocation rows with it (`script.js:1614-1629`).

**3. Plugin failure diagnosis.** What: map the plugin status call's HTTP outcome to a named cause and remedy. Their evidence: `mcp-client.ts:43-67` (404 → "install the plugin, restart SillyTavern"; 500 → "check the console"). Our evidence: `judgeStatus()` returns `null` for 404, 403, 5xx and network alike (`src/services/stHost/judge.ts:28-31`); probe text "not installed, or the route refused" (`capabilities.ts:64`). The 403 case matters to us specifically: stale CSRF makes every POST 403 while the page looks fine (our gotcha, `ensureSTReady` in the harness) — a player should see "reload the page", not "plugin missing". Fit: none violated; lands in `CapabilitiesGroup` + Copy-for-bug-report.

**4. Anti-pattern: story memory/state as function tools.** Tempting inversion of this extension (let the main model pull `story_recall` or push `report_state` via tools). It breaks us three ways, all host-evidenced: non-stealth tool results are persisted as a visible system message whose text is the result (`tool-calling.js:903-915`) → memory/epistemic content shown in chat, violating invariant 9 (and 15 for private rows); stealth calls stop the generation outright (`script.js:5421`), so a stealth tool cannot serve recall; tools only exist when `main_api === 'openai'` and `function_calling` is on (`tool-calling.js:618-620`), never for impersonate/quiet/continue (`:697-699`), while our live backend is text completion. A model-asserted delta via tool also has no evidence quote in the window (invariant 4) and puts state writes on the reply path (invariant 5). Keep push-injection + off-path extraction.

## Patterns to copy / anti-patterns to avoid
Copy:
- Server-side config file with **lazy field migration on read** + atomic write (`source-server/src/mcp.ts:38-74`). If the judge plugin ever grows config, this is the shape (per-user `request.user.directories.root`).
- **Cache the expensive listing on disk** so UI can render without starting the backend (`mcp.ts:183-184`, `:414-421`). Analogous to our per-page capability cache; nothing new.
- **Validate arguments server-side against the declared schema** before forwarding (`McpClient.ts:435`).
Avoid:
- **No timeout anywhere on the call path**: `ErrorCode.RequestTimeout` declared (`McpClient.ts:12`) but `sendRequest` never arms a timer (`:439-470`), and ST shows the tool toast with `timeOut: 0` while awaiting (`tool-calling.js`, `invokeFunctionTools`) → a hung MCP server hangs the reply forever. We already timeout+fallback; keep it that way.
- **`process.env` passed wholesale to third-party child processes** (`mcp.ts:98`, `McpClient.ts:181`) — every secret in ST's environment reaches every installed MCP server.
- **Server-supplied strings into `innerHTML`** (tool name/description, `source/src/index.ts:224-233`). We render popups via text nodes (`src/services/stHost/popup.ts:13`); keep it.
- **Missing `return` after an error response** (`mcp.ts:290-295`: 409 sent, then config overwritten and a second response attempted); `stopMcpServer` not awaited on delete (`mcp.ts:311`); 100 ms sleep as a readiness signal (`McpClient.ts:232`).
- **Hard-coded install folder** in `renderExtensionTemplateAsync('third-party/SillyTavern-MCP-Client', …)` (`index.ts:51-52`) — breaks when installed under another folder name.
- **Success toast is a timer, not evidence**: every control shows "Updated"/"Success" after the await and resets after 1500 ms (`index.ts:76-90`) with no read-back; same class as our "saveMetadata never rejects" gotcha.
- **Tool count blows context** (author, post.md follow-ups: 44 tools → instant context error). Everything an extension adds to the prompt needs a visible size; our next-turn preview already carries `characters` per block (`src/runtime/nextTurn.ts:23`).

## ST host facts learned
From their code:
- `context.registerFunctionTool({name, displayName, description, parameters, action, formatMessage})` / `context.unregisterFunctionTool(name)` exist on the context (`source/src/mcp-client.ts:129-140`, `:237`); ST also accepts `shouldRegister` and `stealth` (`public/scripts/tool-calling.js:269-288`; context binding `public/scripts/st-context.js:183-187`).
- `CHAT_COMPLETION_SETTINGS_READY` payload carries `tools` and `chat_completion_source`, and in-place mutation reaches the request (`source/src/index.ts:507-579`; ST `openai.js:3146` awaited emit before fetch). Emitted only from `sendOpenAIRequest`, not from ConnectionManager requests (`custom-request.js:601`).
- Gemini (`makersuite`) rejects `additionalProperties`/`default` and empty `properties` in tool schemas (author's claim, `index.ts:573-578`; not verified against Google).
- Server plugin contract: `export default {init(router), exit, info:{id,name,description}}`, routes under `/api/plugins/<id>/`, `request.user.directories` available, client must send `getRequestHeaders()` (`source-server/src/index.ts:45-53`, `mcp.ts:39`; `mcp-client.ts:73`). Consistent with our judge-plugin gotcha. They ship a webpack-bundled CommonJS `dist/index.js` (`source-server/package.json` `"type": "commonjs"`), the alternative to our own-`package.json` ESM route — no contradiction.
Verified in ST source while tracing their hooks (not in their code):
- Tool turns: intermediary reply emits `MESSAGE_RECEIVED`+`CHARACTER_MESSAGE_RENDERED`, empty placeholder → `MESSAGE_DELETED(chat.length)`, result = `is_system` + `extra.tool_invocations` message, then recursive `Generate('normal')` (`script.js:5410-5435`, `:3798-3801`, `:1607-1611`; `tool-calling.js:899-921`). Recursion bounded by `ToolManager.RECURSE_LIMIT` (`script.js:4495`).
- `TEXT_COMPLETION_SETTINGS_READY(params)` fires for main Generate and textgen `generateRaw` quiet (`textgen-settings.js:1847`; `script.js:5275`, `:4063`).
- **Possible contradiction with our TurnBridge assumption**: `deleteMessage` emits `MESSAGE_DELETED` with the post-deletion `chat.length`, not the deleted id (`script.js:1698`), and removes preceding tool-invocation rows with the reply (`:1614-1629`). `turnBridge.ts:159-167` treats the payload as the deleted message id (`keyed >= messageId`). Deleting a message in the middle of the chat therefore rewinds from the *tail*, not from the deleted message. Verify live before v2.4 builds on delete-rollback. Not recorded in `gotchas.md`.

## Verdict
Relevance **low**. It is plumbing between ST function calling and external tool servers, and it is orthogonal to a story engine. Exposing SO state through tools is an anti-pattern for us (idea 4). The one thing worth taking is **the hook it demonstrates**, not the feature: mutate the outgoing request at `*_COMPLETION_SETTINGS_READY` so checkpoint sampler effects become per-request overlays (idea 1). That answers the chat-completion preset seed and removes a global-state write. A second, cheap item: add a tool-call turn row to the turn-types live check, and check the `MESSAGE_DELETED(chat.length)` finding while doing it (idea 2).
