# ST Memory Books (STMB) — v2.4 review

meta: author Aiko Apples (aikohanasaki) · repo https://github.com/aikohanasaki/SillyTavern-MemoryBooks · commit `0e9bdf9` (2026-09-18), manifest v9.2.3 · 271 upvotes / 20,994 msgs · source available: **y** (~52k lines JS; read the hook wiring, rollback, branch, progress, narrator and macro modules plus the 2.6k-line AI reference manual; skipped `index.build.js`, locales, `userguides/*_xx.md`). **AGPL-3.0**: take ideas, not code.

## What it is
The most-used memory extension. It turns chat ranges (manually marked ►/◄ scenes, or auto every N messages with a buffer) into LLM-written `{title, content, keywords}` entries in ordinary lorebooks ("Memory Books"). Old messages can then be auto-hidden to save tokens. Around that core it adds: tiered consolidation (Scene→Arc→Chapter→…→Epic), Clips and Topical Clips, "Side Prompts" (user-authored trackers re-run on an interval into a WI entry), compaction, reviewable regeneration, a job queue, group and "Narrator" modes with per-character books, branch-aware book copying, and auto-rollback on message deletion. It has no story model: it records what happened, it never steers.

## How it works
- **Boot/wiring**: `APP_READY` → `init` (`index.js:14258-14259`), slash cmds via `SlashCommandParser.addCommandObject` (`index.js:12198`, `:12422-12433`: `/creatememory`, `/scenememory`, `/nextmemory`, `/stmb-catchup`, `/sideprompt*`, `/stmb-highest`, `/stmb-set-highest`, `/stmb-stop`). Entry point is the wand menu, not a drawer.
- **Events** (`index.js:12846-13060`): `CHAT_CHANGED`, `WORLDINFO_UPDATED` (macro cache refresh), `CHARACTER_RENAMED/EDITED/DELETED` (re-key per-character book locks), `MESSAGE_DELETED` (rollback), `MESSAGE_SENT/RECEIVED/EDITED/SWIPED` (re-snapshot chat identity; stamp the narrator cast), `GENERATION_STARTED/ENDED/STOPPED`, `WORLDINFO_ENTRIES_LOADED` (per-speaker book injection), `GENERATE_AFTER_DATA` (legacy request hijack, below). Also `SETTINGS_UPDATED` and `CHAT_RENAMED` (`stmbProgress.js:58`, `:310-322`).
- **Middle-delete decoding**: ST emits `MESSAGE_DELETED` with the resulting `chat.length`, not the deleted id. `createMessageDeletionTracker` (`memoryRollback.js:65-140`) snapshots the chat's identities on every send/receive/edit/swipe/chat change: a `WeakMap` object id per message, plus a fallback "stable" id `[send_date,name,is_user,is_system,original_avatar,mes]`. On delete it diffs before/after to recover `{start,end,count,isTail}` (`:94-103`, `:122-138`). Wired at `index.js:12897-12918`, falling back to "the payload is the id" when undecodable.
- **Auto-rollback policy** (manual §27.2, `memoryRollback.js`): a tail delete rolls back every memory whose `STMB_start..STMB_end` intersects the removed suffix. A middle delete asks the user: **Full** (the affected memory and everything newer), **Affected only** (drop the overlaps, shift later ranges by the count, leave a permanent gap), or **Cancel**. Before writing it re-fingerprints the books (`fingerprintRollbackEntry` `:57-63`). It keeps pre-write clones for compensating saves if a later book write fails, and it moves the chat checkpoint only after every book write succeeded. Consolidation parents are deleted transitively and their disabled sources re-enabled.
- **Branches** (`branchLorebooks.js`): on `CHAT_CHANGED` it compares with the previous snapshot. It is a new native branch when `chat_metadata.main_chat === previous chatId`, the name matches `/ - Branch #\d+$/` and no completed marker exists (`:7`, `:65-73`). Every bound Memory Book is then cloned to `<root> Branch N`, with parent chat ids rewritten inside the entries, and the branch is rebound to the copies (`:362-460`). The copies' existence is verified via `world_names` (`:411-420`) and a `completed|failed` marker is stored. **If copying fails it clears the branch's inherited bindings** so the branch cannot write into the parent's books (`:335-360`). The progress toast says "do not switch chats", and `assertActiveChat` aborts if you do (`:283-299`).
- **Deferred progress** (`pendingProgress.js`, `stmbProgress.js`): a job that finishes after its chat was closed never writes the inactive chat. It parks `{chatRef, target, integrity, sha256(messages[0..end] identity+text)}` in settings (`pendingProgress.js:8-21`) and validates on reopen (`:23-41`: `chat`/`identity`/`marker`/`messages` refusal reasons). The settings write is **verified**: it waits for `SETTINGS_UPDATED`, then reads `/api/settings/get` back, with a 10 s deadline (`stmbProgress.js:49-71`).
- **Group/Narrator per-speaker memory**: during generation it merges the drafted speaker's book (or each active cast member's) into `characterLore` from a `WORLDINFO_ENTRIES_LOADED` handler (`index.js:12978-13015`, `narratorMode.js:221-231`). No book is bound to the chat. The active cast is stamped on `message.extra` **and** on `swipe_info[swipe_id].extra` (`narratorMode.js:159-181`) and restored from the timeline on swipe and tail delete (`index.js:973-985`).
- **LLM calls** (`stmemory.js`): its own `fetch` with JSON-schema structured output plus a `dirty-json` repair. Optionally it goes through `ChatCompletionService.sendRequest/processRequest(body,{presetName},…,signal)`, which applies a chat-completion preset per request (`stmemory.js:347-410`, `:602-621`). Every path is abortable (`/stmb-stop`). The legacy path mutates `generate_data` in `GENERATE_AFTER_DATA` while `isProcessingMemory` (`index.js:13017-13060`).
- **Macros**: `macros.registry.registerMacro('memtierN'|'memclips'|'memside', {category, description, returns, returnType, handler})`, i.e. the new macro engine directly (`memoryTierMacros.js:80-103`).
- **Persistence**: memories live in WI files with custom entry fields (`stmemorybooks`, `STMB_start/end`, `STMB_chatId`, tier, links). Per-chat markers go in `chat_metadata.STMemoryBooks` (highest processed, scene, branch marker). Install-wide settings go in `extension_settings.STMemoryBooks`. Hiding works by flipping `is_system` via `/hide`.
- **Tests**: `node:test` over pure policy modules (`*.test.js` beside each, e.g. `memoryRollback.test.js`); a pre-commit hook builds the bundle.

## Overlap with Story Orchestrator
- **We do more/better**: typed extraction into tiers with provenance, a conflict queue and quarantine (`src/memory/provenance.ts`, `src/runtime/memoryQueue.ts:144`). Rollback ≡ replay across every store (`src/runtime/rollback.ts:35`, `src/memory/reverse.ts:23`), where STMB only handles delete (it explicitly ignores edits and swipes). Per-member private epistemic without WI (`src/memory/epistemic.ts:50`); STMB's own manual §11.7 concedes that its books and filters "are not privacy controls". Canon synthesis and arcs. We already have the compare-and-set curator revert that STMB's regeneration safety check describes (`stagecraftCoordinator.ts:284-351`, `externally-edited`).
- **They do and we don't**: decoding a middle delete correctly; forking memory at an ST branch; verifying a settings save; injecting a book at scan time without binding it; hiding processed messages to save tokens; user-authored trackers (Side Prompts); tiered consolidation with an outlier channel.
- **Both**: WI as a memory surface (ours is the per-chat mirror `src/runtime/memoryMirror.ts:69`, bound to the chat slot `src/services/stHost/worldInfo.ts:151-163`); a chunked catch-up (`runMemorizeBacklog`, `extractionCoordinator.ts:383`).

| # | idea | kind | our area | our state | value | effort |
|---|---|---|---|---|---|---|
| 1 | Decode `MESSAGE_DELETED` with a chat-identity snapshot; roll back from the real start | host-integration | host / rollback | absent | 5 | S |
| 2 | Story follows an ST branch: detect via stamp + `main_chat`, adopt, roll back to the branch tail | new-feature | host / persistence | absent | 4 | M |

**1. Decode the delete.** What: keep an identity snapshot of `chat` (object identity via `WeakMap`, plus a fallback of send_date+name+is_user+mes). Refresh it on every event TurnBridge already hears. On `MESSAGE_DELETED`, diff it to get `{start,count,isTail}` and call `rollbackFromMessage(start)`; the `turnKeys` purge uses `start` too. Theirs: `memoryRollback.js:65-140`, wiring `index.js:12897-12941`, tests in `memoryRollback.test.js`. Host: `deleteMessage` splices the middle and emits `chat.length` (ST `script.js:1678-1699`; also `:1611`, `:4411`, `:11734`). Ours: `src/runtime/turnBridge.ts:56` → `onMutation` `:159-169` treats the payload as the deleted id. A delete at message 3 of 10 therefore rewinds from 9, and boundaries 3..8 plus every memory row sourced there survive against a transcript that no longer holds them. After the splice, every later `messageId` in provenance is also off by one. Already flagged as a *problem* by `mcp-model-context-protocol.md:63` and `roadway-…md:58`; STMB is the tested *fix*. Fit: restores inv. 11. Pure diff function, unit-testable, plus a leg in `so-turn-types-check.mts`. When it cannot decode, fall back to the payload (today's behaviour) and journal it. Keep **full** rollback semantics (see 8).

**2. Branch continuation.** What: ST copies the whole parent `chat_metadata` into a branch (`script.js:7406` `{...chat_metadata, ...withMetadata}`; groups `group-chats.js:2370`) and overrides only `{main_chat, integrity}` (`bookmarks.js:201`). So our blob **does** arrive, stamped for the parent. V5 then reads it as "no story selected" (`src/runtime/persistence.ts:34`, `:61-72`), and an explicit select adopts it (`storySelection.ts:71`) while hydrating the **parent's tail state**. Nothing reconciles the engine against the shorter chat (`engine.ts:140-146` has no tail check; `runtimeManager.ts:522-546` neither). Proposal: when the blob's `chatId === chat_metadata.main_chat` and the open chat differs, offer "Continue the story from the branch point". That means adopt, then `rollbackFromMessage(chat.length)`, which rides the existing horizon notice/restart, and a fresh mirror book (already the adoption path, `memoryMirror.ts:65`). Theirs: detection `branchLorebooks.js:65-73`, failure-safe `:335-360`. Fit: explicit, never automatic (V5 stands); invariants 11/12 are reused. **Contradicts** `multihog-…md:45,85`, which says the blob does not follow a branch. It does.

**3. Transcript fingerprint.** What: at each committed boundary, store a short hash of the consumed messages' identity (`send_date|name|is_user|mes`) beside `{lastMessageId, chatLength}`. On hydrate, re-hash the latest K boundaries against the loaded chat and `rollbackFromMessage(firstMismatch)`. This catches everything no event reports: edits and deletes made on another device or with SO disabled, a branch (idea 2), and a chat restored from `data/default-user/backups/`. Theirs: `progressFingerprint` + `validatePendingProgress` (`pendingProgress.js:8-41`), and regeneration's "source range unchanged" check (manual §19.4). Ours: `sourceRevision` is an in-session counter (`src/runtime/runOwner.ts:22`, `:103`), not a content hash, and boundaries record indexes only (`src/engine/engine.ts:13`, `:26`). Fit: the runtime computes the hash and the engine stores an opaque string (inv. 1). Adding the field bumps the blob version with a migration (inv. 13). A legacy boundary without a hash is "unknown", never a mismatch. Alternative considered: stamp a boundary marker into `message.extra`. It is per-swipe (`script.js:6939`, `:7015`) and travels with branches, but it is a new write into the host's chat, so keep the hash in our own blob.

**4. Inherited mirror binding.** What: the branch also inherits `chat_metadata.world_info` = the parent's mirror book (`worldInfo.ts:160`). Until someone adopts, ST activates the parent's mirror rows in the branch, including rows from messages after the branch point. The same happens in any chat that copied the metadata. Fix: when a foreign-stamped blob's `memory.wiBook` equals the chat slot, unbind the slot (the chat slot, not our blob) and journal it. Theirs: bindings are cleared rather than shared (`branchLorebooks.js:242-255`, `:335-340`). Fit: a slot write with a typed result (inv. 16). It never deletes the parent's book.

**5. Unbound mirror.** What: stop occupying the chat lorebook slot. From a `WORLDINFO_ENTRIES_LOADED` handler, push the per-chat mirror's entries into `chatLore` as `{uid, world, ...}` (ST shape `world-info.js:4557`; the event is awaited with mutable arrays, `:4604`). Theirs: `index.js:12978-13015`, `narratorMode.js:221-231`. Why: today a user's own chat book makes the mirror inert (`bindChatLorebook` → `occupied`, `worldInfo.ts:159`; `memoryMirror.ts:122`), and a slot binding leaks into branches (idea 4). Costs: the event fires on every scan, including dry-runs and quiet passes, so it must be cheap and cached. A new `stHost/` seam is needed (inv. 2). The book still exists on disk for inspection. **Never** use this for epistemic rows (inv. 15).

**6. Hidden ≠ deleted.** What: `/hide` only flips `is_system` (ST `chats.js:147-162`), and `readMessage` drops every `is_system` (`src/extraction/chatWindow.ts:8`). With STMB's auto-hide (manual §9.2) or Presence running, a re-read of an already-consumed range sees holes: conflict re-read, reconciliation, memorize backlog. It can then fail evidence or read a different story. STMB hits the same wall and offers "unhide for generation" (`chatcompile.js:60-66`). Proposal: re-reads of consumed ranges take an `includeHidden` option and skip only real system posts (`extra.type`). Policy question: a user may hide OOC on purpose. Fit: read-only.

**7. Settings-save evidence.** Corroborates `multihog-…md:51`, with a tested technique. `saveSettings` swallows errors and emits `SETTINGS_UPDATED` only after a 2xx (ST `script.js:8096-8114`). STMB awaits that event and then compares `/api/settings/get` (`stmbProgress.js:49-71`). Ours: library saves, wizard sessions and settings go through `saveSettingsDebounced()` with no evidence (`src/runtime/storyLibrary.ts:110`, `wizardSessions.ts:44`, `settingsStore.ts:135`), yet the UI states `Saved "X" vN to the library.` Fit: inv. 17 extended to the install-wide home.

**8. Anti-pattern: "affected only".** Dropping only the overlapping memories and shifting later ranges by the deletion count leaves a gap that STMB itself calls permanent, and it keeps derivations built on a transcript that no longer exists. For us it breaks rollback ≡ replay (inv. 11). Take their decoder (1), not their choice menu.

## Patterns to copy / anti-patterns to avoid
- Copy: **pure policy module + `node:test` per concern** (rollback, branch, pending progress, retry policy), with host deps injected: the same shape as our coordinators.
- Copy: **refusal reasons as data** (`validatePendingProgress` → `invalid|chat|identity|marker|messages`). It matches our `WriteResult` rule and the "two findings must not share a reason" gotcha.
- Copy: **fail closed on a partial fork**: a failed branch copy clears inherited bindings rather than share the parent's (`branchLorebooks.js:335-360`).
- Copy: **multi-book writes with pre-write clones and compensating saves**, and the chat marker moved last (manual §27.2). Relevant if the curator ever writes more than one book per boundary.
- Copy (prompt shape): consolidation JSON with `member_ids` plus an explicit `unassigned_items` outlier channel, and the previous higher-tier summary given as read-only canon context (manual §17.5-17.6). Candidate for our arc-summary/canon prompts (`src/memory/canon.ts:23`), which have no outlier escape.
- Corroborates (already in 4 reports): memory-model calls are abortable. STMB passes `signal` through its fetch and `ChatCompletionService` (`stmemory.js:347-410`), and ST's `ConnectionManagerRequestService.sendRequest` honours `custom.signal` (`shared.js:415,424`, since ST commit `ec474f557`, 2025-03-21).
- Avoid: mutating the host's `generate_data` in `GENERATE_AFTER_DATA` to repurpose it for a side generation (`index.js:13017-13060`). It is global state shared with every other listener.
- Avoid: auto-hiding chat messages from the product. It rewrites host chat state that other extensions (Presence) also fight over (manual §9.2, §23.2), and it conflicts with our "SO never rewrites the chat" stance.
- Avoid: branch detection by display-name regex alone (`/ - Branch #\d+$/`). Our stamp plus `main_chat` plus `integrity` is sturdier and survives renames.

## ST host facts learned
- `MESSAGE_DELETED` payload = post-deletion `chat.length`, not the deleted id: `script.js:1611` (deleteLastMessage), `:1699` (deleteMessage, middle splice at `:1678-1684`), `:4411`, `:11734`. STMB `memoryRollback.js:65-68`. **Contradicts** the assumption in our `turnBridge.ts:56,159-169`. It is not in `gotchas.md`.
- A branch's `chat_metadata` = the parent's whole `chat_metadata` + `{main_chat, integrity: uuid}`: `bookmarks.js:201`, `script.js:7406`, `group-chats.js:2370`. So our blob and the chat lorebook slot follow a branch. **Contradicts** `multihog-d-d-…md:85`. The name is `<root> - Branch #N` (`bookmarks.js:209-213`), and the parent's message gets `extra.branches.push(name)` (`:239-243`).
- `chat_metadata.integrity` is a per-chat UUID minted on load if missing (`script.js:7665-7667`, `group-chats.js:276-278`). It survives a rename, is fresh per branch, and is checked server-side on save (`src/endpoints/chats.js:337-368`). It is a stable chat identity we do not use (grep `integrity` in `src/` → none).
- `WORLDINFO_ENTRIES_LOADED` is awaited with the mutable `{globalLore, characterLore, chatLore, personaLore}` arrays, before strategy sorting (`world-info.js:4604`). Entries are `{uid, world, ...rest}` (`:4557`).
- `message.extra` is per swipe: `syncMesToSwipe` copies it into `swipe_info[id].extra` (`script.js:6939`), and `syncSwipeToMes` replaces it on swipe (`:7015`).
- `/hide` = flip `is_system` only, no marker (`chats.js:147-162`).
- `saveSettings` catches its own failure (toast only) and emits `SETTINGS_UPDATED` only after a 2xx (`script.js:8096-8114`).
- `ChatCompletionService.processRequest(body, {presetName}, extractData, signal)` applies a completion preset to one request (`custom-request.js:544-557`). `ConnectionManagerRequestService.sendRequest` forwards `custom.signal` (`shared.js:415,424`). **Contradicts** `src/runtime/runOwner.ts:60-62` (already flagged elsewhere).
- The new macro registry is `macros.registry.registerMacro(key, {category, description, returns, returnType, handler})` from `scripts/macros/macro-system.js` (STMB `memoryTierMacros.js:80-103`). `MacrosParser.registerMacro` bridges into it only while `experimental_macro_engine` is on, as category `legacy` (`macros.js:81-115`, `:183-211`). Consistent with our gotcha.

## Verdict
Relevance **medium-high**. The product overlaps our memory tier and is less principled: no typed state, no edit/swipe rollback, WI as its only store. But at 21k messages it has been hammered on host edge cases we get wrong. **The one thing worth taking: decoding `MESSAGE_DELETED` by chat-identity diff (idea 1).** Today a middle delete rewinds from the tail and leaves stale boundaries and off-by-N provenance; the fix is S-sized and pure. Close runners-up: branch continuation (2) with the inherited-binding leak (4), and a transcript fingerprint on hydrate (3). Together they cover every mutation SO cannot observe live.
