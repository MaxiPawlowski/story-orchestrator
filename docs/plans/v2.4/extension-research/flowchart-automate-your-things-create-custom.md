## What it is
Visual node-graph alternative to STScript (React + `@xyflow/react`). A user wires ~90 node types (ST event / slash / menu / message-toolbar / QR / manual triggers → logic, chat, lorebook, character, LLM, variable, JS/HTTP nodes) into "flows" that run on host events or on demand. General automation toolkit, not a narrative engine. Relevant to us for **host-integration techniques and debugging UX**, not for its feature set — SO deliberately keeps state typed and code-owned where Flowchart makes everything user-scriptable.

## How it works
- **Boot**: `src/index.tsx:55-61` → `ExtensionSettingsManager` (utils-lib) loads + migrates `extension_settings.flowchart` → mounts React settings into `#extensions_settings` → `flowRunner.reinitialize()`.
- **Registration is idempotent teardown+rebuild** (`src/FlowRunner.ts:243-350`): remove every `eventSource` listener it added, `delete SlashCommandParser.commands[cmd]` for its commands (`:252`, `SlashCommandNode/definition.ts:142`), call each trigger def's `unregisterAll`, then re-register from enabled **valid** flows only (`validateFlow` at `:271`; invalid flows are logged and skipped). One `eventSource.on(eventType)` listener per event type fans out to every trigger node (`:341-349`).
- **Event args → typed inputs**: event params declared per event as zod schemas (`src/flow-types.ts:15-280`), mapped positionally and `safeParse`d (`FlowRunner.ts:536-548`). Ids use `z.coerce.number()` (`flow-types.ts:20,27,32,40,44…`).
- **Execution**: top-level runs go through a single serial queue (`FlowRunner.ts:352-403`), sub-flows run inline with depth cap 10 (`:385`) + runtime cycle check on the execution path (`:420-427`). Event triggers default `preventRecursive: true` — suppressed if the same flow is running or queued (`:519-530`, `TriggerNode/definition.ts:11`). `LowLevelFlowRunner` is a Kahn topological walk; branch nodes prune edges via `determineEdgesToFollow` (`src/LowLevelFlowRunner.ts:83-227`). "Run to here" = restrict to the ancestor subgraph of a node (`:56-81`); "Run from here" = start queue at a node (`:98-103`, `FlowRunner.ts:658-686`).
- **Run trace**: every node emits `node:run:start/end` with `{status,input,output,error}` (`LowLevelFlowRunner.ts:148-199`) into a zustand store keyed by `runId` that ignores stale-run events (`components/popup/flowRunStore.ts:41-67`); the editor highlights the active node and shows per-node Input/Output tabs with copy (`components/nodes/NodeRunReport.tsx:11-50`).
- **Execution history**: last 50 run reports, strings truncated to 2048 chars, character objects reduced to 7 fields, stored in **browser IndexedDB via `SillyTavern.libs.localforage`**, not in settings; on quota error drop the oldest and retry (`FlowRunner.ts:29-100`).
- **LLM calls** (`src/api.ts`): utils-lib `Generator.generateRequest` → `ConnectionManagerRequestService.sendRequest(profileId, prompt, maxTokens, {stream, signal}, overridePayload)` (confirmed in bundle). Abort via one `AbortController` per top-level run, threaded to every LLM node (`FlowRunner.ts:455,468`; `api.ts:105-156`); `/flow-stop` aborts current + clears queue (`FlowRunner.ts:332-338,692-719`). Structured output three ways: native `overridePayload.json_schema={name,strict,value}` (`api.ts:193-208`), or JSON/XML prompt templates (Handlebars, user-editable in settings) with an example auto-generated from the schema (`api.ts:209-242`, `src/schema-to-example.ts`), then zod `safeParse` (`api.ts:244-251`). "Create Messages" builds the full ST prompt for a profile via utils-lib `buildPrompt` (`api.ts:76-101`).
- **UI injection**: message toolbar button injected into ST's message **template** (`#message_template .mes_buttons .extraMesButtons`) + one delegated `document` click reading `.mes[mesid]` (`MessageToolbarTriggerNode/definition.ts:41-57`, `FlowRunner.ts:184-206,231-235`); QR-bar groups re-rendered on `CHAT_CHANGED` (`QuickReplyTriggerNode/definition.ts:27-77`, `FlowRunner.ts:238`); wand-menu entries in `#extensionsMenu` (`MenuTriggerNode/definition.ts:35-43`).
- **Host internals by static relative import**: `updateMessageBlock` from `script.js`, `hideChatMessageRange` from `chats.js` (`src/config.ts:1-5,80-86`).
- **Safety**: per-flow "Allow Dangerous" toggle; JS/HTTP/advanced-If nodes fail validation without it (`validator.ts:123-135`, `ExecuteJsNode/definition.ts:59`, `HttpRequestNode/definition.ts:108`). Static checks: cross-flow cycle detection (`validator.ts:27-73`), in-flow cycles (`:225-256`), triggers with no incoming edges (`:258-289`), global slash-name uniqueness (`:291-320`).
- **Versioning**: per-node `_version` + registry of node/edge migrations incl. edge rewiring when an output handle is renamed (`src/migrations.ts:15-60`); flow-format BFS migration path (`src/flow-migrations.ts:33-109`, currently a no-op).
- **Persistence**: flows + prompts in `extension_settings.flowchart`; chat-local / global variables via ST's variable API. No `chat_metadata` of its own.
- **Mutation handling**: none. Swipes/edits/deletes are just more events a flow may subscribe to; nothing is rolled back.

## Overlap with Story Orchestrator
- Event → work fan-out: we do far more (typed boundaries, denylist of non-turn types, rollback on mutation: `src/runtime/turnBridge.ts:37`); they have no mutation semantics at all.
- Serial queue + recursion suppression ≈ our `ExtractionScheduler` P0/P1 lanes (`src/extraction/scheduler.ts:54`) — ours is richer (cadence, retry/pause, ownership tokens).
- Graph validation ≈ Studio diagnostics (`src/studio/diagnostics.ts:113`) — ours states consequences; theirs refuses to register an invalid flow (same stance as our parse-time refusal).
- LLM routing per node profile ≈ our single memory profile (`src/extraction/client.ts:11`). **They cancel in-flight calls; we do not** (see idea 1).
- Run trace UI: they are **better** here — live per-node input/output on the graph. Our graph (`src/components/studio/GraphPanel.tsx:25`) has no live state; the driver shows unmet gates as text only (`src/runtime/coordinators/copilotCoordinator.ts:170-173`).
- Debug history: theirs is bounded (2048-char strings) and off the settings file; ours persists 20 full audits incl. `prompt` + `rawResponse` inside `chat_metadata` (`src/extraction/types.ts:90-104`, `src/runtime/extras.ts:246`, `src/runtime/coordinators/extractionCoordinator.ts:198`).
- Undo: both have it (`src/studio/draft.ts:90`).
- Everything else (custom slash commands, QR/menu buttons, JS/HTTP nodes, user-editable prompt templates, message edit/delete/hide nodes) is automation SO deliberately does not offer (baseline §4: no QR/regex management, no autonomous rewriting).

**1. Cancel off-path LLM calls.** What: thread `runOwner.signal()` through `ExtractionClientOptions` → `sendConnectionProfileRequest` → `sendRequest(…, {…, signal})`. Theirs: one `AbortController` per run passed as `custom.signal` (`api.ts:118-127`, `FlowRunner.ts:455,468`). Host: `shared.js:416` documents `custom.signal`, `:424` destructures it, `:463`/`:481` pass it to `ChatCompletionService`/`TextCompletionService.processRequest`. Ours: `src/runtime/runOwner.ts:57-64` states sendRequest "takes no signal (shared.js:423)" — **false on current ST** — so only the judge honours the epoch signal; `src/services/stHost/connectionProfiles.ts:43-50` sends `{extractData, includePreset, includeInstruct, stream}` only. Payoff: on the RunPod backend (~33 tok/s, 15–35 s per pass) a chat switch or rollback currently lets every in-flight scene/epistemic/canon/curator pass run to completion and be discarded at the write edge. Fit: additive to invariant 10 (RunToken check stays the defence; abort is an economy). Traps: `shared.js:487` rethrows everything as `Error('API request failed', {cause})`, so abort must be recognised via `cause.name === 'AbortError'`, and an aborted read must **not** count as a failed read (a failed read pauses extraction install-wide). Verify the declared older host (ST 1.18.0) has the parameter before relying on it; if absent, the signal is simply ignored.

**2. Per-message toolbar actions.** What: a `stHost/messageButtons.ts` that prepends buttons into `#message_template .mes_buttons .extraMesButtons` + one delegated click resolving `.mes[mesid]`. Theirs: `MessageToolbarTriggerNode/definition.ts:41-57`, `FlowRunner.ts:184-206`. Ours: `flagMoment(note)` only flags the *current* boundary/message (`src/runtime/runtimeManager.ts:199-204`, `src/runtime/journal.ts:178-179`) from the drawer ⚑ or `/story flag` — a human-eval player cannot point at the message they mean, which is what the outstanding rubrics (J8.4, J9.6/7) need. Author variant: open the boundary log / audit / fired transition for that message id (data already in `getSessionJournal()`). Fit: flag is persona `both` (player-safe); inspector button only while author view is on (author view *adds* — invariant 9); `assert-player-clean` selector sweep must learn the new class. Caveats: template injection only affects messages rendered afterwards (`script.js:448,2618`) — existing messages get it on the next chat render; `a11y.js` rewrites roles on `.mes_button`.

**3. Gate trace.** What: pure `traceGate(gate, blackboard)` in `src/engine/gates.ts` returning each leaf with current value + boolean, surfaced in the driver panel and as an overlay on the Studio graph (active checkpoint, `visitedPath`, per outgoing transition met/unmet). Theirs: live node highlight + per-node input/output/status (`flowRunStore.ts:41-67`, `NodeRunReport.tsx:11-50`). Ours: `evaluateGate` returns a bare boolean (`src/engine/gates.ts:17-21`); driver shows `renderGateText` of unmet transitions only (`copilotCoordinator.ts:170-173`); `GraphPanel` props carry no runtime state (`GraphPanel.tsx:15-25`). This is the "why hasn't it advanced?" question every author asks. Fit: engine stays pure; UI reads it from the snapshot (invariant 18); author-only (invariant 9 — gates are spoilers). Their stale-run guard (`state.runId !== runId`) is our RunToken idea in UI form — reuse the chat id as key.

**4. Studio dry-run.** What: "run from / to here" for stories — choose a start checkpoint, edit blackboard values in a scratch form, step boundaries through the pure engine (`runReplay`, `src/engine/replay.ts:19`; `selectFiring`, `src/engine/transitions.ts:5`) and show the path taken. Theirs: ancestor-subgraph execution + start-at-node (`LowLevelFlowRunner.ts:56-103`). Ours: no simulation in Studio (grep `runReplay|simulate|playtest` over `src/studio`, `src/components`, `src/runtime`: 0 hits outside tests). Fit: touches no chat, no host, no LLM → no invariant strain; must never write the draft or the chat's engine state.

**5. Debug payload out of `chat_metadata`.** What: persist audits with `prompt`/`rawResponse` truncated (e.g. 2 KB head/tail + sha), keep the full text in-memory and optionally in `SillyTavern.libs.localforage` under `so:<chatId>:audits` with quota back-off. Theirs: `FlowRunner.ts:29-100` (localforage, 50 cap, 2048-char truncation, drop-oldest on quota). Ours: `SharedReadAudit` carries full `prompt` + `rawResponse` (`src/extraction/types.ts:97-98`), ring of 20 hydrated from and persisted to the chat blob (`src/runtime/extras.ts:246`); no truncation found by grep. Every `saveMetadata` re-uploads that ballast (each prompt embeds a chat window), on top of the 400 KB history budget V11 measured. Fit: truncation alone strains nothing; a localforage home strains invariant 13 (a fourth, device-local home) — acceptable only for debug data that may be lost, never for state. `so-journal follow` / J-suite readers of `audit.prompt` must switch to the full copy. Also applies to `extras.stagecraft.lastPass` prompt/raw.

**6. Hidden-message reconciliation.** What: at read/boundary time, detect provenance rows whose `messageId` now has `is_system === true` and quarantine them (`source-hidden` or reuse `source-removed`), reversible on unhide. Evidence: their Hide node calls `hideChatMessageRange` (`config.ts:84-86`), which flips `is_system` and saves **without emitting any event** (`chats.js:147-169`). Ours: the read window drops `is_system` messages (`src/extraction/chatWindow.ts:8`) but quarantine happens only on rollback (`src/memory/stores.ts:109-115`) — so a fact read from a message the player later excluded from prompts keeps steering replies. Same exposure from ST's own eye toggle, `/hide`, and Presence. Fit: a new validity value is a persisted shape change (invariant 13: blob bump + migration); rollback ≡ replay (11) is unaffected because hide is not a rollback. Value 2: niche, but it is a silent-correctness gap of the kind plan 05 exists for.

**7. Native json_schema for JSON passes.** What: optional `overridePayload.json_schema` on the copilot/wizard proposal call (`src/copilot/parse.ts:495,515` parses free JSON today, with a repair pass). Theirs: `api.ts:193-208`; host parses the content for chat completion (`custom-request.js:489-491`). Fit: no invariant issue, but user memory records that llama.cpp ignores `json_schema` when ST also sends a grammar — ship only as a measured, opt-in toggle; never for the line-parsed extraction grammar.

**8. Anti-pattern: coercing host ids.** `z.coerce.number()` turns `null`/`""` into `0` (`flow-types.ts:20,40,44…`) — exactly the V4 defect (`Number(null) === 0` rewound stories to boundary 0). Ours is already right (`hostMessageId`, `src/runtime/turnBridge.ts:14-19`). Take-away: if any future schema library enters `src/`, forbid coerce on host ids in review.

## Patterns to copy / anti-patterns to avoid
Copy:
- One `AbortController` per unit of work, passed all the way to the host request (idea 1).
- Idempotent teardown-then-register for everything bound to host (`FlowRunner.ts:243-350`) — every listener/command/DOM button tracked so re-init never doubles.
- Stale-event guard in the UI store keyed by run id (`flowRunStore.ts:43,49,60`).
- Bounded, truncated, device-local debug history with quota back-off (idea 5).
- Per-node versioned migrations that can **rewire edges** when an output is renamed (`migrations.ts:44-57`) — a model for future format-2 changes to gates/effects, where we now rely on parse-time alias normalization.
- Refuse to register invalid artifacts rather than run them partially (matches our R9 "never partially inserted").

Avoid:
- `z.coerce.number()` on host ids (idea 8).
- Static relative imports of host internals (`config.ts:1-5` → `../../../../../script.js`) — ties the bundle to install depth and bypasses a seam; ours goes through `stHost/modules.ts` dynamic imports.
- Top-level runs are fire-and-forget with results only via toasts (`FlowRunner.ts:390-398`) — nothing an author can audit later except the local history.
- A second automation extension posting, editing, deleting or hiding messages drives our TurnBridge (boundaries/rollbacks) and read window. Add Flowchart-style automation to the coexistence list next to Stepped Thinking/Presence; a turn-types check with a scripted `/sendas` + `/hide` run would cover it.
- User-editable LLM prompt templates in settings: fine for a toolkit, wrong for us — our floors/goldens are calibrated on fixed prompts.

## ST host facts learned
- `ConnectionManagerRequestService.sendRequest` accepts `custom.signal` and forwards it to both chat- and text-completion `processRequest` (`scripts/extensions/shared.js:416,424,463,481`; used by theirs via utils-lib `generateRequest`, `api.ts:121-127`). **CONTRADICTS** `src/runtime/runOwner.ts:61` ("takes no signal (shared.js:423)").
- `sendRequest` wraps every failure, abort included, as `Error('API request failed', {cause})` (`shared.js:487`) → detect abort through `cause`.
- `overridePayload.json_schema` is spread into the request, and for chat completion the returned content is `JSON.parse`d by the host (`shared.js:460`, `scripts/custom-request.js:489-491`).
- `messageTemplate` is the **live** `#message_template .mes` node, cloned per render (`script.js:448,2618`); `.extraMesButtons` lives in it (`index.html:7414`). Buttons prepended there appear on messages rendered afterwards (theirs `MessageToolbarTriggerNode/definition.ts:42-53`).
- `hideChatMessageRange(start,end,unhide)` sets `message.is_system`, updates the DOM attr, `saveChatConditional()` — **no event emitted** (`scripts/chats.js:147-169`).
- `globalThis.SillyTavern = { libs, getContext }` (`script.js:293-296`); `libs.localforage` exported (`lib.js:89,117`) — IndexedDB storage without touching settings or chat files (theirs `FlowRunner.ts:38,90`).
- Slash commands unregister by `delete SlashCommandParser.commands[name]` (static map, `scripts/slash-commands/SlashCommandParser.js:44`; theirs `FlowRunner.ts:252`).
- Wand menu container `#extensionsMenu`; QR bar `#qr--bar` / `#qr--popout .qr--body` (theirs `MenuTriggerNode/definition.ts:35`, `QuickReplyTriggerNode/definition.ts:36`) — not re-verified in host source.
- Their event param table (`flow-types.ts`) matches ours on `GENERATION_STARTED (type, options, dryRun)` and `MESSAGE_RECEIVED/CHARACTER_MESSAGE_RENDERED (messageId, type)`; no contradiction with our gotchas beyond the coerce issue.

## Verdict
Relevance **medium**. Its product (visual automation) is out of SO scope, but the code surfaces one real host fact we have wrong. **Take idea 1**: `sendRequest` takes `custom.signal`. Wiring the epoch signal we already mint into our memory-model calls lets a chat switch or rollback actually stop the GPU, instead of letting the work finish and discarding it at the write edge. It is a small change, fits the existing ownership design, and should also fix the comment in `runOwner.ts`. Secondary: gate trace + Studio dry-run (ideas 3/4) for author debugging, and per-message flagging (idea 2) for the human-eval sessions still outstanding.
