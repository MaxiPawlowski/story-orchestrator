## What it is
A floating, draggable OOC assistant window with its own chat sessions per ST chat. The user asks anything about the running roleplay: analysis, plot twists, continuity. The model can emit fenced proposal blocks (`lorebook-changes`, `character-changes`/`character-create`, `chat-changes`, `memory-update`), which render as review cards with a diff and are applied to real ST assets on click. v2.8 added a text-based tool loop (search chat, search lorebook, get char info, ask user) and scoped "Human" memories. No background calls: it only calls the model when the user presses Send (post.md follow-up 2026-04-22 17:10).

## How it works
- **LLM call**: `ConnectionManagerRequestService.sendRequest(profileId, messages, maxTokens, {stream, signal, extractData:false, includePreset:true})` when a profile is chosen. Otherwise it falls back to `ChatCompletionService`/`TextCompletionService.processRequest` with the main API's preset (`index.js:14410-14530`). Streaming failure retries non-streaming (`:14506-14550`).
- **Global fetch monkey-patch per request**: `origFetch = window.fetch`. The patched fetch rewrites the JSON body of any `/generate` or `/caption-image` request: it drops `reasoning_effort:auto`, maps min/max to low/high, and strips `messages[].name` for GLM. `finally { window.fetch = origFetch }` (`:14449-14485`, `:14555-14557`). The patch covers every extension's request made during a Copilot generation, which can run for minutes when streaming or in the tool loop.
- **Prompt assembly**: XML-wrapped sections (`system_prompt`, `character_information`, `lorebook_context`, `persistent_memory`, `summary_context`, `lorebook_management`, `chat_messages_editing`, `tool_calls_system`, …; known-key list `:15871`). Toggles cover the card, persona, AN and system prompt. The last N messages come from a CTX slider, or from a hand-picked index list (`pickedChatIndices`, `:6640-6647`). It reads Summaryception's `chatMetadata.summaryception.layers` directly (`:13897-13916`). A raw payload inspector shows the formatted/JSON request.
- **Lorebook context**: it resolves the active books itself (global `selected_world_info`, the card's `extensions.world`, `world_info.charLore[].extraBooks`, the chat book `chatMetadata.world_info`, the persona book; `:2309-2342`). Its keyword scan is its own substring/regex match over recent messages (`:2376-2395`), not ST's activation. Per-entry always/never overrides are keyed `${book}_${comment}` (`:2397-2404`). Cache has a 30 s TTL and is evicted on `WORLDINFO_UPDATED`/`WORLDINFO_SETTINGS_UPDATED` (`:2151-2173`).
- **Proposal protocol**: fenced JSON parsed with strict → `_repairJSON` → per-line quote-escape fallbacks (`parseLBChangesFromText` `:2617-2648`). LB actions are `add|edit|patch|prepend|append|delete`. `patch` anchors are `"first 3 words || last 3 words"` (prompt `:42-80`), the same boundary syntax as our curator. Apply order in `applySearchReplaceToField` (`:1133-1290`): exact substring, then `||`/`...` split with **tokenized sliding-window Levenshtein** (window ±1 token, per-token similarity, prefix match = 0.85, threshold 0.72, punctuation re-attached at the seams), then whole-query fuzzy. A failed match logs `LB_PATCH_FUZZY_MATCH_FAILED` and skips the op. `add` of an existing title silently becomes `edit`. `add` with no triggers becomes `constant:true` (`:3838-3860`). A book that is not active gets **created and bound to the character** by pushing into `world_info.charLore` and calling `saveWorldInfoSettings` (`bindNewLorebookToCharacter` `:2657-2720`). Writes go through `ctx.saveWorldInfo` + `reloadWorldInfoEditor` (`:2267-2300`).
- **Decision feedback**: every accept/reject/dismiss is appended to the Copilot session as a system note ("ACCEPTED ✎ PATCH "X" in `Book`") so the next proposal knows (`logLBHistoryChanges` `:3788-3806`). After a decision the proposal block is stripped from history to save tokens (prompt `:47-49`, `stripLBChangesBlock` `:2650`).
- **Chat edits**: `replace|overwrite|prepend|append|bulk_replace|regex|delete|add|hide|unhide|rename_chat` (`:6657-6740`). Edits mutate `msg.mes`, then `ctx.saveChat()` + emit `MESSAGE_UPDATED(idx)` (`:6749-6759`). `hide`/`unhide` call `/hide a-b` (`:6844-6858`). `add` **splices a message into `ctx.chat` mid-array and saves, emitting nothing** (`:6865-6882`). `delete` does `msgs.splice(idx,1)` **and then** `ctx.deleteMessage(idx)` (`:6979-6981`). ST's `deleteMessage` splices again (script.js:1680-1685), so the message after the target is deleted too. At the end it emits a synthetic `CHAT_CHANGED` + `printMessages()` (`_refreshSTChatDOM` `:6768-6775`, called `:7016`).
- **Character edits**: `/api/characters/merge-attributes`, `/edit-attribute`, `/rename` (+ `/rename-char`), `/create` (`:5491`, `:5554`, `:5666`, `:5765`). AN edits write `chatMetadata.note_prompt` + `saveMetadata` directly (`:5620-5622`). A name in a card-change block is resolved by exact → case-insensitive → substring → single-candidate → Levenshtein ≤2 (`resolveCharacterByName` `:5184-5216`). Literal card/persona names are rewritten to `{{char}}`/`{{user}}` before apply (`normalizeCharNamesInBlock` `:1114-1131`).
- **Tool loop** (model-agnostic, no ST function calling): the model emits ```` ```tool_call {"name","input"}``` ```` (`:286-297`). `parseToolCallsFromText` (`:8492`) runs each tool. Results come back as a user turn `<tool_results>…</tool_results> CONTINUE your response…`, for up to `toolsMaxRounds` (default 5) rounds (`:14763-14850`). `ask_user` pauses the loop for a user answer (streaming only).
- **Persistence**: sessions live in a **sidecar user file** `copilot_sess_<ts>_<rnd>.json` via `/api/files/upload` (base64) and are read from `/user/files/<id>` (`:1614-1670`). `chatMetadata.st_copilot = {format:'v4', file_id, chat_id}` is only a pointer. On load a `chat_id` mismatch means **branch detected**: the file is copied to a new id and the pointer is re-stamped (`:1705-1720`). An unparseable file keeps the broken file on disk, starts fresh, and shows a 15 s toast (`:1748-1765`). Debounced saves are flushed on `beforeunload` with `keepalive` (`:1633-1638`). Stats (messages, regens, LB edits, token in/out) are kept per global/char/chat/day in extension settings (`recordStat` `:3229-3247`). Window position is kept in `localStorage`.
- **Events**: `CHAT_CHANGED`, `CHARACTER_SELECTED` (reload session), `CONNECTION_PROFILE_*` (refresh lists), and `MESSAGE_*` only for resizing the CTX slider (`:16856-16895`). **There is no mutation handling**, because nothing it holds is derived from specific messages.

## Overlap with Story Orchestrator
- **OOC assistant**: theirs is a free-form Q&A with the whole value in "ask anything". Ours is fixed-prompt author tooling: Driver Suggest/Report (`src/copilot/authoring.ts:63-69`, `src/copilot/prompts.ts:130`) plus the wizard interview (`src/wizard/interview.ts`). We have no free-form "ask" (idea 5). Our answers could be grounded in typed state (unmet gates, reachable qualities, canon), which they cannot do.
- **Lorebook proposals**: same `first || last` anchor. Ours (`src/stagecraft/proposal.ts:30`) is scoped to `stagecraft.lorebooks`, boundary-applied, journaled, revertible, and write-edge re-previewed with `externally-edited` detection (`src/runtime/coordinators/stagecraftCoordinator.ts:284-346`). Theirs writes any active book immediately, has no revert, and creates or binds books. Ours is strictly safer. Theirs is more tolerant in matching (idea 4) and remembers decisions (idea 3).
- **Context transparency**: their raw payload inspector ≈ our Payload tab + next-turn preview (`src/runtime/nextTurn.ts:76`). Ours reads what ST actually holds (`readInjectedPromptBlocks`). Their "in context" badge comes from their own keyword scan, not ST's activation, so ours is more honest.
- **Card creation**: both create via `/api/characters/create`. Ours is create-only by code (`src/wizard/provisioning.ts:25`). Theirs also edits and renames existing cards and personas, which is out of scope for us (baseline §4).
- **Chat editing / message hiding**: we have none and should not add any (baseline §4). What matters is that their edits hit our TurnBridge (ideas 2, 7).
- **Model routing**: both use a Connection Manager profile. Neither overlays a preset per pass.

**1. Branch = fork.** ST's `saveChat` merges `withMetadata` over the live `chat_metadata` (ST `public/script.js:7406`). A branch or checkpoint therefore carries our whole blob plus `{main_chat, integrity}` (`public/scripts/bookmarks.js:201`, `:284`). Since V5, a blob stamped for another chat reads as "no story selected", and only an explicit select adopts it (`src/runtime/persistence.ts:22-32`, `:87-93`). Adoption keeps the parent's latest state, including boundaries past the branch's last message. Grep found no hydrate check against a shorter chat (verify). So a player who branches silently loses the story, and re-selecting brings back a future that never happened in this branch. Their evidence: a stamp mismatch is treated as a branch and copied into a fresh file (`index.js:1705-1720`). Our fix would recognise `chat_metadata.main_chat === stampedFor` (plus a fresh `integrity`) as a fork: adopt, then `rollbackFromMessage(chat.length)` through the existing `runRollback` path. That reuses the E1 horizon notice when the branch point is older than 200 boundaries, and journals `branch-adopted`. Fit: inv. 11 (rollback ≡ replay does the work), 12 (the pin travels with the copy), 13 (no blob version bump needed). The one question is whether to do it automatically or show a one-click notice. Auto is safe because `main_chat` is written by ST, not by a peer.

**2. Save watcher vs fetch-swapping peers.** `installSaveWatcher` wraps `globalThis.fetch` lazily on the first `observeNextSave` (`src/services/stHost/persistence.ts:57-73`, `:80`) and sets `installed = true` for good. Copilot saves `window.fetch`, swaps in its own wrapper, and restores the saved one in `finally` (`index.js:14449`, `:14556`). If our first save lands during a Copilot generation (open the page, ask Copilot, the story commits a boundary), our wrapper sits on top of theirs and their restore removes it. Every later observation then times out as `unconfirmed`. `hasUnsavedChanges` goes sticky, and `withLedger` refuses host effects with `PENDING_NOT_SAVED` for the rest of the page. Our fix: install at `startRuntime`, tag our wrapper (`fetch.__soSaveWatcher`), and have `observeNextSave` re-wrap when the tag is gone. Add a jest case that swaps and restores fetch around an install. Fit: inv. 16/17 (evidence stays honest); `stHost/` only.

**3. Declined-op memory.** Their proposer sees every accept/reject as a history line (`index.js:3788-3806`). Our curator prompt carries scope, canon and entries but no history (`src/stagecraft/prompt.ts:8-50`, `CuratorScope` `src/stagecraft/types.ts:53`). Nothing in `stagecraftCoordinator.ts` compares a new op with a rejected one (only `setOpDecision` `:214`). Every P4 pass can therefore re-propose what the author just declined. Proposed: (a) deterministic, drop an op whose `opTargetKey`+kind+normalized text equals a rejected record in the ring since the last checkpoint change, logged as `dropped`; (b) optionally list declined titles in the prompt. (a) alone is code-owned and testable. Fit: inv. 6 unchanged (still proposal-only).

**4. Fuzzy patch anchor.** Our `findSpan` only forgives whitespace and case (`src/stagecraft/proposal.ts:13-20`). The comment at `:5-6` records small models shortening anchors. Theirs: exact first, then token-window Levenshtein ≥0.72 per side (`index.js:1156-1285`). Proposed: keep exact as the first try. On a miss, fall back to a token-window match, return `{start,end,score}`, and have `previewCuratorOp` show the matched span, so the author approves the real text. Only `review` mode may take a fuzzy match; `auto` stays exact. Measure the acceptance lift on the plan-10 curator fixtures before shipping, and declare a floor first (plan-10 rule). Fit: inv. 6 (the write edge still re-previews against live content).

**5. Author "Ask".** Their whole product is a free-form OOC question over the story (`DEFAULT_SYSTEM_PROMPT` `index.js:12-40`). Ours only has canned Suggest/Report (`src/copilot/authoring.ts:63-69`). Proposed: one text box in the author-view DriverPanel that sends `DriverContext` (checkpoint, unmet gates, reachable qualities, canon, open arcs, recent window) plus the question to the memory profile, and returns text only. That lets an author ask "why isn't cp3 firing?" or "is Luke's secret consistent?" and get an answer grounded in the gate state. Fit: author-only (inv. 9), writes nothing (so no RunToken rows), off-path (inv. 5). Their tool loop (`:14763-14850`) is the pattern if it later needs retrieval (search chat by quality). Keep that read-only.

**6. Cost/latency ledger.** They count token in/out per chat/day (`recordStat` `index.js:3229-3247`, counting via `getTokenCountAsync` → `/api/tokencount` → len/3.5, `:14180-14225`). We run 6+ off-path pass kinds on one profile. Audits keep prompt + raw response but no duration or size aggregate (grep for `durationMs|latency` in `src/extraction`, `src/runtime/coordinators`: none). Only the judge carries `usage` (`src/judge/types.ts:62`). The plan-11 cost/latency report is unrun. Proposed: record `{pass, chars in/out, ms, ok}` per call in a capped ring, derive per-chat totals at read time the way the journal does, show them in the author Scheduler tab and "Copy for a bug report". Fit: inv. 18 (a snapshot slice). No persistence beyond a capped ring.

**7. Interop rows.** A Copilot chat edit exercises four shapes our turn-types check lacks. (a) Synthetic `CHAT_CHANGED` with no chat switch (`index.js:6768-6775`): our `onChatChanged` resets and re-hydrates (`src/runtime/turnBridge.ts:149-152`), dropping pending queue writes. (b) `bulk_replace` over N old messages sends N `MESSAGE_UPDATED`, and each one rolls back (`turnBridge.ts:57`, `:159-167`). A rename typo fix 10 messages back rewinds 10 messages of story. (c) Mid-chat `splice` insert with no event (`index.js:6865-6882`) shifts every later index under our boundary logs. (d) `/hide` emits nothing (ST `public/scripts/chats.js:147-169`), yet `chatWindow` drops `is_system`. Add these rows to `scripts/debug/so-turn-types-check.mts` next to the CYOA foreign-message probe (`cyoa-extension.md` idea 3) and decide each outcome explicitly. (b) is arguably correct (an edit is history). (c) needs at least a journaled "chat shifted under the story" detection.

**8. Card macro normalization.** They rewrite literal names to `{{char}}`/`{{user}}` in card blocks (`index.js:1114-1131`). Our wizard's `createCharacterCard` op carries free text (`src/copilot/prompts.ts:48`), with no `{{char}}`/`{{user}}` anywhere in `src/copilot`/`src/wizard` (grep). A first message that hardcodes the author's persona name breaks for any other persona. Proposed: a pure transform inside provisioning (own name → `{{char}}`, `requirements.personas` names → `{{user}}`), shown on the review card. Fit: inv. 8 (still create-only, still reviewed).

**9. Director name tolerance.** `matchCandidate` is exact after lowercasing (`src/talk/parse.ts:12-16`), so `SPEAKER: Luke` for a card named "Luke Skywalker" returns null and falls back to rules. Their cascade is exact → case → substring → single candidate → Levenshtein ≤2 (`index.js:5184-5216`). Take only case → unique-substring. Levenshtein risks picking a wrong but similar member. Record the fallback reason in the decisions ring.

## Patterns to copy / anti-patterns to avoid
Copy:
- Decision feedback to the proposer (`index.js:3788-3806`), done code-side (idea 3).
- Stamp mismatch as a branch signal (`:1705-1720`). With ST's `main_chat` we can do better (idea 1).
- Corrupt-state recovery that keeps the broken artifact and says so loudly (`:1748-1765`). This matches our "refuse, don't destroy" V5 rule.
- A model-agnostic tool loop over fenced blocks with bounded rounds (`:8492`, `:14763-14850`), if an author Q&A ever needs retrieval. Never give it write tools.
- LB `add` of an existing title → `edit` (`:3838-3846`). This is useful input for the F5 curator-create seed (baseline §3B).

Avoid (each seen in their code):
- **Global `window.fetch` swap-and-restore around a request** (`:14449-14485`, `:14556`). It rewrites other extensions' generate bodies and erases any wrapper installed meanwhile (idea 2).
- **Direct `ctx.chat` splice + `ctx.deleteMessage`**: a double delete (`:6979-6981`, ST `script.js:1680-1699`). Also a silent mid-chat insert (`:6865-6882`) and a synthetic `CHAT_CHANGED` (`:6768-6775`). SO must never do any of these. We should expect peers to.
- **Auto-binding books to a character by mutating `world_info.charLore`** + `saveWorldInfoSettings` (`:2657-2716`). Our WI rule already forbids anything beyond the per-chat mirror binding.
- **Untriggered `add` → `constant:true`** (`:3855-3860`): a silent per-turn token cost.
- **An "in context" indicator computed by its own keyword scan** (`:2376-2395`) instead of ST's activation. It looks authoritative and can be wrong. Our next-turn preview reads ST's blocks; keep it that way.
- **Sidecar session file via `/api/files/upload`** (`:1614-1670`). It keeps chat files small but splits state from the chat (branches need a copy step, restores need two files). For SO it would defeat save evidence, which reads the chat file back (`src/services/stHost/persistence.ts:107`). Considered, not recommended, despite the 201 KB history blob.
- A 17k-line single-file bundle with `typeof ctx.x === 'function' ? … : window.x` fallbacks everywhere. It is untestable, which is the contrast with our `stHost/` seams.

## ST host facts learned
- `saveChat({withMetadata})` merges over the live metadata: `{ ...chat_metadata, ...withMetadata }` (ST `public/script.js:7406`). Branches and checkpoints are created with `{main_chat, integrity: uuidv4()}` (`public/scripts/bookmarks.js:201`, `:284`), so **every branch inherits `chat_metadata.story_orchestrator` stamped for the parent**. Not in gotchas; drives idea 1.
- `/hide`/`/unhide` → `hideChatMessageRange` flips `is_system`, updates the DOM, and calls `saveChatConditional()` **with no event** (`public/scripts/chats.js:147-169`). Not in gotchas.
- `deleteMessage(id)` splices `chat` itself and emits `MESSAGE_DELETED(chat.length)` (`public/script.js:1680-1699`). A caller that also splices deletes two messages (their `index.js:6979-6981`). Consistent with the existing `mcp-model-context-protocol.md` finding that the payload is the post-deletion length, not the deleted id. That report flags the tail-rewind consequence for `turnBridge.ts:159-167`, and it is still unverified live.
- World Info `_save` POSTs `/api/worldinfo/edit`, then emits `WORLDINFO_UPDATED(name, data)` (`public/scripts/world-info.js:4151-4160`); `WORLDINFO_SETTINGS_UPDATED` fires on selection changes (`:5842`, `:6228`). Our `src/services/stHost/events.ts:30` types `WORLDINFO_UPDATED` as `[]` (payload ignored; minor type drift, **contradicts our vendored type**). They use it to evict their book cache (`index.js:2158-2163`).
- Context exposes `saveChat` = `saveChatConditional`, `deleteMessage`, `printMessages`, `saveWorldInfo`, `reloadWorldInfoEditor` (= `reloadEditor`), `updateWorldInfoList` (ST `public/scripts/st-context.js:142`, `:155`, `:278-281`, `:290`).
- `ConnectionManagerRequestService.getSupportedProfiles()` is a static method (`public/scripts/extensions/shared.js:530`). They use it to list profiles (`index.js:983`, `:14410-14413`).
- Character endpoints exist: `/api/characters/rename` (`src/endpoints/characters.js:1053`), `/edit-attribute` (`:1193`), `/merge-attributes` (`:1328`). User files: `/api/files/upload` (base64 `data`; `src/endpoints/files.js:28`), readable at `/user/files/<name>` (their `index.js:1616-1660`).
- A card's lorebooks are the primary `data.extensions.world` plus `world_info.charLore[{name: <chara filename>, extraBooks}]`; the chat book is `chat_metadata.world_info`; the persona book is `power_user.persona_description_lorebook` (their `index.js:2309-2342`). A requirement check that only reads global selection (ours: `requirements.lorebooks` vs globally selected) misses books that are active through these routes. This is by design for us, but a player could see "missing lorebook" while the book is actually active via the character.

## Verdict
Relevance **medium**. It is a player-side OOC assistant with live-asset editing, mostly outside our scope. We already do its lorebook proposals in a safer form. What it teaches is the host: branches inherit our blob (idea 1), and fetch-swapping peers can silently disable save evidence (idea 2). **The one thing worth taking: treat a branch/checkpoint chat (`main_chat` + parent stamp) as a fork rolled back to the branch point**, so a player's branch keeps the story instead of losing it. Cheap runners-up: declined-op memory for the curator (3), and the eager, self-healing save watcher (2).
