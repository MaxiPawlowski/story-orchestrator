## What it is
Visual stat cards for RP ("dating sim" by default; TTRPG/disposition/tactical packs). The **main model** is told (via the `{{sim_tracker}}` macro placed in the system prompt) to end every reply with a fenced ```` ```sim ```` JSON/YAML block of `worldData` + per-character stats; the extension hides the block and renders it as Handlebars HTML cards (under the message, or in left/right/top/bottom "positioned" sidebars). Optional **secondary LLM** fills in a block after the reply when the main model omitted it. Template packs (HTML + prompt + field schema + optional JS "template logic") are shareable JSON presets. Inline "display add-ons" let the model embed `[[D=phone, DATA={...}]]` widgets in narrative text.

## How it works
- **Prompt side.** `MacrosParser.registerMacro("sim_tracker")` `index.js:544` returns the pack's system prompt with a format example generated from the field schema (`{{sim_format}}` expanded by hand, `index.js:429-542`, because "MacrosParser doesn't handle nested macros" `index.js:550,659`); also `{{last_sim_stats}}` `:690` (module variable holding the last block), `{{sim_displays}}`/`{{sim_display_format}}` `:766,:868` (catalogue of inline widgets). Hard caps / band labels live only in prompt text (default pack `tracker-card-templates/dating-card-template.json` `sysPrompt`: "HARD CAP at 200", "Status strings are CONCRETE").
- **Context pruning (dead).** Manifest `generate_interceptor: simTrackerGenInterceptor` `manifest.json:13`; `index.js:107-214` `structuredClone`s the chat, strips sim blocks older than the last N assistant replies + `filterSimBlocksInPrompt` `utils.js:106`, and **returns** the clone `index.js:213`. ST ignores the return value (`scripts/extensions.js:2037`), so none of this reaches the prompt.
- **Render.** `CHARACTER_MESSAGE_RENDERED` `index.js:1345` → `renderTracker` `renderer.js:1383`: regex the block out of `message.mes`, `parseTrackerData` `formatUtils.js:222` (JSON, else a hand-rolled YAML parser that splits on `''` — characters, not lines, `formatUtils.js:30`, i.e. broken), `+N` → `N` coercion `formatUtils.js:214`, re-`innerHTML` the message via ST `messageFormatting` `renderer.js:1467`, Handlebars cards appended. Stat deltas (`affectionChange` …) computed against the previous block for a **hard-coded list** of stat names `renderer.js:708`. MutationObserver hides `code[class*=sim]` during streaming and shows "Preparing new tracker cards…" `index.js:306-396`.
- **Secondary LLM.** `GENERATION_ENDED` `index.js:1541`: if the last rendered char message has no block, `generateTrackerWithSecondaryLLM` `secondaryLLM.js:648` builds one user-message prompt = pack sysPrompt + **"Previous tracker state:"** (block from the message before) + last N messages with sim blocks/HTML stripped `secondaryLLM.js:543-596, 797-807`, calls the provider **directly from the browser** (OpenAI/Anthropic w/ `anthropic-dangerous-direct-browser-access`/OpenRouter/Google/Chutes/custom, own SSE parser) with keys pulled from ST secrets via `POST /api/secrets/find` `secondaryLLM.js:80-101,159-469`; then **appends the block to `message.mes` and `saveChat()`** `index.js:1597-1603`. `/sst-regen` `:941` does the same on demand; `/sst-add` `:1175` appends an empty skeleton block and calls `Generate("continue")` `:1300`.
- **Persistence.** State lives only in message text (the fenced block). Settings/presets in `extension_settings` (`settingsHandler.js:3,120`). Nothing in `chat_metadata`. On `CHAT_CHANGED` it rewrites every message, wrapping blocks in `<div style="display: none;">` and saves the chat `index.js:1405-1484`.
- **Mutations.** Swipe handler subscribes to `event_types.MESSAGE_SWIPE` `index.js:1527` — no such key (ST has `MESSAGE_SWIPED`, `scripts/events.js:7`), so it never fires; its helper `updateLastSimStatsOnRegenerateOrSwipe` `utils.js:65-103` has a double-escaped regex (`[\\\\s\\\\S]` `utils.js:80`) and a line of code swallowed into a comment (`utils.js:84`), so it can only return null. Edits re-render the card `index.js:1514`. No rollback concept: state is "whatever the newest block says".
- **Other hooks.** `MESSAGE_UPDATED`/`MORE_MESSAGES_LOADED` full refresh `index.js:1502-1512`; Lumiverse (third-party React chat renderer) dual-path DOM bridge `domBridge.js:7-80` + `lumiverse:content-rendered` custom event `index.js:1388`. Template "logic" `<script type="text/x-handlebars-template-logic">` extracted from pack HTML `templating.js:634` and run with `new Function('data', …)` `renderer.js:633-634`. Inline widgets: regex over rendered `innerHTML`, LLM `DATA` loosely JSON-ified (`inlineTemplates.js:63-81`), rendered and written back with an unescaped `data-template="${templateName}"` attribute `inlineTemplates.js:216-223`.

## Overlap with Story Orchestrator
- **State capture**: theirs = main model self-reports every turn (context + latency cost, format drift) or a secondary model with no evidence, scope, typing or rollback. Ours = off-path typed shared read, closed vocabulary, evidence span, boundary-drained queue, rollback ≡ replay (`src/extraction/sharedRead.ts:87`, `src/engine/applyQueue.ts:30`, `src/runtime/rollback.ts:35`). We are strictly better on correctness.
- **Previous state in the extractor prompt**: they send it (`secondaryLLM.js:797-801`); our shared read does **not** show current blackboard values — `renderSharedReadPrompt` `src/extraction/contract.ts:31-54` renders key/type/rubric/allowed only; blackboard feeds scope only (`src/extraction/scope.ts:22`). Already raised in `blazetracker-…md` #2.
- **Hard caps**: theirs prompt-only; ours: no `min`/`max` on `Quality` either (`src/engine/schema.ts:53`), only `monotonic` (`src/engine/blackboard.ts:62`). Already raised in `bettersimtracker-…md` #3.
- **Player-visible stats**: their whole product; ours deliberately none (baseline §4; `src/runtime/narrative.ts` has no blackboard read; values are author-view/macros only).
- **Per-character stat sets**: theirs `characters[]` with one schema; ours: global quality keys + ledger per entity, one `ledger_binding {entity, field}` per quality (`src/engine/schema.ts:32`).
- **Shareable packs**: theirs executable (JS in JSON); ours data-only story records (`src/studio/io.ts:6`).
- **Swipe/edit handling, ownership, save evidence, secrets**: ours far ahead (TurnBridge, RunToken, save evidence, judge key server-side only).

## Ideas for v2.4

| # | idea | kind | our area | our state | value | effort |
|---|---|---|---|---|---|---|
| 1 | Transcript hygiene for memory-LLM windows: strip fenced machine blocks + hidden/structural HTML, keep them out of evidence | host-integration | extraction | absent | 3 | S |
| 2 | Signed numeric values: stop reporting `value=+1` as generic "invalid value"; optionally a relative op resolved at drain | enhancement | extraction / engine | partial | 3 | S (reason) / M (op) |
| 3 | Opt-in player-visible qualities + direction chip at boundary | new-feature | player-ui | absent | 3 | M |
| 4 | Per-member quality family (`per_member` → `key@rosterId`) | new-feature | engine / studio / extraction | absent | 2 | L |
| 5 | Guard: every subscribed host event key must exist in ST `event_types` | testing | host | partial | 2 | S |
| 6 | Anti-pattern: interceptor that returns a modified clone | anti-pattern | host / talk | present (we avoid it) | 2 | S |
| 7 | Anti-pattern: off-path writer that edits message text / pulls provider keys into the page | anti-pattern | host / extraction | present (we avoid it) | 2 | S |

**1. Transcript hygiene.** `getChatWindow` passes raw `mes` (`src/extraction/chatWindow.ts:10`) to every pass (shared read, scene/epistemic/curator, `memorize:full`). Any chat that also runs SimTracker or one of the "status HTML" presets the author's post complains about carries multi-hundred-token JSON/HTML blocks — including ones wrapped `display:none` the player never sees (`index.js:1466`) — into our prompts, and our evidence check (`src/extraction/evidence.ts:38` `evidenceInWindow`) will accept a quote taken from inside a machine block (`"affection": 120` as evidence for a trust delta). They solved the same problem for their own reader (`secondaryLLM.js:571-585`: drop fenced blocks, strip structural tags). Proposal: one pure `sanitizeWindowText` in `extraction/` (drop fenced code blocks, `<details>`/`<div>`/`<script>`/`<style>` blocks, collapse tags) applied in `readMessage`, window keeps `raw` for audit display. Optional second step: apply ST's prompt-placement regex (`getRegexedString(..., {isPrompt:true})`, `script.js:4505`) through a new `stHost` seam so users' own "hide from prompt" regex applies to us too. Fits inv 4 (tightens evidence), eases seed D (request size). No conflict.

**2. Signed numeric values.** Models write `+5` for "went up by 5". SimTracker silently coerces `+5` → absolute `5` (`formatUtils.js:214`) — a corruption. Ours rejects it as generic `invalid value` (`src/extraction/parse.ts:118-129`, `parseJsonLiteral("+1")` fails), which is safe but indistinguishable in audits/live-suite from a genuinely wrong value. Cheap half: a distinct reject reason `relative value` so we can measure how often it happens. Full half (pairs with blazetracker #2 "show current value"): `DELTA q=noise value=+1` resolved **at drain** against the blackboard value then current (`src/engine/applyQueue.ts:30`), never at parse — two relative deltas in one window must stack on the drained base, not both on a stale one; replay stays deterministic because the queue re-drains (inv 3, 11). Needs `min`/`max` (bettersimtracker #3) to be safe. Evidence need unchanged. Real fixtures need it: `test/fixtures/branching.story.json:7` `noise` is an extractor `int` "How much noise has been made?" with no way for the reader to know the running total.

**3. Opt-in player-visible qualities.** The product the 992-message thread is about: players like seeing a relationship meter move. Ours shows none by design (baseline §4, inv 9). Shape that keeps the split: authored per quality `player_display: {label, as: "level"|"value"}` (default absent = hidden); HUD/Overview show current level name (from `read_as` rubric levels, `src/engine/qualityRead.ts:3`) and an up/down chip at the committed boundary that changed it — never gate operators, thresholds, the next checkpoint, or pending (unapplied) deltas. `assert-player-clean` gains "only declared qualities render". Conflict: baseline §4 is a scope decision, so this needs a user call; a displayed value can hint gate proximity, so the Studio should warn when a displayed quality appears in a gate (new diagnostic with consequence). Snapshot-only read (inv 18).

**4. Per-member quality family.** Their schema is "same fields × each present character" (`index.js:503-514`). For a group dating-sim or party-loyalty story, SO authors must hand-declare `trust_luke`, `trust_arin`, … and the ledger can bind one entity field per quality (`src/engine/schema.ts:32`). A normalize-time expansion (`per_member: true` → one quality per roster id, gates reference `trust@luke`) keeps the engine pure and the vocabulary closed, but touches validate, scope (only present members), storyDiff (roster edits add/drop keys, inv 12), Studio editors, and prompt size. Value 2: nice for a genre SO does not target yet; park unless a real story needs it.

**5. Event-key guard.** SimTracker's swipe handling is dead because `MESSAGE_SWIPE` is not an ST event (`index.js:1527` vs `scripts/events.js:7`). Ours has the same failure mode latent: `resolveEventName` falls back to the raw string when `eventTypes[key]` is missing (`src/services/stHost/events.ts:48-52`), so a typo'd or renamed key subscribes to a literal that never fires, silently. All 17 keys we use exist today (checked against `scripts/events.js`), but nothing enforces it. Add a jest guard reading ST's `events.js` when present (like `scripts/release/manifest.mjs` hashes host files) and a runtime warn + capability row when a key resolves to itself.

**6. Interceptor returns are discarded.** `runGenerationInterceptors` awaits each interceptor and only honours `abort()` (`scripts/extensions.js:2024-2049`); SimTracker's retention/pruning feature returns a clone and is therefore a no-op (`index.js:132,213`). `coreChat` entries are already shallow copies with regexed `mes` (`script.js:4501-4527`), so an interceptor that needs a prompt-only edit must mutate `chat[i].mes` in place. Ours uses `abort` only (`src/runtime/index.ts:186`). Record as a host fact for any v2.4 prompt-side feature; also note interceptors are skipped on dry runs (`script.js:4562`), so a prompt edit made there never shows in a dry-run capture.

**7. Writers that edit chat text / page-side keys.** (a) After an unowned `await`, SimTracker appends to `message.mes` and `saveChat()` (`index.js:1580-1603`) — a chat switch mid-call saves the new chat with an edited object from the old one; on every `CHAT_CHANGED` it rewrites all messages and saves (`index.js:1484,1474`), which also edits text our extraction window and evidence read. (b) It fetches provider keys into the page via `/api/secrets/find` (refused unless `allowKeysExposure`, ST `src/endpoints/secrets.js:560-569`) and calls providers straight from the browser. Both confirm existing SO rules (never write message text; RunToken per write; judge key server-side only, memory LLM via Connection Manager). No action beyond keeping them in the anti-pattern list; the coexistence consequence is covered by idea 1.

## Patterns to copy / anti-patterns to avoid
Copy:
- Reader gets the previous state + a stripped transcript (`secondaryLLM.js:559-596`) — the two inputs our shared read lacks (ideas 1, 2).
- Field schema → generated format example in the prompt (`index.js:429-542`) — same idea as our rubric-driven quality questions; nothing new.
- Placeholder text while an async artifact is pending (`index.js:358-371`) — we have the pipeline chip already (`src/runtime/pipeline.ts:47`).

Avoid:
- State stored only in message text; macro caches in a module variable (`lastSimJsonString` `index.js:104`) that nothing rolls back.
- Coercing model output toward "valid" (`+N` → `N`, unquoted keys quoted, HTML stripped then JSON-parsed `inlineTemplates.js:63-81`) without recording what was changed.
- Executable community packs: JS from imported JSON via `new Function` (`renderer.js:633`, `templating.js:634`). Any future SO shareable pack/stagecraft template stays data-only.
- Rewriting `innerHTML` of rendered messages with LLM-derived strings (`inlineTemplates.js:216-223`, unescaped attribute) after ST's sanitizer ran.
- Hard-coded stat names in generic code (`renderer.js:708`).
- Subscribing by `event_types.X` without checking X exists (`index.js:1527`).

## ST host facts learned
- `runGenerationInterceptors` ignores interceptor return values; only `abort(immediately)` propagates (`scripts/extensions.js:2033-2048`). Consistent with ours.
- Interceptors do not run on dry runs (`script.js:4562-4573`).
- `coreChat` = `chat.filter(!is_system …)`, `pop()` on swipe, then each item `{...chatItem, mes: regexed}` with prompt-placement regex applied (`script.js:4496-4527`): in-place `mes` edits in an interceptor are prompt-only; system messages (our `/comment` transition notes) never reach the main prompt.
- No `MESSAGE_SWIPE` event; it is `MESSAGE_SWIPED` (`scripts/events.js:7`). `GENERATION_AFTER_COMMANDS` exists (`scripts/events.js:22`).
- `POST /api/secrets/find` returns a secret only with `allowKeysExposure: true` or for `EXPORTABLE_KEYS` (`src/endpoints/secrets.js:560-569`).
- `getContext().saveChat` is `saveChatConditional` (`scripts/st-context.js:155`) — same function our gotchas say swallows its errors.
- Lumiverse Helper (third-party) replaces the chat DOM with React (`.lcs-message[data-mesid] > .lcs-message-content`, event `lumiverse:content-rendered`) per `domBridge.js:7-8`, `index.js:1388`. SO renders no message DOM, but the HUD mount (`src/index.tsx:582`) was never checked under it — unverified.
- Their claim "MacrosParser doesn't resolve nested macros in a macro's returned text" (`index.js:550,659`) — not verified here; this install runs the new macro engine (gotchas), so re-measure before relying on either behaviour.
- None contradicts our gotchas.

## Verdict
Relevance **medium**. Mechanically it is the design SO replaced (self-reported state in message text, no evidence/rollback, dead swipe and pruning paths), so most value is as anti-pattern evidence. Worth taking: **idea 1, transcript hygiene** — cheap, pure, stops status-block extensions (very common, per this thread) from polluting our reads and our evidence check. The product question it raises is idea 3 (opt-in player-visible qualities), which needs a user decision against baseline §4.
