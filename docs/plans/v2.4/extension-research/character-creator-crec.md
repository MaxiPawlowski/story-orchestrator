## What it is
LLM-assisted character-card authoring inside ST. Popup (icon injected into the char create/group/list panels) with one textarea per card field (name, description, personality, scenario, first_mes, mes_example, alternate greetings, plus user-defined "draft fields"). Each field is generated/continued independently via a chosen Connection Manager profile, grounded on author-selected ST data (other cards, lorebooks, persona, a chat-history slice). A second mode, "Revise sessions", is a chat with the LLM where every assistant turn returns a structured edit to the whole card (or one field) and carries a state snapshot, with per-turn diff, fork-on-edit, regenerate and "read-only discuss" mode. Output: save as new card, overwrite a loaded card, or append as a WI entry. No chat-time behaviour at all.

## How it works
- **Boot**: bails unless `ConnectionManagerRequestService` exists (`src/index.tsx:74-76`); settings via `sillytavern-utils-lib` `ExtensionSettingsManager` with a from→to migration strategy list keyed by `FORMAT_VERSION` (`src/settings.ts:23`, `:364`). Settings panel via `renderExtensionTemplateAsync('third-party/<name>','templates/settings')` (`src/index.tsx:14`); popup icon prepended into three ST containers (`src/index.tsx:35-39`).
- **Field generation** (`src/generate.ts:73` `runCharacterFieldGeneration`): Handlebars-templated prompt blocks assembled from a user-editable "main context template" (ordered list of `{promptName, role, enabled}`; `src/settings.ts` default preset: chatHistory, stDescription (a long card-writing guide, `src/constants.ts:1`), charDefinitions, lorebookDefinitions, existingFieldDefinitions, persona, outputFormatInstructions, taskDescription-as-user). Chat history is rebuilt with `sillytavern-utils-lib` `buildPrompt` for the profile's preset/context/instruct, with `ignoreCharacterFields/ignoreWorldInfo/ignoreAuthorNote` and a first/last/range message window (`src/components/MainPopup.tsx:235-275`). Lorebooks: only author-selected names, disabled entries dropped (`src/generate.ts:136-151`), rendered as comment/triggers/content (`src/constants.ts` `DEFAULT_LOREBOOK_DEFINITION`). `{{user}}`/`{{char}}` are swapped to placeholders around `substituteParams` so the generated card keeps literal macros (`src/generate.ts:242-246`); mes_example keeps literal `{{char}}/{{user}}` (`:115`).
- **Continue**: partial field text is re-sent as a trailing assistant message wrapped in the output format's opener (`<response>…` / `{"response":"…`) and the completion concatenated before parsing (`src/generate.ts:253-258`, `:269`; `src/parsers.ts:156` `getPrefilled`).
- **LLM call**: `ConnectionManagerRequestService.sendRequest(profileId, messages, maxTokens)` (`src/generate.ts:261`) for fields; revise uses the lib's `Generator.generateRequest` with `custom: {stream, signal}` + `overridePayload` (`src/request.ts:39`). Streaming is disabled whenever `json_schema` is set (`src/request.ts:23`).
- **Structured output, three modes** (`src/request.ts:89` `makeStructuredRequest`): `native` → `overridePayload.json_schema {name, strict:true, value: z.toJSONSchema(schema)}` (`:110`), accepts content already parsed or string (`:118`); `json|xml` → appends a system prompt holding the JSON schema plus an example **generated from the schema** (`src/schema-to-example.ts:46`), parses last fenced block, XML via fast-xml-parser with array/string coercion back to schema (`src/parsers.ts:14` `ensureArray`, `:47`, `:80`). All modes end in zod `safeParse` (`src/request.ts:155`).
- **Revise schema is built from live state**: `fields_to_change[].field` is a `z.enum` of the field ids that exist right now; `draft_fields_to_remove` only present when drafts exist; greetings via 1-based add/remove/change lists (`src/revise-types.ts:51-97`). Applied by a pure `calculateNewState` (`src/components/ReviseSessionChat.tsx:38`).
- **Revise session mechanics**: each assistant message stores `stateSnapshot` (`src/revise-types.ts:102-107`); the current state block is injected right before the last message of every request, not accumulated (`ReviseSessionChat.tsx:406`); after a change a hidden `isStateUpdate` system message lists only the changed fields (`:326`); diff per turn = snapshot vs previous snapshot (`:547`); editing a message forks and drops everything after it (`:584`); read-only mode routes to a plain request and never applies state (`:424`); chat history is a placeholder expanded at send time (`src/revise-prompt-builder.ts:87-94`).
- **Persistence**: sessions + revise sessions in `SillyTavern.libs.localforage` (IndexedDB, browser-local) with one-time migration from `localStorage` and a typed `{persisted, error}` save result (`src/browser-storage.ts:27`, `:41`). Nothing in `chat_metadata`.
- **Writes to ST**: `createCharacter` (`MainPopup.tsx:448`), `saveCharacter` over a loaded card (`:480`, spread of the loaded object), `applyWorldInfoEntry(add)` with uid -1 (`:863`) — all via `sillytavern-utils-lib`.
- **Mutation handling**: none needed (no chat-time state). Aborts via `AbortController` passed to the host request.
- **Tests**: vitest on parsers, storage migration, WI helpers (`src/test/*`).

## Overlap with Story Orchestrator
- Card creation: our wizard provisioning creates cards (`src/wizard/types.ts:19` `createCharacterCard`, `src/services/stHost/provisioning.ts:40`) — one JSON op per card, whole card at once, inside a story-level stage. CREC is far deeper per card (field guides, per-field generate/continue, revise chat); we are stricter (create-only enforced in `src/wizard/provisioning.ts:27-31`, never overwrite, per-op review card, asset ledger + cleanup). CREC's "Override Char" is exactly what we forbid.
- Grounding: our wizard sees only NAMES of characters/lorebooks/groups (`src/copilot/prompts.ts:75-83`); CREC feeds full content of author-picked cards/lorebooks. Theirs better for consistency with existing lore; ours better on privacy/size.
- Structured output: ours = prompted JSON + one repair pass (`src/copilot/authoring.ts:36-46`, `src/copilot/parse.ts:491`), op shapes hand-written as prompt strings (`src/copilot/prompts.ts:19-50`). No `json_schema` caller anywhere; `sendConnectionProfileRequest` always sends one user message (`src/services/stHost/connectionProfiles.ts:43-54`).
- History/undo: our Studio draft has global undo/redo (`src/studio/draft.ts:90`); wizard history is text only (`src/wizard/types.ts:70`), no per-turn snapshot/diff/fork. `ProposalReview` lists "update X" labels, no before/after text (`src/studio/components/ProposalReview.tsx:51-60`).
- Abort: ours has epoch-minted signals that reach the judge only; the test note claims the host cannot take a signal (`src/runtime/epochAbort.review.test.ts:9`) — CREC and ST source say otherwise (see host facts).

**1. Abort signal to the host.** What: pass `custom.signal` (from `RunOwner.signal()`) through `sendConnectionProfileRequest` so a chat switch/story swap/restart cancels an in-flight extraction, epistemic, canon, curator or wizard call instead of paying for a refused answer. Theirs: `src/request.ts:39` `custom: {stream, signal}` and abort handling `:27-31,54-56`. Host: `scripts/extensions/shared.js:415,424` destructures `signal` from `custom`, forwards to `processRequest` (`:463`, `:483`), which reaches `fetch` (`scripts/custom-request.js:125,152,468`). Ours: `src/services/stHost/connectionProfiles.ts:48` builds `custom` without `signal`; `src/runtime/epochAbort.review.test.ts:9` records the opposite claim ("no signal … cannot be cancelled at the host"). Fit: strengthens invariant 10 (RunToken still guards the write; abort only saves cost/latency on slow pods). Catch: ST wraps errors in `'API request failed'` (`shared.js:490`) — the caller must read `cause.name === 'AbortError'` so an abort is not logged as a failed read and does not pause extraction install-wide. Re-verify on the declared older host (ST 1.18.0) before claiming it; if absent there, gate on a capability probe.

**2. Native structured output.** What: a per-profile opt-in `native` mode for copilot/wizard stages sending `json_schema` whose `kind`/id fields are enums of what exists in the draft right now (checkpoint ids, quality ids, lorebook names), falling back to today's prompted JSON; generate the prompted example from the same schema so prompt and validator cannot drift. Theirs: `src/request.ts:89-156`, `src/revise-types.ts:51-97`, `src/schema-to-example.ts:46`. Ours: hand-written op grammar `src/copilot/prompts.ts:19-50` vs validator `src/copilot/validate.ts`; repair pass `src/copilot/authoring.ts:42`. Conflicts/traps: (a) with `json_schema` on chat completion ST returns `content` already JSON-parsed (`scripts/custom-request.js:490`) and our seam returns `""` for non-string content (`connectionProfiles.ts:51-53`) — must be fixed first; (b) memory note: llama.cpp ignores `json_schema` when ST also sends a grammar (textgen) — needs a capability probe per backend; (c) real-LLM live gate on Artemis required (invariant 20). Not for the extraction line grammar (DELTA/FACT parser is calibrated; goldens).

**3. Per-turn snapshots in the wizard.** What: store the draft hash/patch accepted per copilot turn; "show what this turn changed", "revert to before this turn", editing an author message forks (drops later turns). Theirs: `ReviseSessionChat.tsx:547` diff, `:584` fork, snapshot on message `src/revise-types.ts:105`, only-changed-fields system note `:326`. Ours: `src/wizard/types.ts:70` text history; `src/studio/draft.ts:90` global undo. Fit: Studio-local, no host writes; provisioning already applied is NOT revertible this way (create-only assets stay; say so in the UI, ledger unaffected). Wizard sessions live in extension settings (cap 8) — store diffs, not full drafts, to keep settings.json small.

**4. Word diff on proposals.** What: for `update*`/`setStoryField`/card text ops render old vs new with word diff. Theirs: `src/components/CompareFieldPopup.tsx:12` (`diffWords`) — but it builds HTML strings and injects with `dangerouslySetInnerHTML` unescaped (`:23`, `:46`), a card with `<img onerror>` executes. Ours: `ProposalReview.tsx:51-60` label only; our popup guard already bans innerHTML (`src/services/stHost/popup.test.ts:64`) — build spans as React text children. Also usable in the curator review ring (`src/components/drawer/StagecraftPanel.tsx`) for `first||last` patches. Storybook story + a11y required.

**5. Field-scoped refine on provisioning cards.** What: a "refine this field" action on `ProvisioningCard` (description / first_mes / mes_example) that sends the other fields + the story premise + a short card-writing guide, returns only that field; "continue" when truncated. Theirs: per-field task + field-specific instructions `src/generate.ts:73-120`, continue prefill `:253-269`, guide `src/constants.ts:1`. Ours: fields editable, no regenerate (`src/studio/components/ProvisioningCard.tsx:26-27`). Fit: invariant 8 intact (edits the op before apply; validation still in `wizard/provisioning.ts`). Our `st-character-authoring` skill already holds the card checklist — reuse it as the guide text. Continue-by-prefill is untested on textgen+instruct through `sendRequest` (instruct may append an output sequence after the trailing assistant message) — measure before promising it.

**6. Reference context picker.** What: author ticks specific existing cards/lorebooks to send in full to the provisioning stage, so new cast/entries match existing lore. Theirs: `src/generate.ts:122-151`, toggles `src/revise-prompt-builder.ts:78-84`. Ours: names only `src/copilot/prompts.ts:75-83`. Conflict: `docs/plans/v2.3/privacy-report.md` counts "card text is never read" as a property and flags the uncapped request size seam (baseline §3 D) — must be explicit per-item opt-in, author-only, token-budgeted, and listed in the privacy report. Value 2 because Adolion-style stories author their own cast anyway.

**7. Discuss-only turn.** What: "Ask" button: answer goes into history, no proposal parsed or offered. Theirs: `ReviseSessionChat.tsx:420-435` (read-only enforced by routing to `makePlainRequest`, not by the prompt alone). Ours: interview is copilot→author only (`src/copilot/types.ts:80`). Low effort, modest value.

**8. Anti-pattern: overwrite card.** Theirs: `MainPopup.tsx:454-480` spreads the loaded card and `saveCharacter`s over it behind one confirm, no backup. Ours forbids it (`src/wizard/provisioning.ts:30`, baseline inv. 8). Keep it that way; if a "revise existing card" flow is ever wanted, it should produce a NEW card (copy) and let the author swap it in.

## Patterns to copy / anti-patterns to avoid
Copy:
- Schema narrowed to live state (enum of existing ids) so a model cannot name a target that does not exist (`src/revise-types.ts:75-94`).
- One schema → prompt example + validator (`src/schema-to-example.ts`), no hand-maintained duplicate.
- Current-state block injected just before the last message instead of accumulating stale copies in history (`ReviseSessionChat.tsx:392-411`).
- Read-only mode enforced by the code path, not by an instruction (`:420-435`) — same stance as our create-only.
- Storage load returns `{value, migrated, recovered, error}` and save returns `{persisted, error}` (`src/browser-storage.ts:15-25`) — matches our `WriteResult` discipline.
Avoid:
- Unescaped diff HTML via `dangerouslySetInnerHTML` (`CompareFieldPopup.tsx:23,46`).
- Lenient fallback that returns regex-scraped partial text when parsing fails (`src/parsers.ts:127-132`) — silently accepts truncated output; our strict parser + repair is right.
- JSON prefill escaping only `"` (`src/parsers.ts:162`) — backslashes/newlines break the continuation.
- Compiling user field text as Handlebars (`src/generate.ts:180-185`, field values) — any `{{` in a card is interpreted; plus the placeholder-swap hack around `substituteParams` (`:242-246`). We already escape braces in `quoteSlashArg`.
- Destructive overwrite of user assets (idea 8).
- Browser-local IndexedDB for authoring sessions: survives nothing across devices/browsers; fine for their scratch data, wrong for our per-chat state (three homes, inv. 13).

## ST host facts learned
- `ConnectionManagerRequestService.sendRequest(profileId, prompt, maxTokens, custom, overridePayload)` accepts `custom.signal` and forwards it to the backend fetch (theirs `src/request.ts:39`; ST `scripts/extensions/shared.js:415,424,463,483`, `scripts/custom-request.js:125,152,468`). **CONTRADICTS** our note `src/runtime/epochAbort.review.test.ts:9` ("takes … and no signal"). Verified on the current ST tree (`7c3994196`); check ST 1.18.0.
- `prompt` may be a message array; for chat completion it is passed as `messages`, for textgen it is formatted with the profile's instruct (`shared.js:443`, `:470`; theirs sends arrays `src/generate.ts:261`). Consistent with our gotcha (message array required for instruct).
- With `overridePayload.json_schema` on chat completion, ST returns `content` already `JSON.parse`d (`scripts/custom-request.js:490`); theirs handles both (`src/request.ts:118`). Our seam would return `""` (`src/services/stHost/connectionProfiles.ts:51-53`) — new trap, not yet in gotchas.
- `SillyTavern.libs` exposes `localforage` (and `Handlebars`, `DOMPurify`) to extensions (theirs `src/browser-storage.ts:27`; ST `script.js:294`, `lib.js:89`).
- `getContext().CONNECT_API_MAP[profile.api].selected` resolves a profile to `openai|textgenerationwebui` (theirs `src/generate.ts:97`) — cheaper backend classifier than our `presetBackend()` if ever needed for a structured-output probe.
- `substituteParams` resolves `{{user}}`/`{{char}}`; to keep them literal in generated card text they must be shielded (theirs `src/generate.ts:242-246`).
- `powerUserSettings.persona_description` is readable from context (theirs `src/revise-prompt-builder.ts:29`) — we deliberately never read it (privacy report).
- `globalContext.Popup.show.confirm/input` are the promise popups (theirs `MainPopup.tsx:191,359`).

## Verdict
Relevance **medium** — no chat-time mechanics, but it is the most mature card-authoring loop in the corpus and it touches our wizard, copilot parsing and host seam. The one thing worth taking: **idea 1, the host abort signal** — a cheap fix that corrects a false claim in our own records and cuts wasted calls on slow pods. Runner-up for the wizard: schema-narrowed structured output (2) plus per-field refine (5).
