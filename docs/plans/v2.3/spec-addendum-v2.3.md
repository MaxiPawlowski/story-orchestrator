# Spec addendum v2.3 — contract changes

Additive to `../v2/story-orchestrator-spec-v2.md`, `../v2.1/spec-addendum-v2.1.md` and the v2.2
rules in `../v2.2/00-overview.md`. Every row below is **proposed** until the named plan's gate
ratifies it; a plan may narrow a row, never widen it silently. Source: the review roadmap's
"Explicit proposed contract changes" table and the v2.2 integration review's recommendations,
filtered to what v2.3 actually builds. Revised 2026-09-20 after the peer review
(`review-astra-2026-09-20.md` Q7): every row traces to a review proposal; the defaults and
migration rules Astra questioned are stated here explicitly.

| Contract | Change | Migration / compatibility | Plan |
|---|---|---|---|
| Extraction protocol | A parsed delta always carries `source: "extractor"`. A delta naming a non-extractor quality, a quality outside the requested residual scope, or evidence that is not a **contiguous normalised span of one message inside the read window** is **rejected with a reason** and never enqueued. There is no evidence-length rule (short legitimate evidence such as `"crossed"` or `yes` is accepted). A response over `MAX_DELTAS_PER_READ` lines or the prompt budget is rejected whole (`oversized response`) and retried once. The line syntax is unchanged. | Fixtures gain `rejected`/`accepted` expectations per case; goldens that relied on leakage are re-recorded and the change is listed in the Gate record. | 02 |
| Judge inputs | Candidate content for memory verify, lore ranking, the warden and typed extraction travels in named `state` fields, never interpolated into instructions; a typed value and its evidence come from one request (combined option set, or a second request conditioned on the chosen value), so they cannot disagree. | Prompt-side only; calibrations re-run at floor. | 02, 05 |
| Story format: asset ownership | `requirements.lorebooks` is a dependency only. Write authority for the wizard is (a) the created-asset ledger of the session that made the asset (`wizardSessions[].applied`) or (b) an **explicit, durable, revocable grant** the author confirms on a card, stored in `wizardSessions[].grants` keyed by story id + book file id. Existing stories never receive ownership by migration; nothing is added to the story record. | Additive to the install-wide wizard store; format 2 readers unaffected. | 02 |
| Runtime task interface | Every asynchronous unit of work carries an immutable `RunToken {chatId, storyId, playedVersion, sessionEpoch, window: {from, to}, windowRevision}` minted at scheduling. A result applies only when the token still matches. `windowRevision` invalidates a read only when a message **at or below `window.to`** is mutated; a reply appended after the window is harmless. Mismatch → **discarded and journaled**. Abort is signalled on chat/story switch, restart, disable and stop; cleanup of an aborted task touches only state tagged with its own epoch. Applies to every writer in `src/runtime/**` and `src/wizard/**`, including `catch`/`finally` paths (architecture guard). | Introduced at every await-then-write site; no legacy callback may bypass the check. | 03 |
| Turn identity | A rendered reply is identified by `{chatId, messageId, revision}`, not by elapsed time. Duplicate events for one identity commit one boundary; distinct identities commit each. | None (in-memory). | 03 |
| Persisted runtime blob | v3 → **v4**, one schema for plans 03–06, non-recursive, designed in plan 04 before code: stamped `chatId`; `engine.historyFrom {boundary, messageId}` + base snapshot + bounded boundary log; provenance on memory maintenance events (`supersededAt`, retirement `{messageId, boundary}`, append-only ledger versions); `derived[]` artifacts with `inputs`; write-ahead effect ledger rows with stable targets and status. A v3 blob migrates with `historyFrom = current`: rollback before it is `unavailable` **permanently for that chat** (until Restart), never "until the first new boundary"; an unstamped blob is readable and stamped on first save; a stamped blob for another chat is refused and journaled. Every store compacts only below `historyFrom`. | The bump lands in plan 03; plans 04–06 add fields to v4 before any release; one captured real v3 blob fixture, re-captured after plan 05. | 03 (bump + stamp), 04 (history), 05 (provenance), 06 (effects) |
| Pinning | **Pin = retention.** A pinned record is never trimmed or expired, but it *can* be superseded (record kept, `supersededBy` set) and its validity follows its source: rollback of its only provenance quarantines it from injection until an author reconfirms it. A separate, explicit **lock** freezes truth and is author-only. An author override (reconfirm, lock, manual fact, "Store anyway") is anchored to the boundary it was made at: rolling back past its source message keeps it; rolling back past the override's own boundary removes it. | Legacy pins stay pins; the UI offers the conversion once per chat. | 05 |
| Provenance envelope | Memory entries, epistemic rows, ledger versions, scene fields, WI curator writes and "Store anyway" carry `{source, messageId, boundary, pass, sourceRevision?, inputs?, confidence?, override?, validity}`. `source` includes `blackboard` (a bound ledger row follows the quality's version) and `legacy` (a hydrated row with no envelope — a stated unknown, never dressed as an extractor read). `validity ∈ live | superseded | source-removed | conflicted | quarantined`. The warden, canon derivation and every injection builder consume `validity: "live"` only; a **conflicted** record is excluded, not ranked lower. Derived artifacts (compactions, summaries, canon, exclusions, dedup confirmations) carry `inputs` and are dropped or re-derived when any input is rolled back. | Persisted with the v4 blob; derived at read for canon. | 04 (derived), 05 |
| Host effects | Every host write is a ledger row `{id, effect, target, before, after, checkpointId, boundary, messageId, at, status}` with a **stable target identity** (group+member id, book file id+uid, AN slot, background name, preset name+api), persisted **write-ahead** (`pending` before the host call). Restore on leave/rollback/restart is **compare-and-set**: only if the host still holds `after`; otherwise `externally-changed` and the author decides. Statuses `pending | applied | failed | reverted | revert-failed | externally-changed`; `pending` rows are reconciled on hydrate. `cast_changes` is mirrored per chat and re-applied on hydrate. Unsupported effects (preset on any non-textgen backend, **chat completion included in v2.3**) are diagnosed before play, never reported applied. Durability of a persist is evidenced by observing the save request's status and by read-back, never by `await saveMetadata` (the host swallows save errors). | Additive per-chat ledger; group `disabled_members` is restored, not migrated. | 06 |
| Generation cache | Every validated outcome of a generated beat gets a stable `id` and becomes its own outgoing transition with deterministic priority (declaration order) and per-path progress validation. States `draft / rejected / needs-review / validated / inserted / stale` are explicit; a boundary inserts only `validated`; a critic failure never partially inserts. | Existing caches are invalidated on upgrade and regenerated on demand; a played graph is never mutated invisibly. | 07 |
| Story format: agency | Optional per-checkpoint `agency {protect_player_choice?, never_narrate_player_action?, objective_kind?: "world_pressure" \| "player_action", alternate?: checkpointId}`. **Defaults when absent are `true / true / world_pressure`**, which changes steering and generation phrasing for every story that does not declare the field — a deliberate behaviour change, not "absent = today". The policy takes precedence over pacing steering and scene look-ahead. When a refusal cannot be classified for two boundaries, the outcome stays unset, the player sees a neutral line, and the author gets a recovery (authored alternate, generated alternate, or nudge). | Additive optional field; old readers ignore it; old stories change phrasing by default. | 07 |
| Compatibility claim | A release ships two files with different lifecycles: the **build manifest** (`dist/manifest.json`: version, commit, source sha256, bundle sha256, host version + host-file hashes, required capabilities) written by the build, and the **acceptance attestation** (`docs/release/<version>/attestation.json`: bundle hash loaded, host commit, browser, model/template and judge model ids, journeys green) written by plan 11. No "all SillyTavern versions" promise. A tracked `dist/` is checked by hash, not by commit ancestry. | Generated at build (manifest) and at acceptance (attestation). | 08, 11 |
| Story format: player summary | *Proposal only*: optional `player_summary` per checkpoint for player surfaces, separate from the author objective. **Plan 11's human eval decides it** (objectives leaking twists); if approved, a v2.4 plan builds it with the format decision. Plan 09 neither builds nor decides it. | Additive optional field if built. | 11 (decision) |
