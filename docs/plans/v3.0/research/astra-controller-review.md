Several opportunities remain compatible with unchanged prompts:

- **S — Idle speculative prefill:** prepare the likely next member’s exact stable prefix while the player types; validate against the eventual prompt and cancel/yield immediately. This hides work without inventing player text. Side passes dependent on new state cannot safely start early.
- **I/S — Concurrent prefill/decode was not actually disproved.** The sequential `parallel=2` replay tests slot overhead, not continuous batching. Two independent side requests or chunked prefill alongside decode could improve throughput, but compete for power, VRAM, and inter-token latency. The gateway currently serializes them.
- **I/S — CUDA 13 and the unlock deserve separate tests.** The unlock targets FP16/BF16 operations with FP32 accumulation; stock quantized MMQ decode should gain little. Compare stock MMQ against `GGML_CUDA_FORCE_CUBLAS` with FP32 accumulation, including activation-memory peaks. Neither microbenchmark TFLOPS nor toolkit version predicts application gains. [unlock measurements](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/main/docs/RESULTS.en.md), [llama.cpp build options](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)
- **I/S — Revisit alternatives selectively.** IQ4_XS could buy cache/image headroom, but speed and blind quality require measurement. Mixed KV types need compiled FA support; q4-V already lost decode speed here. vLLM’s host KV offloading now documents SWA support, weakening “GPU cache starvation” as a categorical rejection; quant, sampler, Windows, and RAM costs remain. ExLlama’s failed configuration does not establish an engine-wide limit, but retrying it ranks low. [IQ4_XS](https://github.com/ggml-org/llama.cpp/pull/5747), [vLLM offloading](https://docs.vllm.ai/en/latest/features/kv_offloading_usage/)
