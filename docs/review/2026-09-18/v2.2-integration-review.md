# v2.2 integration and feature review — 2026-09-20

## Scope and confidence

This is a bounded source/design review of how Story Orchestrator's features compose, with a focused
review of v2.2. It is **not** acceptance certification. I did not run Jest, the browser, SillyTavern,
the server plugin, or either model. Runtime, latency and UX conclusions below are source-based and
explicitly need the unfinished live and human gates.

Reviewed snapshot: Git `5078476a11c2947a7d6ff03bd3d99c400570957a`, committed
`2026-09-20T01:25:32-03:00` (`v2.2: record the live gate status (J11 24/26, calibrations 11/11,
three product bugs found and fixed)`). The worktree already contained the ongoing review-dossier
edits listed by `git status`; this review did not modify production code or those edits.

The direct answer is: the major pieces form a credible loop, but they do not yet form a reliably
owned, fully explainable roleplay system. The deterministic boundary remains a good spine. v2.2
adds useful judgment at the right seams and preserves fallbacks. Composition now creates new risks,
however: one late result can cross chat ownership; stale scene state can feed both narration and
future planning; multiple derived truth stores can reinforce one another without shared provenance;
and pacing plus generated scaffolding can narrow player choice without an explicit agency contract.

## Jev: identity and architectural idea

The model is **TypeSafe AI Jev**, pinned here as `jev-1.13.0`, not a second chat LLM. The plugin
calls TypeSafe's `/v1/systemone` endpoint
(`server-plugin/story-orchestrator-judge/index.mjs:8,22`). Primary sources reviewed:
[introduction](https://docs.typesafe.ai/introduction),
[System One](https://docs.typesafe.ai/concepts/system-one),
[primitives](https://docs.typesafe.ai/primitives),
[building guidance](https://docs.typesafe.ai/concepts/how-to-build-with-system-one),
[confidence](https://docs.typesafe.ai/confidence),
[known jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13),
[models](https://docs.typesafe.ai/models), and the
[official GitHub organization/SDKs](https://github.com/typesafe-ai).

I found official SDKs, but no official public Jev weights repository or peer-reviewed Jev/RLCD
paper in this bounded check. “RLCD” (reinforcement learning for calibrated decisions), latency,
consistency and calibration are vendor claims. The docs qualify calibration as a property across
groups, not proof that one answer is correct. Local calibration matters more here.

Jev receives shared `state` plus typed questions. `Choice` selects one code-defined option and
returns a distribution and confidence; `Score` locates state on code-defined ordered levels;
`Noul` returns the probability that one statement is true, with no separate confidence field.
Questions in one request are independent. Jev does not explain, plan, write prose or own an action.
This makes v2.2's rule unusually apt: code owns workflow, thresholds, fallback and effects; Jev
supplies bounded common-sense judgments; the story model keeps generation. Per-use policy is
inspectable at `src/judge/policy.ts:1-61`, and runtime fallback/version logging at
`src/runtime/judge.ts:100-140`.

### Consumer fit

| Consumer | Assessment |
|---|---|
| Director | **Excellent.** A role `Choice`, addressed/reason `Noul`s and silence `Noul` fan out; code confidence-gates and combines them (`src/judge/director.ts:39-89`). Withholding names-only after its floor miss was correct. |
| Memory verify/pairs | **Excellent.** One support `Noul` per line; pair relation `Choice` plus same-thing `Noul`, with a code veto and confidence floor (`src/judge/memory.ts:33-77`). |
| Scene/look-ahead | **Strong.** Location/time `Choice`; scene-break, presence and per-candidate heading `Noul`s; explicit `unclear`/`elsewhere` support abstention (`src/judge/scene.ts:69-104`). |
| Lore/curator filter | **Strong retrieval fit.** One relevance `Noul` per entry, then code top-k/filter (`src/judge/lore.ts:49-77`). Jev's context-rot warning means one book's calibration does not prove every distribution. |
| Warden | **Excellent primitive, risky source truth.** One contradiction `Noul` per fact; code writes the note (`src/judge/curators.ts:10-31`). |
| Typed extraction/stall | **Most inventive fit.** Code finds bounded candidates and Jev chooses; simple stall leaves direct-write only at 0.95 (`src/judge/extraction.ts:61-197`). The independent evidence `Choice` cannot condition on the chosen value, so value/evidence can disagree. |
| Expansion critic/ranker | **Weakest conceptual fit.** Chain-level `Noul`s plus trajectory `Score` are code-composed (`src/judge/expansion.ts:28-80`), but “any beat contradicts any of 40 facts” hides many comparisons. Local 40/40 and 10/10 calibration is encouraging but small/authored; per-beat/fact fan-out would fit Jev better. |

Two corrections follow directly from Jev's contract. Keep untrusted content in named state fields:
memory, lore and continuity interpolate candidate content into instructions
(`src/judge/memory.ts:37`; `src/judge/lore.ts:61`; `src/judge/curators.ts:15`), while
TypeSafe recommends structured state and documents adversarial-content sensitivity. Also reconcile
independent answers in code. Memory pair's veto does this well; dependent value/evidence should use
a combined option or a second bounded request.

The floor discipline is one of v2.2's best decisions. OOC, memory rerank and scene-setter missed
their declared floors and were withheld. Jev's best future role is bounded contrastive scoring over
options already present—per-branch agency compatibility or per-outcome support—not free-form intent
generation.

## How the composed loop behaves

The happy path is coherent:

1. Rendered character replies commit a boundary through `TurnBridge`; the boundary drains queued
   deltas, selects at most one deterministic transition, applies host effects, then persists
   (`src/runtime/turnBridge.ts:44-63`; `src/runtime/runtimeManager.ts:207-233`).
2. Ordered boundary work schedules typed reads, reconciliation, expansion, scene read, the warden,
   compaction, the WI curator and consolidation (`src/runtime/boundaryWork.ts:30-146`). This is a
   clear orchestration point and keeps model work away from the deterministic engine.
3. Shared extraction separates judge-answered hinted qualities from the residual LLM scope, then
   queues evidence-bearing deltas for the next boundary (`src/extraction/sharedRead.ts:39-77`).
4. Accepted reads update memory, arcs, private knowledge and the ledger; pacing turns committed
   tension into a generation hint; scene state and continuity notes add prompt context
   (`src/runtime/coordinators/extractionCoordinator.ts:152-174`;
   `src/runtime/coordinators/pacingCoordinator.ts:47-100`).
5. Expansion uses canon/facts/state and, when opted in, scene look-ahead to prepare generated beats;
   the judge critic/ranker is subordinate to binding code checks (`src/runtime/coordinators/expansionCoordinator.ts:135-167`;
   `src/generation/generate.ts:38-67`).
6. The player sees one composed narrative/status model, while author machinery stays in author view
   (`src/runtime/snapshotBuilder.ts:33-65`; `src/components/drawer/PlayerOverview.tsx:44-70`).

That architecture supports flexible play better than a monolithic model pass. The remaining gaps
are at ownership, freshness, shared truth and agency boundaries rather than in the basic feature
inventory.

## New composition findings

### C1 — P1 reliability: v2.2 late results do not share immutable chat/session ownership

This is source-traced and **not live-reproduced in this bounded review**. The new lore selector
captures the current story, state and a cache key, then awaits the lorebook read and parallel judge
calls. It force-activates the chosen host entry objects without rechecking chat, story, message
revision or a session epoch (`src/runtime/loreSelect.ts:38-69`). The selector is one install runtime
whose host effect targets ST's next global WI scan (`src/runtime/index.ts:114-133`). A switch from
chat A to chat B during the wait can therefore let A's selection affect B's scan.

The same ownership test is incomplete elsewhere. Scene read checks only that the current chat has
the same last numeric message index (`src/runtime/coordinators/sceneCoordinator.ts:65-84`); two
chats at index 7 can accept A's late scene record and prompt injection into B. Typed extraction uses
state `lastMessageId` and current chat length, also without chat/story identity
(`src/runtime/coordinators/extractionCoordinator.ts:106-119`). `JudgeRuntime` obtains the boundary
and message context only after the await, so the call-ring record itself can be attributed to the
new chat (`src/runtime/judge.ts:100-124`; wiring at `src/runtime/index.ts:86-92`).

This is more than a repeated async bug: v2.2 connects the late record to scene injection, player
location, expansion look-ahead, forced lore and author diagnostics. One ownership error can affect
both the next generation and the evidence used to explain it.

### C2 — P1/P2: failed scene reads retain an active old scene, creating a self-reinforcing loop

On no answer or timeout, `SceneCoordinator.run` returns without clearing or aging the previous
record (`src/runtime/coordinators/sceneCoordinator.ts:71-84`). `sync` continues to inject that old
tracker while the feature remains active (`:87-100`). The same record supplies the player's
“At …” line (`src/runtime/snapshotBuilder.ts:54-65`) and expansion's `headingTo`
(`src/runtime/coordinators/expansionCoordinator.ts:135-147`).

The result is an integration feedback loop: a stale location/presence block can steer generated
prose, the next judge read sees prose influenced by that block, and prepare-ahead can spend model
work on the old heading. Boundary ordering adds an intentional one-boundary lag: expansion runs at
40 and the async scene read at 55 (`src/runtime/boundaryWork.ts:67-97`). That lag is acceptable when
the heading is stable, but there is no freshness contract for failure, rollback, rapid travel or a
new chat with the same message index.

### C3 — P1 before auto mode: derived truth stores can enforce each other's mistakes without shared provenance

Memory verification covers only new fact/memory lines; deltas, arcs, epistemic signals and ledger
signals explicitly bypass it (`src/runtime/coordinators/extractionCoordinator.ts:177-200`). The
continuity warden then treats bound ledger rows and live/pinned facts as established truth
(`src/runtime/continuity.ts:7-15`) and can inject a corrective note into the next generation
(`src/runtime/coordinators/stagecraftCoordinator.ts:341-353`). The review card labels each input
only as “established” and shows no originating message/evidence/store or conflicting value
(`src/components/drawer/StagecraftPanel.tsx:54-72`).

The earlier review already established incomplete rollback/provenance and ambiguous pin semantics.
v2.2 raises their consequence: a stale ledger or pinned/source-invalidated fact is no longer merely
displayed or recalled; the warden can actively make future prose conform to it. The “Store anyway”
escape hatch similarly inserts a rejected line at the judge's low probability without marking an
explicit author override in the entry contract (`src/runtime/coordinators/memoryCoordinator.ts:282-291`).
The separate blackboard, memory, canon, epistemic, ledger, scene and WI records need a common account
of source and authority before automatic corrective behavior is safe.

### C4 — P2 product contract: deterministic progression is strong, but player agency is still implicit

The player surface explains location, objective, threads, canon, pending work and extraction setup,
which is good recovery feedback (`src/runtime/narrative.ts:65-96`). It does not express which parts
of an authored objective are constraints on the world versus suggestions to narration, or how a
player can reject a predicted route without fighting the system.

This matters because several independent steering features compose. Strong pacing drift tells the
model to “force a confrontation, reveal, or hard consequence” (`src/pacing/steering.ts:19-28`).
Look-ahead selects one likely heading for pre-generation. Generated beats can declare multiple
outcomes, but merge still builds transitions from `beat.outcomes[0]` only
(`src/generation/merge.ts:23-50`), even though expansion scope collection iterates all outcomes
(`:61-69`). The critic/ranker evaluates beat-chain quality, not whether the resulting guidance
preserves the player's declared refusal or alternative action.

The likely experience is flexible when extraction recognizes the player's action and the authored
graph covers it. At branch edges, the combined pacing/guidance/first-outcome behavior can feel like
the narrator is pulling play back toward its prepared route. The existing player flag is useful
evaluation instrumentation, but it is not a runtime agency contract or recovery action.

## Ranked recommendations

### 1. Must-fix reliability — one run token for every asynchronous read and host effect

**Scenario:** lore selection begins in chat A; the player opens chat B before the judge responds.
No A result, call record, injection or force activation may touch B.

Add a shared immutable token such as `{chatId, storyId, playedVersion, sessionEpoch,
sourceWindowRevision, messageId}` at scheduling time. Validate it immediately before every extras
write, apply-queue enqueue, prompt injection, call-ring append and host effect. Abort supported
requests on chat/story switch or stop; invalidate the token where cancellation cannot stop the call.
This generalizes the existing reliability finding into one contract used by every v2.2 consumer.

Tradeoff: more coordination code and discarded work after legitimate switches. Acceptance: delayed
success, timeout and failure across switch/restart/edit/stop leave both chats, every injection key,
the WI force map and both call rings unchanged; same-chat controls still apply exactly once.

### 2. Must-fix reliability plus a small author capability — shared provenance and reconciliation

**Scenario:** a fact says the bridge fell, a later ledger value says it is intact, and the scene
tracker still places the cast there. Before the warden corrects narration, the author should see the
conflict, each source message and authority, then keep one, reread, or mark a deliberate canon fact.

Give blackboard values, memory/facts, canon sentences, epistemic rows, ledger rows, scene fields and
WI changes a common provenance envelope: source message/revision, producing pass, confidence,
author override, supersession and validity. Add one reconciliation queue for conflicts and unknown
rollback history. Warden auto mode and derived canon should consume only currently valid records;
“Store anyway” should become an explicit author override rather than a low-confidence model fact.

Tradeoff: persistence migration and a denser author UI. Acceptance: edit/delete/reload replay yields
the same active truth as a clean replay; a conflicted or source-invalidated record cannot steer a
reply until resolved; the UI can trace every injected statement back to evidence or an explicit
author decision.

### 3. Small missing capability — a composed next-turn preview with freshness and fallback

**Scenario:** the next reply will receive a pacing escalation, stale scene tracker, private
knowledge block, continuity note, lore force and checkpoint guidance. Today these are split across
panels and payload tooling. The author needs one preflight view to spot a contradiction before
generation.

Build a read-only “Next turn” preview from the existing injection registry and runtime snapshot. For
each contributor show owner, target speaker, source message/revision, freshness, fallback state and
whether it will be consumed once or persist. Provide only existing safe controls: clear a one-shot
note, rerun a scene read, or open the owning editor. Keep raw private blocks author-only.

Tradeoff: the preview must mirror actual host composition closely enough not to mislead. Acceptance:
for solo and group generation, its ordered contributors match a captured real payload; a timed-out
scene read is visibly stale/unknown rather than silently current; clearing a one-shot item removes
exactly that item.

### 4. Product contract — authorable player-agency policy and complete generated alternatives

**Scenario:** the prepared route expects accepting a duel, but the player refuses and negotiates.
The narrator should acknowledge the refusal, preserve the world consequence, and either follow an
authored alternate outcome or expose an author recovery choice instead of repeatedly forcing the
duel.

First complete the existing multiple-outcome promise so every generated outcome gets a stable id,
gate, deterministic priority/tie rule and validation. Then add a small checkpoint-level agency
policy for generation guidance: protect player decisions, never narrate an unspoken player action,
and classify objectives as world pressure versus player-required action. Feed that policy to pacing,
expansion generation/critic and the driver preview, with a player-visible neutral recovery line only
when the story genuinely cannot classify the action.

Tradeoff: more branching and stricter critic fixtures; authors must state intent for ambiguous
objectives. Acceptance: refusal/alternate-action fixtures never narrate the player's compliance,
all valid generated outcomes remain reachable, and a human player session has no unresolved
railroading flag. This extends plan 08's human rubric; it does not replace it.

## What plan 08 already covers

Do not add a second feature for work already planned. Plan 08 already owns the full judge-off and
judge-on matrices, per-use calibration, cost/latency/fallback report, recommended configuration,
privacy disclosure and player/author human sessions (`docs/plans/v2.2/08-acceptance.md:37-99`). Those
deliverables are prerequisites for recommending v2.2 defaults. The current settings self-test only
reports speaker-direction fixture accuracy (`src/components/settings/JudgeSettingsGroup.tsx:88-98`),
so the plan-08 recommended configuration should eventually become a setup/readiness summary rather
than another long list of flags. That is completion of planned work, not a new product expansion.

The most valuable next step is therefore not another autonomous curator. It is to make the existing
passes share identity, provenance, freshness and an explicit agency contract, then complete plan 08
against that integrated behavior.
