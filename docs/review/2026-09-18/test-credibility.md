# Test credibility audit (preserved baseline)

## Scope and method

This is a read-only source audit of the preserved isolated baseline at revision `0a094e...`. It maps the journey runner, scenario runner, model fixtures, runtime live suite/self-test, and Storybook runner. I did not rerun the host, browser, model, or Storybook. The original workspace changed concurrently, so the line references and conclusions below describe the preserved baseline, not necessarily the later working tree.

Overall, the harness has substantial behavioral coverage. All 63 automated J1-J10 checks contain either a supported `expect`/`expect_ui`, a polling condition, or an explicit throwing assertion in `eval` (usually several). The deterministic scenarios intentionally inject model text while still exercising the production parse/apply paths; the `live-*` scenarios and most journey generation steps use the configured model. The main credibility risks are in the definition of a 窶徭trict窶・journey pass, unchecked assertion schemas and return flags, delta-only live-fixture scoring, and permissive self-test grading.

## Runner semantics

- A check passes when `runSteps` completes without a thrown exception. The engine processes only the first key of each step, and an empty step array also passes (`scripts/debug/so-scenario.mts:724-745`). `expect` and `expect_ui` throw on their recognized failures (`so-scenario.mts:709-717`). I enumerated the current fixture keys; every declared top-level `expect`/`expect_ui` key is implemented.
- Unknown expectation fields are silently ignored. `evaluateExpect` has no unknown-key validation before returning `ok: failures.length === 0` (`so-scenario.mts:126-314`), and UI expectations only inspect `selector`, `contains`, and `notContains` (`so-scenario.mts:628-652`). A typo can therefore turn an assertion-only step into a vacuous pass. **Severity: high for future test credibility; confidence: high.** Remedy: validate step and expectation objects against a closed schema and reject unknown or empty assertion objects.
- `import_story`, `extract`, `expand`, and `restart_story` return an `ok` value without throwing when it is false (`so-scenario.mts:379-428`). `copilot probe` has the same pattern (`so-scenario.mts:462-463`). Most current fixtures follow these verbs with state assertions, but the runner does not guarantee this. **Severity: medium; confidence: high.** Remedy: make these verbs throw on false unless the fixture explicitly requests `expectFail`.
- Waits poll and throw on timeout (`so-scenario.mts:317-376`). No current wait object has multiple primary conditions, so the implementation's first-satisfied/OR behavior is not presently ambiguous. UI assertions retry for five seconds by default (`so-scenario.mts:628-640`). New-chat setup retries once (`so-journey.mts:168-174`). Curator `expectOps` retries up to three real calls by default, then fails with dropped/raw-response evidence (`so-scenario.mts:542-555`).
- Capability expressions are probed lazily, cached, and exceptions become `false` (`so-journey.mts:108-127`). Missing capabilities yield `blocked`; `--strict` promotes only blocked outcomes to failure (`so-journey.mts:279-292,309-322`). Human checks always become `skipped`, reserved journeys become `not-runnable`, and neither fails strict mode. Cleanup failures are captured as report data and also do not fail the run (`so-journey.mts:191-235,298-310`). Thus 窶徭trict pass窶・means no automated failure, runner exception, or blocked automated check; it does not mean human acceptance or successful cleanup. **Severity: high if reported as full acceptance; confidence: high.** Remedy: publish separate automated, human, and cleanup gates; add `--require-human-record` and fail strict mode on cleanup errors/not-runnable checks.
- `--only` marks unselected checks skipped (`so-journey.mts:281`), so a filtered run can exit successfully. Records include tallies and `strict`, which allows consumers to detect this (`so-journey.mts:317-322`); acceptance tooling should reject any unexpected skipped count.

## Fixture corpus and live suite

The deterministic extraction corpus discovers at least 20 complete triples and checks prompt scope, exact parsed `{q,v}`, evidence substrings, rejection reasons, and required/forbidden fact text against archived responses (`src/extraction/extraction.test.ts:211-255`). This is strong parser/prompt regression coverage and intentionally does not call a model.

The browser live suite is genuinely model-backed: `registerLiveSuite` builds the same fixture prompt, calls `callExtractionModel` with the selected profile, and parses the response (`src/runtime/liveSuite.ts:16-29`). The CLI then scores exact non-tension deltas and a ﾂｱ0.3 tension tolerance (`scripts/debug/so-live-suite.mts:30-44`). Its credibility limits are material:

- Although `runFixture` returns facts and rejected lines, the scorer ignores both (`so-live-suite.mts:82-100`). In the preserved 22-fixture corpus, six fixtures require facts and seven require rejected lines, so those behaviors can all regress while live accuracy remains 100%.
- Incomplete fixture triples are silently skipped (`so-live-suite.mts:52-70`), and `--filter` can run an arbitrary subset. The only protection is 窶彗t least one fixture.窶・- The default gate permits 10% fixture failures (`--min 0.9`; `so-live-suite.mts:9-20,98-116`). That is a policy choice, not exact contract conformance.

**Severity: high if 窶徑ive suite passed窶・is presented as full extraction/memory correctness; confidence: high.** Remedy: score facts, rejection reasons, epistemic/ledger/arcs when specified; record discovered/skipped fixture names; require an expected corpus count for release runs; label the metric 窶徘lot-delta accuracy窶・ preserve per-tier thresholds rather than one aggregate.

## Runtime self-test

The product UI calls `runModelSelfTest` with the selected profile and no debug responses (`src/index.tsx:147-160`), so an actual user run is live. Unit tests intentionally mock the extraction client and pass fixed responses (`src/runtime/selfTest.test.ts:5-15,38-68`); they validate prompt routing, parsing, grading, failure, and cancellation rather than model quality.

The live grader is too permissive for its wording:

- Deltas pass if either `location=tunnel` or `has_lantern=true` appears (`src/runtime/selfTest.ts:77-86`).
- Memory and arcs pass on any nonempty line (`selfTest.ts:89-99`), without checking the tunnel/lantern/debt semantics.
- Epistemic and ledger pass on any nonempty entry (`selfTest.ts:103-118`), without checking Corin, Bel, hidden letter, or wounded arm.
- A capability-disable suggestion appears only when epistemic/ledger results are empty (`selfTest.ts:146-151`). Wrong-but-nonempty output passes, and a model-call error returns early without a suggestion (`selfTest.ts:137-143`).

**Severity: high because this can bless a semantically incapable profile; confidence: high.** Remedy: grade both required core deltas; match required memory/arc concepts; require the expected epistemic subject/tag/hidden-from relation and ledger entity/field/value; distinguish transport failure from semantic failure; add negative unit responses that are well-formed but about the wrong entities/content.

## Storybook runner

The preserved baseline has 26 story files, 107 `export const` declarations, and 103 `play:` callbacks by static count. This is broad component-interaction coverage rather than render-only smoke testing. The standard test runner executes those play functions, while the custom hook injects axe and runs it after each story unless a story disables accessibility (`.storybook/test-runner.ts:5-17`). I found no story-level `a11y.disable` in the preserved story files.

The boundary is intentionally isolated: webpack aliases `@services/STAPI` to a Storybook mock (`.storybook/main.ts:16-36`). That mock uses fixed profiles/assets/context, no-op persistence/prompts, empty model responses, and canned popup/background behavior (`.storybook/mocks/STAPI.ts:22-102`). Storybook passes therefore support component rendering, local interaction callbacks, and accessibility against fixtures; they do not support live SillyTavern persistence, event ordering, model calls, world-info writes, or popup behavior. Also, color-contrast axe checks are globally disabled (`.storybook/preview.ts:14-17`), while other axe rules remain active.

**Severity: informational as long as the suite is labeled component coverage; confidence: high.** Remedy: report play-function count and axe scope separately, explicitly note the STAPI alias and disabled contrast rule, and rely on journeys for host seams.

## Coverage limits

This audit did not execute the baseline or current host, inspect model response quality, validate saved screenshots, or re-score historical acceptance records. It did not review every assertion inside all 103 Storybook play callbacks. Current-source drift may have changed individual lines after the preserved snapshot. The audit establishes what the harness is capable of proving and where a passing result can be weaker than its label; it does not re-certify any recorded pass.
