A story engine that runs underneath your roleplay chat

LLMs write a good next message but can't run a story: over long play the plot wanders, tension flattens and setups never pay off. Story Orchestrator lets an author define a story as a graph of checkpoints with typed conditions between them. While you chat normally in SillyTavern, the extension quietly reads what happened, keeps a scoreboard of story state, advances the plot by fixed rules, remembers what matters, steers the narrator, decides who talks in group chats, and generates connecting beats where the author left gaps.

For the player

Pick a story, chat as usual. A HUD strip shows where you are and the tension; a drawer shows a spoiler-free "where am I" overview and what the story remembers. Swipes, edits and deletes are understood — the story steps back with you.

For the author

A Checkpoint Studio (graph editor + diagnostics) and a Wizard that interviews you and creates the characters, lorebook and group a story needs. An "Author view" reveals the machinery: blackboard, scheduler, next-turn prompt preview, memory internals.

Under the hood

A pure deterministic engine (no AI, fully testable) + a separate "memory model" that does all fuzzy reading off the reply path. Everything host-facing goes through one seam (STAPI), and every async write proves it still owns the chat.

The design spine: deterministic engine, measured AI layer

The single most important idea. The rulebook is arithmetic; the only fuzzy step is the AI reading prose into typed values — and that step is isolated, evidence-backed and scored against answer keys.

🧮 Deterministic engine no AI

  • Blackboard of typed qualities (int/float/bool/enum/string), with versions, latching (a flag stays true) and monotonic checks (progress only rises).
  • Gates: JSON condition trees {all|any|not} over leaves {q, op, v}. Same blackboard ⇒ same result.
  • Transitions with priority; exactly one checkpoint active; one transition per boundary.
  • Apply queue: all writes wait and drain only at a turn boundary. Boundary logs + snapshots ⇒ rollback.
  • Lives in src/engine/**, which is forbidden (by a build-failing test) from importing the host.
⇄

🔎 Measured AI layer fuzzy, isolated

  • Shared read (extractor): a second "memory" LLM reads recent chat and proposes DELTA lines + memory lines, each quoting evidence.
  • Closed vocabulary: can only name declared qualities and allowed values; strict line parser rejects the rest.
  • Runs off the reply path on a priority scheduler; results are applied only at the next boundary.
  • Scored by goldens in jest and by a live suite against the real model (per-tier floors).
  • Other AI helpers (scaffold generator, critic, curator, director, judge) propose; code decides.
A gate on message_count >= 5 is deterministic end-to-end. A gate on mara_trust >= 4 is deterministic given the blackboard, but rests on a reading. The author chooses per gate where on that spectrum to sit.

Extraction — the one fuzzy step

A missed reading is load-bearing (a gate may never open), so the read is hardened in layers.

Anatomy of a shared read

  1. Window: recent messages (cadence N, stability lag K), cleaned of hidden/system/extension rows.
  2. Scope: only not-yet-latched qualities gated at or ahead of the active checkpoint on any reachable path (+ snapshot qualities). Wide by default; scope_hint narrows.
  3. Contract: each quality's rubric (question + scale) + transition extraction_hints.
  4. Call the memory model via a Connection Manager profile (inline <think> stripped).
  5. Parse strict DELTA/MEMORY/arc/epistemic/ledger lines; reject unknown keys, bad values, and any delta whose evidence quote isn't in the window.
  6. Audit stored; accepted deltas queue for the next boundary.

Example model output

DELTA mara_trust +1 | "Mara laughs despite herself and slides the map across"
DELTA player_has_key true | "You close your fist around the brass key"
MEMORY [event:2:session] Mara showed the player the vault map :entity=Mara
[arc] The missing ledger
[knows] Mara: the vault's east door is unguarded after midnight
[hiding] Mara from Guard Captain: she forged the pass
SCENE_NONE

Scheduler priorities: P0 forced (cue/reconcile) · P1 cadence read · P2 scene-break tier passes · P3 scaffolding + critic · P4 consolidation / canon. Two lanes so a long generation never delays a forced read.

Stall reconciliation If no gate fires for max(1.5 × target_turn_length, 6) turns, a targeted re-read runs over the turns since the checkpoint was entered, for the unmet gates' qualities only. It may raise an under-read value on quoted evidence; un-latching needs explicit contradicting evidence. It can never write source: code qualities.
Failure handling (being reworked in v2.4 plan 03) Today a failed read can pause extraction install-wide. v2.4 decision D4: the runtime never writes extraction.enabled again — failures are classified transport (in-memory breaker per profile, backoff, auto-resume, player "Try again"), config (not-configured + a Repair step) or bug (per-chat error, retried next boundary). Every call becomes abortable, time-bounded and size-bounded.

Maintenance machinery

  

    
Scene detection
Code heuristics (time-skip, location change, ---, cast change) force a read; every read also asks "did a scene break?". Breaks trigger heavy tier passes + a scene summary.

    
Supersession
A changed fact retires its predecessor instead of coexisting. Same event as a blackboard mutation, seen from the memory layer.

    
Consolidation
Dedup via ST's vectors backend (dup ≥0.82 / same-topic ≥0.55), Jaccard fallback. Pin / exclude / edit are honoured forever.

    
Derived artifacts
Every summary/canon/dedup records its inputs and what it removed, so rollback ≡ replay (property-tested: 4 seeds × 400 cuts).

  

  
Memory reaches the prompt as injected blocks at controlled depths (single registry: constants/injectionRegistry.ts), as {{story_memory_*}}/{{story_canon}} macros, and as a per-chat World Info mirror book (Story Orchestrator - <title> - <chatId>).







  
Pacing & tension

  
Tension is read as one of five named levels (models label these reliably; 0–1 ratings are noisy), mapped to numbers, smoothed with an EMA into tension_current. The engine compares it to the author's dramatic shape and feeds the narrator a one-line hint. Pure arithmetic — no AI call.

Background generation & convergence

  
Authors write anchors (guaranteed beats) and may leave stubs between them. When the player approaches a stub, the extension generates scaffolding — not prose — for the bridging beats. The main model narrates them at runtime like any authored beat.

  

  

  
Convergence is deterministic: each anchor has a progress_toward_<anchor> counter (source: code). Generated transitions add declared increments; the edge into the anchor requires progress ≥ threshold. Nothing fuzzy can write the counter. Since v2.3 every generated outcome is its own route; a chain with any unusable route is needs-review, never half-inserted.

Stagecraft, the curator, the warden & the judge

  

    
Deterministic stagecraft first
Checkpoint effects fire on activation (and idempotently on hydrate): Author's Note (text/role/depth), preset, World Info on/off, cast enable/disable, scripted or LLM NPC replies, background. Every host effect goes through a write-ahead ledger and is restored compare-and-set on leave.

    
World Info curator
An optional background agent that proposes only: typed ops against the story's authored stagecraft.lorebooks allowlist, reviewed in the drawer (accept mode review|auto|off), applied at a boundary, reverted on rollback. Off by default. Checkpoint-gated entries are invisible to it.

    
Continuity warden
Checks the last reply against known facts; an accepted note is injected for one loud generation (depth 0), committed only when that generation renders its reply. Never rerolls, never rewrites.

  

  

    
The judge (TypeSafe Jev, via an ST server plugin)

    
A small "System One" model that answers typed questions (scores, choices) fast. Rules that never bend: never blocks, never writes; every use is its own install-wide opt-in, all off by default and never flipped by a plan; every use keeps today's path on disabled/timeout/error; the key lives server-side only. Each use must beat a predeclared floor on a calibration fixture — and a floor that isn't reached is never retuned (e.g. the lore-ranking "Score" arm was measured, lost on nDCG, and was not built).

Safety invariants (the hard-won rules)

  
Most of v2.1–v2.4 was spent making the extension correct under a hostile host: chat switches mid-await, other extensions, eventless edits, saves that swallow their own errors. Each rule below exists because a real defect was found.

  







  
Version timeline

  







  
v2.4 — "correct under the host as it really is" in progress

  
v2.3 made the extension correct under the mutations we modelled. A review of 55 community extensions, Jeved and Reddit threads found the host is wider: ST mutates chats without events (/hide, message moves, branches), other extensions generate inside our turn and patch fetch, and MESSAGE_DELETED doesn't carry what we assumed. v2.4 closes that gap first, then spends the rest on author leverage and judge uses that earn their floor. No new autonomous agent, no reroll, no rewrite pass.
